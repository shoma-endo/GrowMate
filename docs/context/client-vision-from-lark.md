## 1. 要約：プロダクト思想・背景

### 1.1 メディア運用と AI の役割

- **内部リンクを張り巡らせてドメイン全体の強度を上げる**ことに強い期待を置いており、手作業では負荷が高い領域を **登録済みコンテキストを読ませた AI** に担わせたい、という動機が繰り返し表れている（過去記事・固定ページ・お客さまの声ページ等の参照）。
- **LP・記事の型（見出し階層・文字数・箇条書きなど）を厳密に守らせる**ニーズがある。プロンプトで「最優先・違反不可」レベルまで指定している例がある。

### 1.2 品質・データ完整性

- **エビデンス（根拠）チェックを最優先課題**として位置づけ、項目の最大数とコスト感を踏まえて **優先順位付け**したい、という発言がある。
- 分析系では **取得できる指標はできるだけ保持**し、UI では表示のオンオフを選べる形がよい、という考え方がある。**順位だけでなくクリック率なども重要**、**上書きより履歴が欲しい**（サーバ負荷とのトレードオフ懸念あり）という技術的関心がある。

### 1.3 WordPress 連携の目的

- **記事修正の現実的なフロー**として、従来のツール内保存だけでは「修正後に公開した記事を再編集しづらい」問題があり、**WordPress から読み込んでツールで編集**したい、という目的説明がある。
- **ツール→WP 一方向同期**だと WP 側で加えた装飾（色・画像等）を活かした修正が難しくなる懸念があり、**キャンバスをそのまま保存しやすい形**の方が望ましい、という UX 判断が述べられている。

### 1.4 ブログ作成フローと「目的」中心のコミュニケーション

- **本文を一気に出すと API コストと手間が大きい**ので、**1 見出し＋本文ずつ**出す必要がある、という制約認識がある。
- 「ステップの流れ」という言い方は誤解を招くため避け、**目的（本文が 1 見出しずつ出ること）が達成されればよい**、というコミュニケーション上の指摘がある。
- ブログ作成の各ステップの**文言（ラベル）を具体的に定義**し、優先開発候補（ログイン追加・評価まわり・ブログアプデ・Instagram 等）について **工数見積りに基づき優先順位を変えたい**、という運用がある。

### 1.5 優先機能ロードマップ（発言ベース）

時期により表現は変わるが、チャット上では以下が「やりたいこと」として繰り返し列挙されている。

- 複数事業者（複数ドメイン）登録
- 広告文の複数案提案
- ブログ作成アプデ（カニバリ・キーワードギャップ等の前段、Gemini 利用希望の記述あり）
- Instagram 連携
- 利用制限（料金プランに応じた利用者数制限）
- メール・LINE ログイン、コンテンツ評価の初回評価挙動変更、など（別スレッドで工数前提の優先順位調整の記述あり）

### 1.6 協働・ガバナンス（開発との関係性）

- **勝手な仕様判断で前提が崩れること**への強い警戒がある。**事前許可なく挙動を変えない**こと、**ミスコミュニケーションを防ぐため具体箇所への差し込み確認**を求める姿勢がある。
- 認識齟齬が **余計な工数とストレス**につながる、という感情表出がある（再作業コストへの嫌悪）。
- **チャット（メッセージ）UI とキャンバスの役割分担**をはっきりさせたい。**メッセージ表示に操作を集約**し、**キャンバスは文章フィードバックに集中**。「あっちもこっちも」だと UI が悪化する、という設計思想がある。
- ユーザー視点では **途中で挙動が変わると混乱**するので、**これまで通りのステップ感**を維持する方がわかりやすい、というフィードバックがある。

### 1.7 入力規模とロバストネス

- キーワード数が少ないときは問題ないが、**数十件規模のキーワード投入で挙動が崩れる**（意図しないキーワード混入等）という報告と、**クロード側では期待通り**という対比がある。ツール側のプロンプト／処理の堅牢性が課題として上がっている。

### 1.8 2026-04-22 定例で確定した優先事項（高優先のみ）

- **「本文途中切れ」は通常運用で発生させないことが前提**。見出し単位の本文生成で途中切れが起きた場合、再生成で全文をもう一度吐かせる運用は、**API コスト増と作業重複を生むため非推奨**という判断が明示された。
- 解決方針は、単純な上限引き上げだけでなく、**途中切れをユーザーに明示して続き生成へ誘導する UI**（例: 途中切れエラー表示、続き生成導線、必要に応じて次ステップ抑止）を優先すること。
- **実装上の制約やトレードオフ（例: トークン上限による制御）は事前共有が必須**。開発側のみが知る「水面下仕様」は運用上の混乱・誤案内を招くため、先出しで説明することが強く要求された。
- **開発着手前に UI のたたき台を共有し、合意してから実装する**ことが明確化された。完成後レビューでは手戻りが大きく、過去に機会損失（契約見送り）につながったとの指摘がある。

### 1.9 2026-08-05 定例：プロダクトの存在価値を「作る」から「提案する」へ再定義

出典: 定例MTG 妙記 `objp8z5w8l677x1bga41oy7n`（2026-08-05、41分14秒）。**本節はこの回で最も重要な合意**であり、以降の優先順位判断の前提とする。

#### 1.9.1 中核：GrowMate Pro の差別化は「制作」ではなく「管理・提案」

- **「作る」機能は他 AI で代替可能**という認識がクライアント側で明確になった。制作能力そのものは Claude Code 等の汎用 AI の進化が速く、GrowMate をわざわざ使う理由にならない。
- **「作った成果物を読み込ませ、次に何をすべきかを提案する」ことを最優先**で開発したい、という方針が示された。
- 差別化の根拠は「**AI を使える人はコンテンツを作れるが、その後の管理をしていない**」という観察。AI により月10本規模だった生産量が1000〜2000本規模になり、**管理不能になっていることが本当の課題**という位置づけ。
- **解約理由への直接の回答**として提示されている点が重要。継続契約しなかったユーザーの理由は「AI で作れるからいい」であり、これに対して「作れても管理はどうするのか」を価値提案の主軸に置きたい、という意図。
- 現状の GrowMate は「順位をチェックするぐらい」の使われ方であり、**それだけなら月数万円を払う価値がない**という危機認識が明示された。

#### 1.9.2 コンテンツ評価機能（最優先の具体化）

検索順位のみの評価から脱却し、**売上に接続する評価軸**を持たせる。**順位が上がっても売上につながらなければ意味がない**という判断が前提。

- 算出したい指標（GA4 連携済みデータの活用）: 平均滞在時間、エンゲージメント率、オーガニックサーチで ROI の高い URL、表示回数、CTR、PV、直帰率、CV 数。
- **評価パターン（クライアント提示の 3 分類）**:

| パターン | 条件 | 提案内容 |
|---|---|---|
| 1 | 表示回数は多い × CTR 低い × PV 少ない | ここを重点的に修正すべき |
| 2 | CTR 高い × PV 高い × エンゲージメント率低い（すぐ離脱） | 書き出しの改善が必要な可能性 |
| 3（発言上は「パターン C」） | PV 高い × エンゲージメント率高い × CV 数低い | CTA が弱い／コンバージョンポイントが高すぎる |
| 全指標良好 | — | 順位が下がっていても広告出稿に耐える |

- **評価結果は点数化**し、**70点以下のコンテンツを一覧化**してユーザーが気づいていない問題を可視化する。
- **ブログを広告に出す**という運用意図がある（「LP を作って広告」ではなくブログ経由も CV する）。1000〜2000 本の中から CV している 3〜4 本の「お宝」を発見することが、AI 量産時代に人力では困難になっている。
- 例示された長さ基準: 8000〜9000 文字のブログなら閲覧時間 4〜5 分が良コンテンツ、30秒〜1分で離脱なら冒頭に問題がある可能性。

#### 1.9.3 外部コンテンツ取り込み時の自動処理

- **インポート直後に「AI 要約」と「初回評価」を自動開始**したい。現状は 100〜200 件を手動で「評価を開始」しており負荷が高い。
- 対象は「チャットで作ったもの以外」＝外部から取り込んだコンテンツ。クライアントは自前のコードで月次更新される大量ページ（地域別の粗大ごみ情報、解体補助金、冷蔵庫の買取相場など）を生成し、WordPress のショートコードで出力したうえで GrowMate にインポートする運用をしている。
- **初回評価には約1ヶ月のデータ蓄積期間が必要**という認識がクライアント側にある。
- 関連要望: **未評価コンテンツをソートできるようにする**（「改善提案あり」フィールドはあるが、評価未開始のものをユーザーが把握できていない）。チャットで作成することが暗黙の前提になっており、外部取り込み中心のユーザーが取り残されている。

#### 1.9.4 Instagram 連携の方針変更（クライアント指定）

- **チャット機能は後回し**。**API 連携によるインサイトデータの取得と一覧表示までを実装**して一旦止める、という順序で合意。
- **表示項目（どの情報を出すか）は現時点で決めなくてよい**。後続の評価は別チケットとし、GA4 側の評価との兼ね合いで検討する。
- 理由: **インサイトデータさえ取得できれば、加工次第でいくらでも提案に使える**ため、まずは取得と表示に集中する。
- **単体指標の数値表示には価値を置いていない**。「CV 率や直帰率の数値そのものは GA4 で十分」であり、**他の数値と掛け合わせてどんな意味があるかの解釈**にこそ価値がある、という判断。
- API で取りたいのは **スマホアプリでしか見られない指標**: 平均再生時間、シェア率、保存率、再投稿率、オーディエンス情報、エンゲージメント率。PC の Insights ではリーチしたアカウント／フォロワー内訳程度までしか見られない。
- 提案の配信経路として **メール連携の活用**（既存の日次メールに、GA4 データを根拠にした修正提案を載せる）が挙げられた。
- チャット画面の設計自体は確認済み: **事業者情報を読み込ませる**方針で、複数作成できるサービス内容は**既存チャット画面の選択形式に合わせる**。

#### 1.9.5 この回で合意した優先順位と分担

- **優先**: ①未評価コンテンツのソート ②評価機能の追加。
- **後回し**: 外部コンテンツ取得タイミングでの自動処理（実装難易度が最も高いと開発側が判断。評価が走っていないものをソートできれば手動運用で代替可能）、Instagram チャット。
- **分担**: 評価軸のロジックとプロンプトは**クライアント（繁田）が調査のうえ提案**する。評価軸のパターン1〜3 がそのままプロンプトになる想定。開発側は評価機能・自動処理の実装期間を確認して回答する。
- **予備課題**: ログインし直すとフィールド構成がリセットされる（自動評価が入れば重要度は下がる、との位置づけ）。
