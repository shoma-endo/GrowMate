## 1. 背景・目的・成功指標

### 依頼文の戦略（原文）

2026-10-26 の依頼文（会話）をそのまま転記する。Q-001 でクライアントと合意済みと回答を得ている（2026-10-30）。

> 自社運用（業者さんのプロフィール）で分かること
>
> - 全ての口コミ
> - どんな検索語で表示されたか、電話やルート検索が何件あったか（オーナーしか見られないデータ）
> - それが問い合わせや成約につながったか（Proの受付データと組み合わせられる）
>
> この「成約までつながったデータ」は、競合分析では絶対に手に入りません。ここが他社には真似できない部分になります。
>
> おすすめの使い分け
>
> 1. 競合分析を入口にする。 業者さんへの営業時に「無料マップ診断」として、エリアの競合と比べた弱点を見せる。契約前に価値を感じてもらえます。
> 2. 契約後は自社データで深掘りする。 検索語・電話数・成約データから改善とコンテンツを回す。
> 3. 溜まったデータをメディアに還元する。 複数の業者のデータを横断して、エリア全体で「何が成約につながるか」を把握する。これがメディア集客の強さになります。
>
> 競合分析は「売るための道具」、自社データは「勝つための道具」という位置づけにする

### 背景・解決したい課題

- 現在、誰が、どの業務で困っているか:
  - GrowMate を操作するのは有料登録ユーザー（メディア運営者）で、業者さんは GrowMate を触らない（2026-10-30 確認）。メディア運営者は、生活の困りごと系の業者さん（`client-vision-from-lark.md` §1.11.3）の集客に関わっており、その入口として Googleマップ（Business Profile）の比重が大きい。しかし GrowMate は GSC / GA4 / Google Ads / Instagram / WordPress しか扱っておらず、マップ経由の集客を評価・提案できない。
  - 営業時に「契約前に価値を感じてもらう」材料が無い（依頼文。クライアント側の課題として確認が必要: Q-001）。
- 放置した場合の影響: 「作るではなく管理・提案」（§1.9.1）の対象からマップ集客が抜けたままになる。

## 3. 業務要件と業務フロー

### 現状（As-Is）

```text
[営業] 口頭・手作業で競合の Google マップを見せる（推定。Q-003）
[契約後] メディア運営者が、担当する業者さんの Business Profile 管理画面（Google 側）を個別に確認（推定）。GrowMate では見られない
```

### 導入後（To-Be）

```text
[競合診断（admin / paid）]
  エリア・業種のキーワードと診断する店（店名）を入力
  → Places API Text Search で上位5件と比較項目を取得（毎回取得。保存は place_id のみ）
  → 診断する店が上位に無ければ店名で Text Search をもう1回 → 診断する店を特定
  → 比較表とルール判定の弱点（ALT-003）を画面表示

[自社分析（admin / paid）]
  /setup で Google Business Profile を連携（business.manage）→ ロケーション選択
  → 画面を開いたときに Performance API・reviews API から取得（保存方針は ALT-001）
  → 指標の推移・検索語・口コミ（未返信の強調）・GA4 CV との並記（ALT-002）
  → 改善提案（LLM）

[成約データ（admin / paid）]
  問い合わせを受けたら GrowMate に記録（受付日・経路・結果。記録方法は Q-009〜Q-011）
  → 成約・失注が決まったら結果を更新
  → 自社分析画面で、月別の経路別問い合わせ数・成約数を GBP の指標（電話タップ・Web クリック・ルート）と並べて表示
```

### 業務ルール

- BR-01: 競合診断で Places API から得た内容（名称・住所・評価・口コミ・写真）は DB に保存しない。保存してよいのは `place_id` のみ（F-06）。
- BR-02: 口コミを表示するときは投稿者名・アバター・Google マップへのリンクと、表示順の説明を表示する（F-09）。競合診断では口コミ本文を表示しない（ALT-003）ため、自社分析の口コミ一覧（GBP API 由来）にだけ関わる。GBP API の帰属表示は Business Profile APIs Policies に従う
- BR-03: 自社分析は、GBP のオーナー／管理者権限を持つ Google アカウントで本人が OAuth 連携した場合だけ使える（GBP API ポリシー「End users … need to manually sign in」）。
- BR-04: 口コミへの返信・プロフィール編集を GrowMate から自動実行しない（MVP は読み取りのみ。§4 Non-goals）。
- BR-05: 問い合わせの経路（Googleマップ経由か）は記録者の申告で決まる。GBP の `CALL_CLICKS` 等と1件ずつ突き合わせることはできない（API は日別の件数しか返さない）。画面では「申告ベース」と分かる表示にする。
- BR-06: 問い合わせ・成約の記録は、メディア運営者が GrowMate に保存するデータであり、GBP API の Content ではない。GBP の指標と並べるのは表示時だけで、両者を結合した値を保存しない（ALT-001・F-07）。
- BR-07: 1人のメディア運営者が複数の業者さん（GBP のロケーション）を扱える。自社分析・成約データは業者さん（ロケーション）ごとに分けて表示・記録する。

## 11. トレードオフ判断

### ALT-001: GBP 内容を保存するか

- 比較した案:
  - 案A: 保存しない。画面を開くたびに API から取得（Performance API は期間指定で過去分を取れる）
  - 案B: 30日以内の一時キャッシュのみ（ポリシーの「限定量・30日・集計しない」に収める）
  - 案C: 日次で取り込んで永続保存（既存 GSC/GA4 と同じ）
- 暫定推奨: 案A。ポリシー（F-07）に最も安全で、実装も最小。表示が遅い・クォータが足りないと分かったら案B
- 却下: 案C はポリシー「Content storage」の文言に抵触し得る。既存の他社ツールが永続保存しているかは確認できておらず、根拠にしない
- 判断者・判断日: 未定（Grill Me）

### ALT-002: 「問い合わせにつながったか」をどこまで作るか

- 案A: GBP の Web サイトクリックと GA4 CV の並記まで（FR-008）。新規データ入力なし
- 案B: 問い合わせ・成約を手入力する台帳を新規に作る
- 案C: 外部 CRM / コールトラッキング連携
- 採用案: 案B（GrowMate に問い合わせ・成約の記録を新設し、GBP の指標と並べる）。案A の GA4 CV 並記（FR-008）も残す
- 採用理由: 依頼文が差別化の核とする「成約までつながったデータ」は、案A では一切手に入らない（電話経由の問い合わせを追えない）。案C は対象顧客の使っている CRM・計測番号の要件が無い
- 却下した案と理由: 案A 単独は差別化の核を欠く。案C は Non-goals（自動取得）へ
- 懸念: 記録が手入力に依存するため、事業者が入力し続けなければデータが溜まらない（R-007）。経路は申告ベースで、GBP の指標との因果は示せない（BR-05）
- 判断変更の経緯: 2026-10-30 に一度「今は作らない（案A）」と回答（Q-002）。同日、戦略の核を MVP に入れるため案B へ変更
- 判断者・判断日: ユーザー・2026-10-30

### ALT-003: 競合診断の弱点提示の方式

- 案A: ルールベース（評価が競合中央値より低い、口コミ件数が少ない、写真が少ない、営業時間・Web サイト未設定 等）
- 案B: LLM に比較表を渡して文章化
- 採用案: 案A（ルールベース。Q-006 回答）。項目が少なく判定が明快で、Places 内容を LLM に渡す規約上の懸念も避けられる
- 判断者・判断日: ユーザー・2026-10-30

### ALT-004: OAuth credential を既存と共有するか

- 案A: 既存 GSC/GA4 credential にスコープを追加（GA4 と同じ方式）
- 案B: Google Ads と同じく別 credential
- 採用案: 案B（別 credential）。OAuth クライアントも別プロジェクト `aozora-gbp` に置く（Q-008）
- 採用理由: GBP API の申請を `aozora-gbp` で出したため。GBP 側の停止の影響を GSC/GA4/Ads に及ぼさない。GBP を管理する Google アカウントが GSC/GA4 と同じとは限らない
- 影響: `GoogleTokenService`（`src/server/services/googleTokenService.ts`）は `GOOGLE_OAUTH_CLIENT_ID` / `SECRET` を1組だけ読むため、GBP 用のクライアント情報を渡せるよう拡張し、環境変数を1組足す（refresh token は発行したクライアントでしか更新できない）。同意画面が GrowMate 名義で2種類になる
- 却下した案と理由: 案A（既存 credential にスコープ追加）は、GBP API の承認が GrowMate 既存プロジェクトに無いため成立しない
- 判断者・判断日: ユーザー・2026-10-29
