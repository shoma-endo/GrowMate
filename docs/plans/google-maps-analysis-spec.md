## 0. 事前調査の結論（Grill Me の入力）

依頼文の前提を、公式ドキュメントと既存コードで突き合わせた結果。仕様の各節はこの表を前提にする。

| # | 依頼文の前提 | 事実 | 仕様への影響 |
| --- | --- | --- | --- |
| F-01 | 自社プロフィールで「全ての口コミ」が分かる | 正しい。My Business API v4 `accounts.locations.reviews`（list / batchGetReviews）で全件と返信を取得できる（要 `business.manage`） | 自社分析の対象にできる |
| F-02 | 「どんな検索語で表示されたか」が分かる | 正しいが粗い。Performance API `searchkeywords.impressions.monthly` は**月単位**・**ユニークユーザー数**で、少ない語は値ではなく `threshold`（「◯未満」）で返る。件数の少ない小規模事業者では大半が閾値表示になる可能性がある | 「検索語ランキング」は値と閾値を区別して表示する。精密な数値分析を約束しない |
| F-03 | 「電話やルート検索が何件あったか」が分かる | 一部正しい。`CALL_CLICKS`（電話ボタンのクリック数）・`BUSINESS_DIRECTION_REQUESTS`・`WEBSITE_CLICKS`・Maps/検索 × PC/モバイルの表示回数が**日次**で取れる。**通話が繋がった数・通話時間は取れない** | UI では「電話ボタンのタップ数」と表記し、「電話件数」と書かない |
| F-04 | 「問い合わせや成約につながったか」を Pro の受付データと組み合わせられる | **GrowMate に問い合わせ受付・成約を記録する機能もデータも無い**。あるのは GA4 キーイベント（`ga4_cv_count`、UI 表記「問い合わせ数」。`src/lib/constants.ts:425`）だけで、これは Web フォーム等のサイト内 CV であり、マップ経由の電話や成約は含まない。GBP API の `CALL_CLICKS` も電話ボタンのタップ数で、通話や成約は分からない | 依頼文の差別化の核がまだ存在しない。**2026-10-30 に成約データを対象範囲に入れると決定**（Q-002）。GrowMate に問い合わせ・成約の記録を新設する（ALT-002 案B、FR-010〜FR-012）。GA4 キーイベントとの並記は、業者さんのサイトと連携済み GA4 が対応しないため行わない |
| F-05 | 競合分析は誰でもできる（公開データ） | Places API（New）で取れるが制約が強い。**レビューは1施設あたり最大5件・関連度順**（Place リソース `reviews` の定義）。順位は Text Search の返却順であり、実際のマップアプリの表示順（端末位置・個人化）とは一致しない | 「競合の口コミ分析」は5件しか見られない前提で設計する。「マップ順位」は出さない（§4 Non-goals） |
| F-06 | 競合データを溜めて推移を見る | **Google Maps Platform 規約で保存できない**。`3.2.3(a)(iii)`「business names, addresses, or user reviews をコピー・保存しない」、`3.2.3(b)` キャッシュ禁止。保存してよいのは `place_id`（無期限）と緯度経度（30日）のみ（Service Specific Terms §14.3、Places API Policies） | 競合診断は**毎回 API を叩いて画面に出すだけ**。競合の評価・件数の履歴は持たない |
| F-07 | 複数業者のデータを横断してメディアに還元する | **GBP API ポリシー上、高リスク**。「Content を Business Profile project 外での利用のために保存してはならない。限定量のみ、30日以内、操作・集計（aggregated）しない」（Business Profile APIs Policies「Content storage」、2026-08-28 更新）。横断集計してメディア記事に使うのは文言に正面から抵触し得る。利用規約・プライバシーポリシーでの同意取得も別途必要 | MVP の Non-goal。やるなら法務・規約確認を先に行う別仕様（§4） |
| F-08 | 自社データは契約後すぐ使える | GBP API は**利用申請と承認が必要**。承認前はクォータ 0 QPM（承認後 300 QPM）。申請者は「60日以上アクティブな確認済み GBP」と「GBP に載った Web サイト」が必要（Prerequisites）。加えて OAuth 同意画面に `business.manage` スコープを追加する（既存の GSC/GA4 用 OAuth クライアントの審査範囲が変わる可能性） | 実装より前にリードタイムのある外部依存。§10 D-001・D-002 |
| F-09 | — | GBP 内容を自社の UI で見せる際、Business Profile の UI の見た目を複製してはならない、帰属表示を消さない等のポリシーがある。Places 内容を Google 地図なしで出すときは Google ロゴの帰属表示、口コミは投稿者名・アバター・Google マップへのリンクを表示する | §6 画面設計の必須表示要件 |

## 1. 背景・目的・成功指標

### 依頼文の戦略（原文）

2026-10-26 の依頼文（会話）をそのまま転記する。Q-001 でクライアントと合意済みと回答を得ている（2026-10-30）。

> 自社運用（業者さんのプロフィール）で分かること
>
> - 全ての口コミ
> - どんな検索語で表示されたか、電話やルート検索が何件あったか（オーナーしか見られないデータ）
> - それが問い合わせや成約につながったか（Proの受付データと組み合わせられる）
>
> この「成約までつながったデータ」は、競合分析では絶対に手に入りません。ここが他社には真似できない部分になります。
>
> おすすめの使い分け
>
> 1. 競合分析を入口にする。 業者さんへの営業時に「無料マップ診断」として、エリアの競合と比べた弱点を見せる。契約前に価値を感じてもらえます。
> 2. 契約後は自社データで深掘りする。 検索語・電話数・成約データから改善とコンテンツを回す。
> 3. 溜まったデータをメディアに還元する。 複数の業者のデータを横断して、エリア全体で「何が成約につながるか」を把握する。これがメディア集客の強さになります。
>
> 競合分析は「売るための道具」、自社データは「勝つための道具」という位置づけにする

### 戦略と本仕様の対応

| 戦略 | 本仕様の範囲 | 状態 | 根拠 |
| --- | --- | --- | --- |
| 1. 競合分析を入口にする（売るための道具） | 競合診断（上位5件・ルール判定）。メディア運営者が業者さんへの営業や担当先の確認に使う（FR-001〜FR-003） | 対象 | Q-003・Q-005・Q-006 |
| 2. 自社データで深掘り（口コミ・検索語・電話・ルート） | 業者さんの GBP 分析と、ルール判定の「次の一手」（FR-004〜FR-007、FR-009） | 対象 | 依頼文、Q-014 |
| 2. 成約データと組み合わせる（勝つための道具・差別化の核） | メディア運営者が業者さんから聞いた問い合わせ・成約を記録し、GBP の指標と月別に並べる（FR-010〜FR-012） | 対象 | Q-002・Q-015〜Q-017 |
| 3. 溜まったデータをメディアに還元 | 作らない | Non-goal | §4。GBP API ポリシーの保存・集計制限（F-07） |

### 背景・解決したい課題

- 現在、誰が、どの業務で困っているか:
  - GrowMate を操作するのは有料登録ユーザー（メディア運営者）で、業者さんは GrowMate を触らない（2026-10-30 確認）。メディア運営者は、生活の困りごと系の業者さん（`client-vision-from-lark.md` §1.11.3）の集客に関わっており、業者さんの集客の入口として Googleマップ（Business Profile）の比重が大きい。
  - しかし GrowMate は GSC / GA4 / Google Ads / Instagram / WordPress しか扱っておらず、業者さんのマップ経由の集客を評価・提案できない。メディア運営者は業者さんごとに Google 側の管理画面を個別に見るしかなく、マップ経由の問い合わせがどれだけ成約したかは記録されていない。
  - 業者さんへの営業で「契約前に価値を感じてもらう」材料が無い（依頼文）。
- 放置した場合の影響: 「作るではなく管理・提案」（`client-vision-from-lark.md` §1.9.1）の対象からマップ集客が抜けたままになる。依頼文が差別化の核とする「成約までつながったデータ」が溜まらない。

### 目的

- この開発のゴール（Q-012。クライアント合意 2026-10-30）: メディア運営者が、担当する業者さんごとにマップ経由の問い合わせ数・成約数を毎月把握でき、次の一手を受け取れる。営業では、エリアの競合と比べた弱点を見せる診断を入口にする。
- 本チケットの先（クライアント談 2026-10-30）: 最終的には GBP への自動投稿と、クチコミ返信（承認制）まで実装する。本チケットでは扱わず、別チケットとする（§4 Non-goals）。
- この開発で実現する状態:
  1. メディア運営者（admin / paid）が、営業先・担当先の業者さんについて、エリアの競合上位5件と比べた弱点を画面で示せる（競合診断）。
  2. メディア運営者が、担当する業者さんを切り替えながら、その業者さんの GBP の表示回数・検索語・電話/ルート/Web クリック・クチコミと、次の一手を見られる（業者さんの分析）。
  3. メディア運営者が、業者さんから聞いた問い合わせと成約を業者さんごとに記録し、月別に GBP の指標と並べて「マップ経由の問い合わせがどれだけ成約したか」を見られる（成約データ）。
- 利用者・事業にとっての価値: 業者さんのマップ集客を「管理・提案」の対象に入れ、他社が持てない成約データを溜め始める。

## 3. 業務要件と業務フロー

### 現状（As-Is）

```text
[営業] 口頭・手作業で競合の Googleマップを見せる（推定）
[契約後] メディア運営者が、担当する業者さんの Business Profile 管理画面（Google 側）を個別に確認（推定）。GrowMate では見られない
[成約] 今はメディア運営者が仲介しているので分かる。今後は業者さん直通になり、業者さんから聞かないと分からない（Q-015・Q-016）
```

### 導入後（To-Be）

```text
[GBP 連携（初回のみ）]
  /setup → 「Google ビジネスプロフィール」→ 業者さんの GBP の管理者の Google アカウントで連携（business.manage）
  → そのアカウントで管理できるビジネス一覧から、担当する業者さんを1件以上選ぶ

[競合診断]（/google-maps-dashboard の「競合診断」タブ）
  「エリアと業種」（例: 岡山市 ハウスクリーニング）と「診断するお店の名前」を入力
  → Places API Text Search を2回（エリアと業種で上位候補、店名で診断するお店の候補）
  → 診断するお店を候補から選ぶ
  → 診断するお店を除いた上位5件と比べた比較表と、ルール判定の弱点（最大3つ）を表示（保存しない）

[業者さんの分析]（/google-maps-dashboard の「業者さんの分析」タブ）
  業者さんを選ぶ（2件以上選んでいる場合）
  → 開いたときに GBP API から取得（保存しない。ALT-001）
  → 直近6か月の月別指標 ＋ 同じ月の問い合わせ・成約（FR-012）
  → 先月の検索語（FR-006）、クチコミの状況（FR-007）、次の一手（FR-009）

[成約データ]（「業者さんの分析」タブ内の「問い合わせ・成約」）
  業者さんから報告を受けたら「問い合わせを記録」→ 受付日・どこで知ったか・結果を入力
  → 結果が決まったら編集して「成約」「失注」に更新
```

### 業務ルール

- BR-01: 競合診断で Places API から得た内容（名称・住所・評価・口コミ件数・写真・営業時間・Web サイト・カテゴリ）は DB に保存しない。規約上は `place_id` だけ保存してよいが、本仕様では `place_id` も保存しない（F-06。Maps Platform 利用規約 §3.2.3(a)(b)）。
- BR-02: クチコミを表示するときは投稿者名と投稿日を表示し、並び順（新しい順）を表示する。競合診断ではクチコミ本文を表示しない（F-09）。
- BR-03: GBP の数字・クチコミは、GBP のオーナーまたは管理者の Google アカウントで、メディア運営者本人が OAuth 連携した場合だけ取得する（GBP API ポリシー「End users … need to manually sign in」）。
- BR-04: クチコミへの返信・投稿・プロフィール編集を GrowMate から行わない（本チケットは読み取りのみ。§4 Non-goals）。
- BR-05: 問い合わせの経路（Googleマップ経由か）は、メディア運営者が業者さんから聞いた内容で決まる。GBP の `CALL_CLICKS` 等と1件ずつ突き合わせることはできない（API は日別の件数しか返さない）。画面では経路が報告ベースであることを表示する。
- BR-06: 問い合わせ・成約の記録は、メディア運営者が GrowMate に保存するデータであり、GBP API の Content ではない。GBP の指標と並べるのは表示時だけで、両者を結合した値を保存しない（ALT-001・F-07）。
- BR-07: 1人のメディア運営者が複数の業者さん（GBP のロケーション）を扱える。業者さんの分析・成約データは業者さんごとに分けて表示・記録する。
- BR-08: 業者さんの GBP の数字・クチコミを GrowMate で見るには、メディア運営者の Google アカウントが、その業者さんの GBP のオーナーか管理者であることを前提とする。業者さんが GBP を自分で運用するようになっても、メディア運営者を管理者として残してもらう（Q-018。クライアントと認識合わせ済み 2026-10-31）。
- BR-09: 成約の結果は、メディア運営者が業者さんから聞いて GrowMate に入力する。業者さんは GrowMate を操作しない（Q-017。クライアントと認識合わせ済み 2026-10-31）。
- BR-10: GBP から取得した内容（ビジネス名・住所・指標・検索語・クチコミ）は DB に保存しない。保存するのは、どの業者さんを選んだかを示す GBP のリソース名（`accounts/{id}`・`locations/{id}`）だけとし、ビジネス名は表示のたびに取得する（GBP API ポリシー「Content storage」。ALT-001）。

#### 競合診断の弱点（FR-003）

「競合」は FR-002 の比較対象（最大5件）。中央値は取得できた競合の値で計算する。上から順に判定し、該当したものを最大3つ表示する。

| ID | 弱点 | 条件 | 表示文（例） |
| --- | --- | --- | --- |
| W-01 | 口コミが少ない | 診断するお店の口コミ件数 ＜ 競合の口コミ件数の中央値 × 0.5 | 口コミが競合の半分未満です（このお店 12件 / 競合の中央値 48件） |
| W-02 | 評価が低い | 診断するお店の評価 ≦ 競合の評価の中央値 − 0.2（評価が無い場合は判定しない） | 評価が競合より低めです（このお店 3.9 / 競合の中央値 4.4） |
| W-03 | 写真が少ない | 診断するお店の写真が10枚未満、かつ写真10枚以上の競合が過半数 | 写真が10枚未満です（競合は5件中4件が10枚以上） |
| W-04 | Web サイトが未登録 | 診断するお店に Web サイトが無く、Web サイトのある競合が過半数 | Web サイトが登録されていません |
| W-05 | 営業時間が未登録 | 診断するお店に営業時間が無く、営業時間のある競合が過半数 | 営業時間が登録されていません |

メインのカテゴリは比較表に表示するだけで、判定には使わない（判定基準を置く根拠が無いため）。

```gherkin
Feature: Googleマップ分析

  Background:
    Given 有料ユーザー（paid）としてログインしている

  Rule: 競合診断は保存せず、ルールで弱点を出す

    Scenario: 競合上位5件と比べて弱点を表示する
      Given 「岡山市 ハウスクリーニング」の検索結果に、診断するお店以外の店が5件以上ある

      And 候補から診断するお店を選ぶ

      Then Googleマップ分析で業者さんを切り替えて、それぞれの分析を見られる

    Scenario: 管理しているビジネスが無いアカウントで連携する

      Then 業者さんに管理者として招待してもらうよう案内が表示される

      And 問い合わせ・成約の一覧と記録は使える

  Rule: 業者さんの分析は、開くたびに Google から取得して表示する

    Scenario: 月別の指標と問い合わせ・成約を並べて見る
      Given 業者さんを選んでいる

      Then 値のある語が多い順に並び、閾値だけの語は「◯未満」と表示されて後ろに並ぶ

      Then 指標の欄に取得できなかった旨が表示される
      And 問い合わせ・成約の一覧と記録は使える
```

## 11. トレードオフ判断

### ALT-001: GBP 内容を保存するか

- 比較した案:
  - 案A: 保存しない。画面を開くたびに API から取得（Performance API は期間指定で過去分を取れる）
  - 案B: 30日以内の一時キャッシュのみ（ポリシーの「限定量・30日・集計しない」に収める）
  - 案C: 日次で取り込んで永続保存（既存 GSC/GA4 と同じ）
- 採用案: 案A
- 採用理由: ポリシー（F-07）に最も安全で、実装も最小。300 QPM で表示時の取得に足りる
- 却下した案と理由: 案B は表示速度の問題が出てからでよい（Non-goals）。案C はポリシー「Content storage」の文言に抵触し得る

### ALT-002: 「問い合わせにつながったか」をどこまで作るか

- 案A: GBP の Web サイトクリックと GA4 CV の並記まで（FR-008）。新規データ入力なし
- 案B: 問い合わせ・成約を手入力する台帳を新規に作る
- 案C: 外部 CRM / コールトラッキング連携
- 採用案: 案B（GrowMate に問い合わせ・成約の記録を新設し、GBP の指標と並べる）。案A の GA4 CV 並記（FR-008）は、業者さんのサイトと GrowMate に連携した GA4 が対応しないため外す（2026-10-31 ユーザー判断。§4 Non-goals）
- 採用理由: 依頼文が差別化の核とする「成約までつながったデータ」は、案A では一切手に入らない（電話経由の問い合わせを追えない）。案C は対象顧客の使っている CRM・計測番号の要件が無い
- 却下した案と理由: 案A 単独は差別化の核を欠く。案C は Non-goals（自動取得）へ
- 懸念: 記録が手入力に依存するため、事業者が入力し続けなければデータが溜まらない（R-007）。経路は申告ベースで、GBP の指標との因果は示せない（BR-05）
- 判断変更の経緯: 2026-10-30 に一度「今は作らない（案A）」と回答（Q-002）。同日、戦略の核を MVP に入れるため案B へ変更

## 13. テスト・リリース・ロールバック

### テスト方針

- 単体:
  - 判定ルール（W-01〜W-05、N-01〜N-04）の純関数。境界値（中央値 × 0.5 ちょうど、評価差 0.2 ちょうど、競合 0・1・5件、評価なし、表示回数 99/100、低下率 20% ちょうど）と期待結果をテストケースにする
  - 月別集計（日別値の月合計、受付日による月の振り分け、成約率の0除算で「—」）
  - 検索語の並び順（value の多い順 → threshold の語）
  - Zod スキーマ（入力の文字数、未来の受付日の拒否、選択肢以外の値の拒否）
- 統合: Places / GBP API はモックで、正常・0件・エラー・トークン期限切れ（`needsReauth`）・権限なし（403）を確認。Places 内容・GBP 内容が DB に書かれないこと（BR-01・BR-10）
- セキュリティ・権限・RLS: admin / paid / trial / unavailable の4ロールでサーバー側を検証。RLS で他人の記録・credential が見えないこと
- 実画面確認: テストユーザー（あおぞら養鶏の GBP の管理者アカウント）で、連携 → 業者さん選択 → 分析表示 → 問い合わせ記録 → 月別並記、競合診断を確認
- Gherkin との対応: §7 シナリオ対応表のとおり

### リリース方針

- リリース単位: P1（競合診断）→ P2（GBP 連携）→ P3（業者さんの分析）→ P4（成約データ）。各 PR は単独で壊れない（P1 の時点ではタブ「業者さんの分析」は未連携の表示）
- Feature Flag / allowlist: 作らない。OAuth 同意画面がテスト中の間は、テストユーザー以外は Google 側で連携できない（D-002）
- データベース変更の適用順序: P2 で credential・locations、P4 で inquiries の migration
- 本番確認項目: 上の実画面確認を本番で1回

### ロールバック方針

- アプリケーション: デプロイ巻き戻し
- DB: 新規テーブルのみのため、巻き戻すときは down migration で3テーブルを DROP する（問い合わせ記録が消えるため、記録が入った後の DROP はユーザー確認のうえ行う）
- データ不整合時の復旧: 外部データは保存しないため不要
- ロールバック判断者: ユーザー（開発）
