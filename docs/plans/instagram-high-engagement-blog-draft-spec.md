### 目的

- この開発で実現する状態: Instagram タブで投稿を選んで（複数可）［ブログ記事を作成］を押すと、キャプションからキーワードを立て、既存のブログ作成フロー（step1〜7）と同じプロンプトで**本文の完成形まで自動で作成**し、コンテンツ一覧に1行として入る。ユーザーは完成した記事をチャット（Canvas）で確認・修正する。
- この開発で実現する状態（Phase 3）: 記事の作成と同時に、その記事へ内部リンクを張るとよい過去記事と、その中の該当箇所・リンクを入れた書き直し案を提案する。ユーザーは記事の詳細画面で提案を見て、WordPress 側で過去記事を直す。
- 利用者・事業にとっての価値: 投稿を選ぶ以外の操作が要らなくなる。記事の品質は既存フローのプロンプト（管理画面で調整済みのもの）をそのまま使うため、手動で作った記事と同じ水準になる。

## 2. 利用者・関係者・利用シナリオ

| 区分 | 対象 | 期待すること・責任 |
| --- | --- | --- |
| 利用者 | Instagram 連携済みの `admin` / `paid` ユーザー | ブログ化する投稿を選び、完成した記事を確認・修正する |
| 運用担当 | 遠藤 | 不具合時の切り戻し、ログでの失敗調査 |
| 管理者・承認者 | カオルさん | 生成の流れ・画面の承認 |
| 外部サービス・連携先 | Anthropic API | 各ステップの生成（既存のブログ作成フローと同じモデル設定） |

### 主な利用シナリオ

1. **カオルさんが**、Instagram タブを「高エンゲージメント率」で絞り込み、記事にしたい投稿を何件かチェックし、［ブログ記事を作成］を押す。しばらくすると結果のメールが届き、コンテンツ一覧にそれらの記事が入っている。
2. **カオルさんが**、完成した記事をチャットで開き、Canvas で本文を確認・修正する。
3. **カオルさんが**、完成した記事の詳細画面の「内部リンク」タブで、魚粉に触れている過去記事と、リンクを入れた書き直し案を見る。記事を WordPress に公開して URL を登録した後、書き直し案をコピーして過去記事を直す。
4. **カオルさんが**、途中で止まった投稿（「失敗」「途中で切れました」の表示）の［続きを作成］を押し、止まったところから作成を再開させる。

## 3. 業務要件と業務フロー

### 現状（As-Is）

```text
Instagram タブで高エンゲージメント率の投稿を見つける（Phase 1）
  → コンテンツ一覧で新しいチャットを作る
  → キャプションを読んでキーワードを自分で考え、step1 に入力して送信
  → step1〜6: 出力を読み、次のステップの入力欄に入れて送信。合間に「メモ・補足情報」へ転記して保存
  → step7: 書き出し案を送信 → 見出しごとに［生成］→［保存］を見出しの数だけ繰り返す
  → 完成形を作る
```

### 導入後（To-Be）

```text
Instagram タブで記事にしたい投稿のチェックボックスを選び（複数可・最大10件）、ツールバーの［ブログ記事を作成］を押す
  → （自動）選んだ投稿ごとに、以下を並行して進める（同時に3件まで）
  → （自動）キャプションからキーワード案を作る
  → （自動）コンテンツ一覧に行とチャットを作る
  → （自動）step1〜6 を順に生成し、各出力を「メモ・補足情報」の対応する項目に保存
  → （自動）step5 の構成案から見出しを作り、step6 の書き出し案を書き出しにする
  → （自動）見出しごとに本文を生成・保存（1見出しずつ）
  → （自動）書き出し＋各見出しを結合して完成形を保存
  → （自動）過去記事から、新しい記事のテーマに触れている記事を探し、内部リンクを入れる箇所と書き直し案を作る（Phase 3）
  → （自動）1回の処理時間の上限に近づいたら、残りを次の処理に自動で引き継ぐ（ユーザー操作は要らない）
  → 選んだ投稿がすべて終わると、結果をまとめたメールが1通届く。Instagram タブの完了した行に［チャット］が出る。チャットを開いて Canvas で確認・修正する
  → 記事を WordPress に公開し、コンテンツ一覧で URL を登録する（既存の操作）
  → 記事の詳細画面「内部リンク」タブで書き直し案をコピーし、WordPress で過去記事を直す
```

### 業務ルール

- ルール ID: BR-001（作成のきっかけ）
  - ルール: 自動作成は、ユーザーが Instagram タブで投稿のチェックボックスを選び、ツールバーの［ブログ記事を作成］を押したときだけ始まる。操作はブログ一覧の一括操作（チェック → ツールバーの［評価サイクルを開始］［AIで要約］）と同じ形にする（2026-09-27 遠藤決定「複数記事作れるようにブログ記事同様に、チェックボックス形式にしてボタンクリックする」「UIも合わせて」）。［最新化］や目標達成の判定をきっかけに自動で始めない。
  - 1回に選べるのは**最大10件**（BR-015）。
  - 例外: キャプションが空（`caption` が null または空白のみ）の投稿と、既に作成がある投稿（BR-003）は、選んでいてもサーバーが対象から外す。外した件数はトーストで伝える（ブログ一覧の一括要約がサーバー側で対象外を飛ばすのと同じ。`docs/specs/analytics-bulk-actions-impl-note.md` §3.2）。
- ルール ID: BR-002（対象の投稿）
  - ルール: どれを記事にするかはユーザーが選ぶ（2026-09-26 遠藤判断「最初のコンテンツ選択はユーザーがやって」。ALT-002）。
  - 選べる投稿は Phase 1 の目標達成（高エンゲージメント率）に限らず、キャプションのある全投稿（2026-09-27 遠藤決定「インスタ投稿の中からどの投稿をブログ記事にするのかは、ユーザーが選択して決める」）。高エンゲージメント率の絞り込み（Phase 1）は選ぶときの手がかりとして使う。Trello のラベル・Phase 1 §17 は目標達成の投稿を想定した書き方のため、この決定は §14 の実装前ゲート（UIたたき台・要件合意）でクライアントに確認する。
- ルール ID: BR-003（1投稿1記事）
  - ルール: 1つの投稿から作る記事は1本だけ。作成中・待機中・止まった・作成済みの投稿は、選んで［ブログ記事を作成］を押しても対象外になる（BR-001 例外）。これらの行の操作列には状態に応じた表示と操作を出す（§6 状態別UI）。
  - 例外: 作成済みの記事をユーザーがコンテンツ一覧から削除した場合も、その投稿から作り直す機能は持たない（§4 Non-goals）。
- ルール ID: BR-004（生成に使うプロンプト）
  - ルール: step1〜7 の生成には、既存のブログ作成フローと**同じプロンプトテンプレート（`prompt_templates` の `blog_creation_step1`〜`blog_creation_step7`）と同じモデル設定（`MODEL_CONFIGS`）**を使う。自動作成専用の step 用プロンプトを作らない。新規に作るプロンプトは、キーワード案の生成（FR-002）と内部リンク提案（FR-012）の2本だけ。
- ルール ID: BR-005（ステップ間の受け渡し）
  - ルール: 各ステップの入力（user メッセージ）は、手動フローでユーザーが送るものと同じ形にする。
    - step1: キーワード案（主キーワード→関連キーワードの順に改行区切り）の下に、元の投稿のキャプションを見出し付きで添える（形は FR-004）
    - step2〜5: 直前のステップの出力をそのまま入力にする
    - step6: 直前（step5）の出力の下に、元の投稿のキャプションを「【一次情報（元の Instagram 投稿）】」の見出し付きで添える。step6 のテンプレートは一次情報が無いと「[ここにあなたの体験談や実績などの一次情報を入れてください]」という穴埋めを本文に残す指示になっており、Instagram の投稿はそのまま一次情報にあたるため（Q-001 の確認結果）
    - step7 の書き出し: step6 の出力のうち「パターンA（課題解決型・王道）」の「通常版」の本文だけを取り出して使う（FR-005）。step6 は1回で「パターンA・B × 通常版・短縮版」の4案と解説を返し、どれを採るかはユーザーが選ぶ作りのため、自動作成では既定を決める（2026-09-27 遠藤決定。テンプレートが「最も使いやすい王道の型」とする A の通常版）。4案すべてを含む出力全体は「書き出し案」（`opening_proposal`）に残し、ユーザーはチャットで差し替えられる
  - 各ステップの出力を、手動フローでユーザーが転記している「メモ・補足情報」の項目に保存する。対応は次の表のとおり（ステップ名は `src/lib/constants.ts` の `BLOG_STEP_DEFINITIONS`、項目の画面表示名は `src/lib/constants.ts:394-412` のラベル）。

    | ステップ | ステップ名 | 保存先の項目（画面表示名） |
    | --- | --- | --- |
    | キーワード案 | — | `main_kw`（主軸kw。1件）、`kw`（kw（参考）。改行区切り） |
    | step1 | 顕在ニーズ・潜在ニーズ確認 | `needs` |
    | step2 | ペルソナ・デモグラチェック | `persona`（デモグラ・ペルソナ） |
    | step3 | ユーザーのゴール | `goal` |
    | step4 | PREPチェック | `prep` |
    | step5 | 構成案確認 | `basic_structure` |
    | step6 | 書き出し案 | `opening_proposal`（書き出し案） |

  - 理由: step2 以降のプロンプトは `{{contentNeeds}}` などの「メモ・補足情報」の値を変数として読む（`PromptService.buildContentVariables`）。手動フローではユーザーの転記で埋まる値を、自動作成では各ステップの出力で埋めないと、後のステップのプロンプトが空の変数で動く。
- ルール ID: BR-006（本文は1見出しずつ）
  - ルール: step7 の本文は、既存フローと同じく**見出し1つにつき AI 呼び出し1回**で生成し、見出しごとに保存する。記事全体を1回で生成しない。最後の完成形は、保存済みの書き出しと各見出しを結合して作る（AI 呼び出しなし。既存の `saveCombinedContentForStep7` と同じ結合）。
  - 理由: クライアント指示「本文を一気に出力されると API 消費が激しいのと、手間がかかるので、本文出力を 1 つずつする必要があります」「目的が達成、つまり本文が 1 見出し＋文章ずつ出れば大丈夫です」（2026-02-28。`docs/context/client-vision-from-lark.md` §2）。自動化しても、出力の単位はこの指示に従う。
- ルール ID: BR-007（途中で止まったとき）
  - ルール: どのステップで止まっても、それまでに保存したチャット・「メモ・補足情報」・見出しの本文は残す。［続きを作成］を押すと、止まったステップから再開する（最初からやり直さない）。
  - 止まる原因: (1) AI の呼び出しに失敗した（`AI_FAILED` / `AI_RATE_LIMITED`）、(2) 出力が上限で途切れた（`stop_reason = 'max_tokens'`。`MAX_TOKENS`）、(3) 実行中にサーバーが落ちた・自動の引き継ぎが途切れた（`updated_at` が 20 分より古い `running` / `queued`）、(4) 処理側の失敗（保存失敗 `SAVE_FAILED`・見出し0件 `NO_HEADINGS`・キーワード形式不正 `KEYWORD_PARSE_FAILED`・書き出しの取り出し失敗 `LEAD_PARSE_FAILED`・引き継ぎ回数の上限 `CHAIN_LIMIT`・権限が外れた `ROLE_REVOKED`）。
  - 1回の処理時間の上限（FR-006）は「止まる原因」に入れない。上限に近づいたら、処理中の投稿を待機中に戻し、次の処理を自動で始めて続きから進める（FR-006。ユーザー操作は要らない）。
  - (2) の扱い: 同じステップを最初から生成し直さない。既存の手動フローの「続きを生成」と同じく、途切れた出力の**続きだけ**を生成して前の出力に結合する（ストリーミング Route Handler の `isContinuation` と同じ指示文「返答がmax_tokensにより途中で途切れました。途切れた箇所の続きのみを出力してください。冒頭から繰り返さないこと。」、保存は `chatService.updateLastAssistantMessage`）。自動作成の中で1ステップにつき2回まで自動で続きを生成し、それでも途切れたら止めて「途中で切れました」と表示する。［続きを作成］はこの続き生成から再開する。
  - 理由: 2026-04-22 定例「もう一回出してくださいは API をただ消化してるだけ」「途中で切れてますよと知らせた上で、続きを生成しますか、で進める方が親切」。手動フローの「続きを生成」ボタンは画面の状態（`isTruncated`）にしか持たず DB に残らないため、後からチャットを開いても出ない。チャット側での手動対応には頼れない。
  - 止まった理由は画面で区別する（(1)(3)(4) は「失敗」、(2) は「途中で切れました」。§6 状態別UI）。2026-04-22「水面下で起こってることが一番の問題」。
- ルール ID: BR-008（メールでの通知）
  - ルール: ［ブログ記事を作成］1回で選んだ投稿（＝1つのまとまり。§9 `instagram_blog_draft_batches`）が**すべて終わった時点で**、結果をまとめたメールを1通、ユーザーの登録メールアドレス（`users.email`）へ送る。
    - 投稿ごとに、完了ならチャットを開くリンク（内部リンクの提案があれば件数と詳細画面へのリンク）、失敗・途中で切れたなら止まった理由と、Instagram タブの［続きを作成］で続きから作れることを載せる。
    - 「終わった」＝まとまりの全投稿が「作成済み」「失敗」「途中で切れました」のどれかになったとき。時間の上限による引き継ぎ（FR-006）の途中では送らない。
  - 理由: 完成まで数分〜数十分かかり、ユーザーは画面を離れる前提（「作って提案しました」）。複数件を選んだときに1件ごとに送ると最大10通になるため、まとめて1通にする（2026-09-27 遠藤決定「完了したらメールで通知する」、停止時も送る案を選択。まとめ方は一括化に伴う設計判断）。
  - 例外1: `users.email` が未登録の利用者には送らない（一括 AI 要約の完了メールと同じ。`contentAnnotationSummaryJobService.fetchUserEmail`）。
  - 例外2: サーバー停止（BR-007 (3)）で処理が途中で落ち、自動の引き継ぎも途切れたときは送れない。定期処理による後追い送信は持たない（§4 Non-goals の cron と同じ理由）。この場合は 20 分後に Instagram タブで「失敗」と表示されるだけになる（R-008）。
  - 例外4: まとまりの投稿の行が1件も残っていない（Instagram の連携解除で `instagram_media` ごと消えた。§9 保持期間）ときは送らず、`notified_at` だけ埋める（FR-010）。
  - 例外3: メールの送信に失敗しても、作成の状態（`status`）は変えない。`console.error` に記録するだけで再送しない。
  - ［続きを作成］で再開した投稿は、新しいまとまり（1件）として扱い、終わったときにもう1通送る。
- ルール ID: BR-015（一度に作れる件数と同時に進める件数）
  - ルール: 1回に選べるのは最大10件。11件以上選んだときは［ブログ記事を作成］を押せず、「一度に作成できるのは10件までです」と出す。作成中・待機中のまとまりがあるあいだは、次の［ブログ記事を作成］を押せない（「作成中の記事があります。終わってから次を選んでください」）。1つのまとまりの中では、同時に3件まで並行して進める。
  - 理由: 1件あたり AI 呼び出し約25回（§8）。10件で約250回になり、それ以上は費用と所要時間が読めなくなる。同時に進める数を絞るのは Anthropic のレート制限（429）を避けるため。作成中の追加起動を止めるのは、既存の一括 AI 要約が実行中のジョブがあるあいだ次の起票を受け付けない（`docs/specs/content-annotation-bulk-summary-background-spec.md` BR-B03）のと同じ理由（同時に走る処理と費用が読めなくなる）。
- ルール ID: BR-009（内部リンクの提案元＝過去記事）
  - ルール: 提案の対象にする過去記事は、そのユーザーの `content_annotations` のうち **WordPress から取り込んだ本文（`wp_content_text`）を持つ記事**。今回作った記事自身は除く。
  - 理由: 内部リンクは公開済みの記事の中に張るもの。GrowMate で作って未公開の記事（本文が `session_combined_contents` にだけある記事）は、WordPress 上に存在せずリンクを張れない。
  - 例外: 本文を取り込んでいない記事（WordPress 未連携・取り込み前）は対象にならない。1件も無いときは提案を作らず、詳細画面で「WordPress の記事を取り込むと提案できます」と案内する。
- ルール ID: BR-010（候補の探し方）
  - ルール: キーワード案（FR-002）と同じ AI 呼び出しで、過去記事の本文に出てきそうな語（`link_terms`。1〜5語。例: 「魚粉」「フィッシュミール」）も作る。過去記事の本文にこれらの語が含まれる記事を探し、含まれる語の種類が多い順に**最大10本**を候補にする。
  - 理由: 全過去記事を AI に読ませると記事数に比例して費用と時間がかかる。語の一致で先に絞り、AI には候補だけを読ませる。
- ルール ID: BR-011（提案の中身と根拠の確認）
  - ルール: 候補の過去記事1本につき AI を1回呼び、新しい記事のテーマに触れている箇所を最大3件選ばせる。1件ごとに「今の文（過去記事の原文そのまま）」「リンクにする語（アンカーテキスト）」「リンクを入れた書き直し案」を持つ。
  - **「今の文」が過去記事の本文に一字一句含まれない提案は捨てる**（AI が原文に無い文を作った場合に、存在しない箇所を直させないため）。2025-10-14「今の所エビデンスチェックが最重要」（`client-vision-from-lark.md` §2）。
  - 書き直しは該当箇所の文だけ。過去記事全体の書き直しはしない（§4 Non-goals）。
- ルール ID: BR-012（リンク先の URL）
  - ルール: リンク先は新しい記事の URL（`content_annotations.canonical_url`）。記事の作成時点では未公開で URL が無いため、提案には保存せず、**表示するときに**その時点の `canonical_url` を当てはめる。未登録のうちは「（この記事の公開後の URL）」と表示し、コピーを押せなくする（§6）。
  - URL の登録は既存の操作（コンテンツ一覧の［編集］で URL を入れる）で行う。新しい登録手段は作らない。
- ルール ID: BR-013（過去記事の修正はユーザーが WordPress で行う）
  - ルール: GrowMate は WordPress へ書き込まない（公開・更新の機能を持たない。`wordpressService.ts` に POST なし）。ユーザーは書き直し案をコピーし、WordPress の編集画面で過去記事を直す。
- ルール ID: BR-014（提案の失敗は記事の完成を妨げない）
  - ルール: 内部リンク提案は記事の完成形を保存した後に作る。候補1本ぶんの AI 呼び出しに失敗・途中で切れた・形式不正のときは、その候補を飛ばして `console.error` に記録し、次の候補へ進む。記事の作成は `completed` にする。
  - 例外: 1回の処理時間の上限に近づいたときは、記事の作成と同じく次の処理に自動で引き継ぎ、残りの候補から続ける（FR-006）。

## 4. 対象範囲と Non-goals

### 対象範囲

- 画面・操作:
  - `/analytics?tab=instagram` の一覧に、ブログ一覧と同じチェック列・ツールバーの［ブログ記事を作成］・操作列（待機中／作成中の進み具合／［続きを作成］／［チャット］）を追加する

- API・外部連携:
  - Route Handler を3本新設する: 開始（選んだ投稿のまとまりを作る）、再開（［続きを作成］）、引き継ぎの受け口（内部専用。`CRON_SECRET` 認証）。いずれも `after()` で応答後に処理を続ける（ALT-001）
  - プロンプトテンプレートを2本追加する（キーワード案 `instagram_blog_keyword_generation`、内部リンク提案 `internal_link_suggestion`。`prompt_templates`。管理画面 `/admin/prompts` から編集できる）
  - step1〜7 の生成は既存のプロンプト組み立て（`getSystemPrompt`）を使う。Cookie に依存しない呼び出し口を足す（§10）
- データ・DB:
  - 自動作成の進み具合を持つテーブル `instagram_blog_draft_jobs`、選んだ投稿のまとまりを持つテーブル `instagram_blog_draft_batches`、内部リンク提案を持つテーブル `internal_link_suggestions`、候補を探す RPC `find_internal_link_candidates` を新設する
  - 既存テーブルへの書き込みは、手動フローと同じテーブル・同じ形（`chat_sessions` / `chat_messages` / `content_annotations` / `session_heading_sections` / `session_combined_contents`）
- 権限・ロール: `admin` / `paid`（既存の `canAccessInstagram`）。Route Handler 側でも検証する
- 内部リンク提案（Phase 3）: 記事の作成の最後に過去記事から候補を探し、該当箇所と書き直し案を作る。記事の詳細画面（`/analytics/[annotationId]`）に「内部リンク」タブを足して表示する
- 通知: 選んだ投稿がすべて終わったら、結果をまとめたメールを1通送る（BR-008。既存の `EmailService`〈Resend〉）
- 運用・監視: 既存の `console.error` ログのみ

### FR ごとの実装上の決定

**FR-001 / FR-003（開始）**:

- Route Handler `POST /api/instagram/blog-drafts`（新設）で受ける。入力は `{ instagramMediaIds: string[] }`（`instagram_media.id`。Instagram の `ig_media_id` ではない。1〜10件）。
- 開始時に同期で行うこと（応答を返す前）:
  1. 認証・認可（`authMiddleware` → `canAccessInstagram(role)`）。不可なら 403
  2. 件数の検証。0件・11件以上なら 400（BR-015）
  3. 作成中・待機中のまとまり（`status in ('queued','running')` かつ `updated_at` が 20 分以内の行を持つまとまり。FR-007 の止まった行は除く。FR-008 の画面の判定と同じ）があれば 409（BR-015）
  4. `instagram_media` を `user_id` 一致・`id in (...)` で取得する。本人のものでない ID・存在しない ID・キャプションが空の投稿・既に `instagram_blog_draft_jobs` の行がある投稿は対象外として数える（BR-001 例外 / BR-003）
  5. 対象が0件なら 400（トーストで対象外の件数と理由を伝える）
  6. `instagram_blog_draft_batches` に1行、対象の投稿ごとに `instagram_blog_draft_jobs` に1行（`status = 'queued'`、`stage = 'keywords'`、`batch_id`）を作る。同じ投稿の行が同時に作られた場合は一意制約違反になり、その投稿は対象外に数える
  7. 200 を返す（本文は対象の件数・対象外の件数と理由の内訳）。以降は `after()` の中で FR-006 のワーカーを動かす。`after()` には開始時に確定した `userId` と `userRole`（ナレッジ注入の判定に使う。`knowledgeInjection.ts:114-123`）と `batchId` を値で渡し、`after()` の中では Cookie を読まない
- トースト: 「N件のブログ記事の作成を始めました」。対象外があれば理由ごとの件数を「（対象外: 作成あり M件・キャプションなし K件・その他 L件）」の形で添える（0件の理由は省く）。「作成あり」は作成中・待機中・止まった・完了のいずれか、「その他」は他人の投稿・存在しない ID。文言は既存の文言の置き場（`error-messages.ts` の規約）に置く。
- チャットとコンテンツ一覧の行は、キーワード案ができた直後（FR-002 の後）に作る。タイトルと `main_kw` / `kw` を最初から入れるため。作り方は既存の `ensureAnnotationChatSession`（`src/server/actions/wordpress.actions.ts:734`）と同じく `chat_sessions` → `content_annotations` の順に作り、`content_annotations.session_id` で紐付ける。`ensureAnnotationChatSession` 自体は Server Action（`withAuth`）で `after()` の中からは呼べないため、`SupabaseService` の既存メソッド（`createChatSession`）と `content_annotations` への upsert（`session_id` で衝突判定）を、`userId` を明示してサービス層から呼ぶ。
  - `createChatSession` には `DbChatSession`（Row 型そのもの。`src/types/chat.ts:44`）の全列を渡す。`id` は TEXT で既定値が無いため `crypto.randomUUID()` で振る。
  - `content_annotations` は `canonical_url` / `wp_post_id` を null で書く（`UNIQUE(user_id, wp_post_id)`・canonical の部分一意のいずれにも当たらない）。
  - **再開で二重に作らない順序**: (1) ジョブに `session_id` が無ければ `chat_sessions` を作り、**直ちに**ジョブへ `session_id` と `link_terms` を書く。(2) `content_annotations` は `session_id` の一意制約（`content_annotations_session_id_unique`。`supabase/migrations/20260107100000_fix_content_annotations_session_constraint.sql:12`）で upsert する。(3) `stage` を `step1` に進める。`keywords` から再開するとき、ジョブに `session_id` があればチャットは作らずそれを使う。そのチャットの `content_annotations` の行があれば、キーワード案の AI は呼ばずに `stage` を進める。行が無ければキーワード案を作り直して (2) から続ける（チャットのタイトルは最初の主キーワードのまま）。
- 作成したチャットの `service_id` は null（既存のブログ作成は「特定のサービスに依存しない」。`src/lib/prompts.ts` `generateBlogCreationPromptByStep` のコメント）。

**FR-002（キーワード案）**:

- 新規テンプレート `instagram_blog_keyword_generation`（`prompt_templates`。§9）。入力変数はキャプション `{{instagramCaption}}` と事業者情報。事業者情報の置換は既存の `replaceTemplateVariables`（`src/lib/prompts.ts:225`。非公開で、事業者情報を Cookie 依存の `getCachedBrief` から取る）を、§10 の Cookie に依存しない事業者情報の取得と組み合わせて使う。
- テンプレートには「キャプションに書かれていない事実（価格・保証内容・数値など）を足さない」と明記する。
- 出力は JSON（`{"main_kw": string, "kw": string[], "link_terms": string[]}`）とし、既存の JSON 抽出（`contentAnnotationSummaryService` の `JSON_BLOCK_REGEX`）と同じ方法で取り出して Zod で検証する。`main_kw` が空、`kw` が0件、形が合わないときは失敗（`error_code = 'KEYWORD_PARSE_FAILED'`）。`link_terms`（BR-010。1〜5語、各 20 文字以内）は0件でも失敗にしない（内部リンク提案を作らないだけ）。`link_terms` はジョブ行に保存する（§9）。
- モデル設定は `MODEL_CONFIGS` に `instagram_blog_keyword_generation` を追加する（`ANTHROPIC_BASE`、`maxTokens: 1000`）。

**FR-004（step1〜6）**:

- 各ステップは、手動フローのストリーミング Route Handler（`app/api/chat/anthropic/stream/route.ts`）と同じ材料で、`llmChat`（§10 で `stop_reason` を返すよう拡張）を1回ずつ呼ぶ。
  - system: `getSystemPrompt(toBlogModel(stepN), undefined, sessionId, undefined, { userId })`（§10 の `userId` 明示の口）の結果に、既存と同じく `resolveKnowledgeBlocksForRequest`（`userRole` を渡す）でナレッジを足したもの
  - 履歴の末尾が user メッセージのときは今回の入力と結合する（ストリーミング Route Handler の `route.ts:140-151` と同じ正規化。step7 の最初の見出しの直前は書き出しの user メッセージになるため、この処理がそのまま効く）
  - messages: そのチャットの直近 `CHAT_HISTORY_LIMIT`（10）件の user / assistant メッセージ＋今回の入力（手動フローの `createRequestMessages` と同じ件数）

- step1 の入力（BR-005）:

  ```text
  <主キーワード>
  <関連キーワード1>
  <関連キーワード2>
  ...

  【元になった Instagram 投稿】
  <キャプション>
  ```

  - step1 のテンプレートは「Web検索機能を用いて競合リサーチ」と指示するが、手動フローの step 送信は Web 検索を有効にしていない（有効にするのは Canvas の編集だけ。`ChatLayout.tsx:1470` / `app/api/chat/canvas/stream/route.ts:298`）。自動作成も Web 検索を有効にしない（手動フローと同じ出力にするため）。

**FR-005（step7）**:

**FR-006（実行方式・並行・時間の上限と自動の引き継ぎ）**:

- `after()`（`next/server`）で、Route Handler の応答後にワーカー `runBlogDraftBatch(batchId, userId, userRole)` を動かす。Route Handler の `maxDuration` は 800 秒（既存のストリーミング Route Handler と同じ。Vercel Pro の上限）。
- ワーカーは起動した直後に、まとまりの `queued` の行すべての `updated_at` を今の時刻にする（開始の Route Handler から動くときも、引き継ぎの受け口から動くときも同じ。待っているだけの行を止まった行と誤って判定しないため。FR-007）。
- ワーカーは、まとまりの中の `status = 'queued'` の行を**古い順に取り出して `running` にする**（条件付き UPDATE `where id = ? and status = 'queued'` で1行ずつ取り、取れた行だけ進める）。同時に進めるのは3件まで（BR-015）。1件が終わる（`completed` / `failed`）たびに、残り時間があれば次の `queued` を取り出す。
- 1回の実行で使える時間は 740 秒（800 秒 − 返却の余裕 60 秒）。各投稿は**次のステップ（または見出し・続きの生成・内部リンクの候補1本）に着手する前に**残り時間を見る。「AI 呼び出しのタイムアウト 180 秒＋保存の余裕 20 秒 = 200 秒」を下回っていたら着手せず、その投稿を `status = 'queued'` に戻す（`stage` などはそのまま。続きから進む）。
- **自動の引き継ぎ**: ワーカーの最後に、まとまりに `queued` の行が残っていれば、次の処理を自分で起動する。`fetch(`${NEXT_PUBLIC_SITE_URL}/api/instagram/blog-drafts/continue`, { method: 'POST', headers: { Authorization: `Bearer ${CRON_SECRET}` }, body: { batchId } })` を送り、応答（200）を確かめてから終える。受け側（下記）は同じワーカーを `after()` で動かす。
  - 受け側 `POST /api/instagram/blog-drafts/continue`（新設）: 既存の `/api/cron/*` と同じ `CRON_SECRET` の Bearer 認証。`batchId` からまとまりの `user_id` を読み、`users.role` を読み直して `canAccessInstagram` を満たさなければ、残りを `failed`（`error_code = 'ROLE_REVOKED'`）にして終える。満たせば `userRole` を付けてワーカーを動かす。
  - 無限に続かないよう、引き継ぐ前にまとまりの `chain_count` を見て、**30 未満なら1増やして引き継ぐ。30 に達していたら引き継がず**、残りの `queued` を `failed`（`error_code = 'CHAIN_LIMIT'`）にする（引き継ぎは最大30回）（10件×最長の記事でも約 3〜4 回で終わる見込みに対し十分な余裕）。
  - 引き継ぎの `fetch` が失敗したとき（応答が 200 でない・例外）は `console.error` に残す。残った `queued` は 20 分後に「失敗」と表示され（FR-007 の止まった行の扱い）、［続きを作成］で再開できる。
- AI 呼び出しは `llmChat` の `timeoutMs: 180_000`（既存の `CONTENT_ANNOTATION_SUMMARY_LLM_TIMEOUT_MS` と同じ値）と `maxRetries: 0` で呼ぶ。429 は `AI_RATE_LIMITED` で `failed`。
- 1ステップごとに「出力の保存 → `instagram_blog_draft_jobs` の `stage` を進める」の順で書く。途中で落ちても、`stage` は最後に保存を終えたステップの次を指す。
- **ジョブの行が消えたとき（Instagram の連携解除）**: 連携解除（`disconnectInstagram` → `purgeInstagramData`。`src/server/actions/instagramSetup.actions.ts:107-117`、`src/server/services/instagramMediaService.ts:605-613`）は `instagram_media` を全削除し、cascade でジョブの行も消える。ワーカーが自分の `running` の行を更新して（`stage` を進める・`status` を変える・`updated_at` を更新する）更新件数が0件だったら、その投稿の処理をそこで止め（次の AI 呼び出しに進まない）、`console.error` を残すだけにする。`queued` の取り出しで0件になるのは別のワーカーが取った通常の場合なので、これには当たらない。
- まとまりの全行が `completed` / `failed` になったら、FR-010 のメールを送る。**行を終わらせたすべての経路**（ワーカーが `completed` / `failed` にしたとき、受け口が `CHAIN_LIMIT` / `ROLE_REVOKED` にしたとき、［続きを作成］でその行を新しいまとまりへ移したとき〈元のまとまりの残りが全部終わっていれば〉）の最後に、共通の関数 `finalizeBatchIfDone(batchId)` で終了を判定する。まとまりの行が0件（連携解除で消えた）のときは「全行が終わった」とみなさず、メールを送らずに `notified_at` だけ埋める（BR-008 例外4）。

**FR-007（再開）**:

- Route Handler `POST /api/instagram/blog-drafts/[jobId]/resume`（新設）。`user_id` 一致・`status = 'failed'` または「止まっている `running` / `queued`」（下記）のときだけ受ける。その投稿を**新しいまとまり（1件）**に移し（`instagram_blog_draft_batches` を1行作り、`batch_id` を付け替える）、`status = 'queued'` にして `after()` でワーカーを動かす（`stage` から続く）。それ以外は 409。作成中・待機中のまとまり（開始の手順3と同じ判定）があるときも 409 にする（BR-015。同時に進む数を3件までに保つため）。
- **止まっている `running` / `queued` の扱い**: サーバーが落ちる・引き継ぎが途切れると、`running` / `queued` のまま残る（BR-007 (3)）。`updated_at` が 20 分より古い `running` / `queued` は、表示と再開の判定で「失敗」として扱う。20 分は既存の一括 AI 要約の止まった判定と同じ値（`supabase/migrations/20260904000000_add_content_annotation_summary_jobs.sql:121-124`。`maxDuration` 800 秒〈13.3 分〉に対し 15 分では余裕が 1.7 分しかなく、動いている処理を止まったと誤判定しうるため 20 分にしている）。DB の値を書き換える定期処理は持たない。
  - `updated_at` は `instagram_blog_draft_jobs` に既存の `update_updated_at_column()` の trigger（`20260805100000_create_instagram_media_and_account_insights.sql:52` と同じ付け方）を付けて、行を更新するたびに自動で進める。`running` の行は `stage` などを更新するたびに進む（AI 呼び出し1回は最長 180 秒）。
  - `queued` の行は、待っているあいだは更新されない。そのため FR-006 のとおり、ワーカーが起動した直後（開始時と引き継ぎの受け口から動いたとき）に、まとまりの `queued` の行すべての `updated_at` を更新する。1回の実行は 740 秒で次の起動が来るため、待っているだけの行が 20 分を超えることはない。
- **再開位置の判定（二重保存と途切れた出力）**: step1〜6 と見出し（`heading`）は、ステップを実行する前に、ジョブの `continuation_count`（§9）と、そのチャットの最後の assistant メッセージの `model` が `stage` の `model` と一致するかを見て、次のとおり進める。

  | `continuation_count` | 最後の assistant の `model` が `stage` と一致 | 動き |
  | --- | --- | --- |
  | null | しない | そのステップを生成する |
  | null | する | 保存後・`stage` 更新前に落ちた。AI を呼ばずにその出力を使って後続の保存（「メモ・補足情報」・見出し）だけを行い、`stage` を進める |
  | 0 以上 | する | 保存済みの出力は途中で切れている。続きの生成から入る（下記） |
  | 0 以上 | しない | 途切れを記録した後、途切れた出力の保存前に落ちた。`continuation_count` を null に戻し、そのステップを生成する |

- **途中で切れたとき（BR-007 (2)）**: `stop_reason = 'max_tokens'` なら、**先に**ジョブの `continuation_count` を 0 にしてから、途切れた出力を加工せずに `continueChat` で保存する。続き生成は、呼ぶ前に `continuation_count` を1増やし、履歴＋続き生成の指示文で呼び、`truncatedContent + 続き` を加工せずに連結して `chatService.updateLastAssistantMessage` で上書きする（ストリーミング Route Handler の `isContinuation` と同じ。`app/api/chat/anthropic/stream/route.ts:361-369`）。
  - 続きで途切れが解消したら、`updateLastAssistantMessage` の直後に `continuation_count` を null に戻し、その後に「メモ・補足情報」への保存と見出しの確定を行って `stage` を進める。「メモ・補足情報」への保存と見出しの確定は、途切れていない出力になってから行う。
  - `continuation_count` が 2 のとき（続きを2回生成してもまだ途切れている）は続き生成を呼ばず、`status = 'failed'`、`error_code = 'MAX_TOKENS'` で止める。［続きを作成］で再開するときは `continuation_count` を 0 に戻し、このステップの続き生成から再開する（同じステップを最初から生成し直さない）。時間の上限による自動の引き継ぎでは `continuation_count` をそのまま持ち越す（引き継ぎのたびに続き生成の回数が増えないようにするため）。
  - `updateLastAssistantMessage` と `continuation_count` を null に戻す更新の間で落ちたときだけ、完成した出力にもう一度続き生成を呼ぶ余地が残る（2つの書き込みを1つのトランザクションにできないため。受容）。
  - `chatService.updateLastAssistantMessage` は失敗を戻り値ではなく例外で返す（`unwrapSupabaseResult` が throw する。`src/server/services/chatService.ts:378-390`）。例外を受けたら `SAVE_FAILED` で止める。

**FR-008（進み具合）**:

- 進み具合の分母 m は「キーワード案 1 + step1〜6 の 6 + 見出しの数 + 完成形 1 + 内部リンクの候補数」。見出しの数は step5 の後、候補数は完成形の後に決まるため、見出しの数が決まるまでは m を出さず「作成中」だけを出す。候補数が決まると m が増える（誤読しやすい罠）。
- 一覧の各投稿に作成の状態を載せる。`instagramMediaService.getPage` の取得に `instagram_blog_draft_jobs`（`instagram_media_id` で結合、`user_id` 一致）の `status` / `stage` / `heading_index` / `heading_total` / `link_index` / `link_total` / `error_code` / `updated_at` / `session_id` を足し、`InstagramMediaListItem` に `blogDraft` として持たせる。ツールバーの「作成中の記事があります」（BR-015）の判定のため、`queued` / `running` の行があるか（止まっている行を除く）も返す。
- 待機中・作成中の行が一覧に1件以上ある間だけ、15 秒ごとに状態を取り直す（`router.refresh()`。一覧のページングと並び順を変えない）。無くなったら止める。

**FR-010（メール通知）**:

- 送る場所: FR-006 の `finalizeBatchIfDone(batchId)`。まとまりの行が1件以上あり、その全行が `completed` / `failed` なら送る。行が0件（連携解除で消えた）なら送らず `notified_at` だけ埋める（BR-008 例外4）。複数のワーカーが同時に最後を迎えても1通にするため、`instagram_blog_draft_batches.notified_at` を条件付き UPDATE（`where id = ? and notified_at is null`）で取れたワーカーだけが送る。
- 宛先: `users.email` を `user_id` で取る（既存の `fetchUserEmail` と同じ取り方。未登録なら送らない）。`ROLE_REVOKED` で終わったまとまりには送らない（`notified_at` だけ埋める。機能を使えなくなった利用者への案内になるため）。
- ［続きを作成］でまとまりから外れた行は、元のまとまりのメールには載せない（新しいまとまりのメールに載る）。
- 送信: `EmailService` に `sendInstagramBlogDraftNotification(to, subject, htmlContent, idempotencyKey)` を足す。形は既存の `sendContentAnnotationSummaryCompletion`（`src/server/services/emailService.ts:130`）と同じ（Resend、`EMAIL_FROM`、`Idempotency-Key`）。`Idempotency-Key` はまとまりの ID。
- 本文: 新規モジュール `src/server/lib/instagram-blog-draft-email.ts` で組む。既存の `content-annotation-summary-email.ts` と同じく、リンクは `NEXT_PUBLIC_SITE_URL` を頭に付けた絶対 URL にし、`sanitizeEmailHtml` を通す。
  - 件名: 全件完了なら「【GrowMate】ブログ記事ができました（N件）」、1件以上止まったら「【GrowMate】ブログ記事の作成が終わりました（完了 X件・止まった Y件）」。
  - 本文: 投稿ごとに1行ずつ、主軸kw（キーワード案の前に止まったときはキャプションの先頭 30 文字）と結果を並べる。

    | 結果 | 本文 | リンク |
    | --- | --- | --- |
    | 完了 | 「できました」。内部リンクの提案が1件以上あれば「内部リンクの提案 N件」 | `/chat?session=<sessionId>&initialStep=step7`、提案があれば `/analytics/<annotationId>`（本文で「内部リンク」タブを案内する。詳細画面はタブを URL で開けないため、タブ指定の URL は作らない） |

**FR-011（候補の検索）**:

- 完成形を保存した後（`combine` の後）、`link_terms` が1語以上あれば候補を探す。0語なら `links` を飛ばして完了にする。
- 検索は新規 RPC `find_internal_link_candidates(p_user_id uuid, p_terms text[], p_exclude_annotation_id uuid, p_limit int)`（SQL は §9）で行う。`content_annotations` のうち `user_id` 一致・`wp_content_text` が空でない・今回の記事以外で、`wp_content_text` に含まれる語の種類数が1以上の行を、種類数の多い順（同数なら `updated_at` の新しい順）に最大 `p_limit`（10）件返す。返すのは `id` / `wp_post_title` / `canonical_url` / 一致した語の配列だけで、本文は返さない（10本ぶんの本文は FR-012 で1本ずつ取る）。
- 部分一致（`position(term in wp_content_text) > 0`）で数える。ユーザーの全記事の本文を毎回走査する。記事数に上限は無いが、1回の取り込みは最大 1000 件（`wordpressImport.actions.ts:192`）で、現状の利用規模では許容する（数千件を超えて遅くなったら全文検索索引を検討する、と RPC にコメントで残す）。
- 候補の数を `link_total` に入れ、`link_index = 0` から始める。

**FR-012（提案の生成）**:

- **本文の正規化**: `wp_content_text` は `stripHtml`（`src/lib/utils.ts:8-10`）でタグを空白1つに置き換えただけの文字列で、HTML エンティティ（`&nbsp;` `&#8217;` など）と改行が残る（取り込み `wordpressService.ts:717-723`、キャッシュ更新 `wordpressContentSync.ts:37-44`）。そのままでは AI が返す文と一致しないため、新規の純関数 `normalizeArticleText` で次の順に揃える: (1) HTML エンティティを文字に戻す、(2) 連続する空白・改行を空白1つにする、(3) 日本語の文字（ひらがな・カタカナ・漢字・全角記号）に挟まれた空白を消す、(4) 前後の空白を除く。AI に渡す本文、`quote` との一致判定、画面に出す「今の文」は、すべて正規化後の文字列を使う。
- **AI に渡す範囲**: 本文全体ではなく、一致した語（`matchedTerms`）の出現位置ごとに前後 500 文字を切り出し、重なりはつなげ、合計 3,000 文字までを渡す（`INTERNAL_LINK_SOURCE_EXCERPT_CHARS`）。本文の上限 `CONTENT_ANNOTATION_SUMMARY_MAX_CONTENT_CHARS` は 80,000 文字で、候補10本に全文を渡すと入力が大きすぎるため。切り出しは正規化後の本文で行う。
- 候補 i ごとに、新規テンプレート `internal_link_suggestion`（`prompt_templates`。§9）で `llmChat` を1回呼ぶ。入力変数:
  - `{{newArticleMainKw}}`（主軸kw）、`{{newArticleKw}}`、`{{newArticleStructure}}`（`basic_structure` の見出し）、`{{newArticleLead}}`（書き出し）
  - `{{sourceTitle}}`（過去記事のタイトル）、`{{sourceText}}`（上の切り出し）、`{{matchedTerms}}`（一致した語）
- 出力は JSON `{"suggestions": [{"quote": string, "anchor_text": string, "rewritten": string}]}`（0〜3件）。Zod で検証し、次の条件を満たさない提案は捨てる。
  - `normalizeArticleText(quote)` が、正規化後の過去記事の本文（切り出し前の全文）に一字一句含まれる
  - `anchor_text` が `rewritten` に含まれる
  - `rewritten` にリンクの書式（HTML・Markdown）を含めない。リンク先の URL は表示時に当てはめる（BR-012）
- 残った提案を `internal_link_suggestions` に保存する（§9）。候補1本ぶんの失敗は飛ばして次へ進む（BR-014）。
- **時間の上限**: 候補は1本ずつ順に呼ぶ（投稿どうしを同時に3件進めるため、1投稿の中では並列にしない。同時の AI 呼び出しを最大3本に抑える。BR-015）。候補1本に着手する前に FR-006 の残り時間を判定し、足りなければ待機中に戻して次の処理に引き継ぐ。
- `link_terms` の検証: 1〜5語・各 20 文字以内に収まらないものは、範囲を超えた語を捨てる・切り詰めるだけにし、キーワード案（FR-002）全体の失敗にしない。
- 1候補ごとに「保存 → `link_index` を進める」の順で書く。再開時は `link_index` の候補から続ける。同じ候補の提案が既に保存されていれば（保存後・`link_index` 更新前に落ちた）、AI を呼ばずに `link_index` を進める。
- モデル設定は `MODEL_CONFIGS` に `internal_link_suggestion` を追加する（`ANTHROPIC_BASE`、`maxTokens: 2000`）。

**FR-013（詳細画面の表示）**: §6 画面設計「`/analytics/[annotationId]`」。

**FR-014（完了メール）**: FR-010 の表の「完了」行。提案の件数は `internal_link_suggestions` の行数。

### 入力・出力・状態遷移

- 入力値・形式・必須条件:
  - 開始: `instagramMediaIds`（`instagram_media.id`、UUID の配列、1〜10件）。本人の投稿でキャプションが空でなく、まだ作成が無いものが対象
  - 再開: `jobId`（`instagram_blog_draft_jobs.id`）。本人の行で再開できる状態であること
  - 引き継ぎ（内部）: `batchId`。`CRON_SECRET` の Bearer 認証
- 正常時の出力: 200。本文は対象の件数と対象外の件数・理由の内訳のみ（生成内容は返さない）
- エラー時の出力:

  | 条件 | HTTP | 画面の表示 |
  | --- | --- | --- |
  | 未ログイン・ロール不可 | 401 / 403 | 既存の Instagram タブと同じ（そもそもチェック列・ツールバーのボタンを出さない） |
  | 0件・11件以上 | 400 | ボタンを押せないため通常は出ない（11件以上は「一度に作成できるのは10件までです」） |
  | 作成中・待機中のまとまりがある | 409 | ボタンを押せないため通常は出ない。出たら一覧を再読み込みして「作成中の記事があります…」を出す |
  | 対象が0件（全部が対象外） | 400 | トースト「選んだ投稿はすべて対象外でした（対象外: 作成あり M件・キャプションなし K件・その他 L件）」 |
  | 自動作成の途中で止まった | —（応答後） | 行が「失敗」「途中で切れました」のどちらかになる（§6 状態別UI） |

- 状態と遷移条件（`instagram_blog_draft_jobs.status`）:

  ```text
  （行なし）──選んで［ブログ記事を作成］──► queued
  queued ──ワーカーが取り出す──► running
  running ──完成形を保存し、内部リンク提案を作り終える──► completed
  running ──時間の上限に近づく──► queued（次の処理に自動で引き継ぐ）
  running ──AI 失敗（AI_FAILED / AI_RATE_LIMITED）・途切れ（MAX_TOKENS）・見出し0件（NO_HEADINGS）・キーワード形式不正（KEYWORD_PARSE_FAILED）・書き出しの取り出し失敗（LEAD_PARSE_FAILED）・保存失敗（SAVE_FAILED）──► failed
  queued ──引き継ぎが30回に達した・権限が外れた──► failed（CHAIN_LIMIT / ROLE_REVOKED）
  running / queued ──サーバー停止・引き継ぎの途切れ（updated_at が20分より古い）──► （表示上）失敗
  running / queued ──Instagram の連携解除（instagram_media ごと削除）──► （行なし。ワーカーは更新0件でその投稿を止める）
  failed / 止まった running・queued ──［続きを作成］──► queued（新しいまとまり）
  ```

- `stage` の値と順序: `keywords` → `step1` → … → `step6` → `headings`（見出しの初期化と書き出しの保存）→ `heading`（`heading_index` で何本目かを持つ）→ `combine` → `links`（`link_index` で何本目の候補かを持つ。Phase 3）→ `done`
- 冪等性・重複実行時の挙動: 開始は一意制約で1投稿1行（BR-003）。ワーカーの取り出しと再開は `status` の条件付き UPDATE で1回だけ通す（2つのワーカーが同じ行を進めない）。チャットと行の二重作成は FR-003 の順序（`session_id` を先にジョブへ書く・`content_annotations` は `session_id` で upsert）で、書き出しの二重保存は FR-005 の `getStep7UserLead` の確認で、ステップの二重保存と途切れた出力の扱いは FR-007 の再開位置の判定で防ぐ。メールは `notified_at` の条件付き UPDATE と `Idempotency-Key` で1通にする。

- 概要: ブログ一覧（`/analytics`）の一括操作と同じ形にする（2026-09-27 遠藤決定「複数記事作れるようにブログ記事同様に、チェックボックス形式にしてボタンクリックする」「UIも合わせて」。提示されたブログ一覧の画面で、左端のチェック列とツールバーの［評価サイクルを開始］［AIで要約］の位置）。
  - **チェック列**: 表の左端（操作列の左）。ヘッダに全選択、各行にチェック。見た目・幅・選択中の行の背景色はブログ一覧と同じ（`src/components/AnalyticsTable.tsx:1107-1119` のヘッダ、`:1244-1263` の行）。
    - 選択はページ送りをまたいで保持し、一覧の中身が入れ替わる絞り込み（種別・投稿日の期間・高エンゲージメント率）を変えたら解除する（ブログ一覧と同じ。`docs/specs/analytics-bulk-actions-impl-note.md` §3.1）。
    - **全選択の範囲はブログ一覧と違い、表示中のページの投稿だけ**にする。ブログ一覧の全選択は「全記事（最大1000件）」だが、本機能は1回10件まで（BR-015）で、全投稿を一度に選ぶ使い方が成り立たないため。全選択中の個別解除・除外集合（`excludedIds`）は持たず、選ばれた ID の集合だけで持つ。
  - **ツールバー**: 1件以上選ぶと、フィルターの行（`app/analytics/components/InstagramTab.tsx:471` の `flex flex-wrap items-end gap-3`）の「期間を適用」のグループの右（［最新化］の左）に、「選択中 N 件」と［ブログ記事を作成］を出す。ブログ一覧で「期間を適用」の右に「選択中 N 件 / 全 M 件」［評価サイクルを開始］［AIで要約］を並べているのと同じ位置関係（`app/analytics/AnalyticsClient.tsx:477-530`）。Instagram 側は全選択が表示中のページだけなので「/ 全 M 件」は出さない。
    - ［ブログ記事を作成］の見た目はブログ一覧の［AIで要約］と同じ（紫の枠線ボタン＋`Sparkles` アイコン。押下中は回転アイコン＋「作成を開始中...」）。どちらも AI に作らせる操作で、同じ見た目にそろえる。
    - 11件以上選んでいる、または作成中・待機中の記事があるときは押せず、ボタンの右に理由を小さく出す（BR-015）。
  - **変更するファイルと差し込み位置**: 表の本体は `app/analytics/components/InstagramMediaTable.tsx`。チェック列と操作列は、今の左端のサムネ列（`<thead>` の `:311`、行の `:345-347`）の左に、チェック列 → 操作列の順で差し込む。選択の状態・作成中の判定・ツールバーは `app/analytics/components/InstagramTab.tsx` で持ち、選択中の ID・切り替えの関数・各行の `blogDraft` を props で `InstagramMediaTable` に渡す。

  - **操作列**: チェック列の右（サムネ列の左）。横スクロールしても左に固定（`analytics-ops-cell`）。見出しは「操作」と折りたたみボタン（展開 380px・折りたたみ 120px。展開状態はブログ一覧と同じ `ANALYTICS_STORAGE_KEYS.OPS_EXPANDED` を共有）。作成が無い投稿の行は空欄。作成がある行は状態に応じて、緑の主ボタン（［チャット］［続きを作成］）・作成中の表示・状態の文字（作成済みを含む）を出す。展開時だけ枠線の副ボタン（止まったときの［チャット］）を出す。

#### 誤読しやすい罠

- 「作成済み」の行は、コンテンツ一覧から記事を削除しても Instagram タブでは作成済みのまま（BR-003）。［チャット］を押すとチャットが無いため既存の「セッションが見つかりません」系の表示になる。削除時に `instagram_blog_draft_jobs` の行を消すかは OPEN-001。
- 進み具合の n/m の m は step5 の後に決まる。作成の前半は m が出ないのが正しい。完成形の後に内部リンクの候補数が足されて m が一度増える。
- 内部リンク タブの書き直し案は作成時点の過去記事の本文から作っている。WordPress で過去記事を直しても、GrowMate 側の本文は更新されない（取り込みの差分判定 `hasChanges` は本文を比べず〈`wordpressImport.actions.ts:269`〉、本文キャッシュも空のときしか取り直さない〈`wordpressContentSync.ts:286`〉）。提案は作り直さない（Non-goal）ので、直し終えた提案もタブに残る。
- 自動作成した記事は URL も WordPress の記事 ID も持たない。公開後に URL を登録する前に WordPress 取り込みを実行すると、同じ記事の行が取り込み側で別に作られ、その後の URL 登録が一意制約で失敗する（R-011）。URL の登録を先に行う。

- 引き継ぎの受け口（`/api/instagram/blog-drafts/continue`）: 利用者の Cookie ではなく `CRON_SECRET` の Bearer 認証で受ける。まとまりの `user_id` から `users.role` を読み直し、`canAccessInstagram` を満たさなければ残りを `ROLE_REVOKED` で終える（FR-006）。
- サーバー側: 開始・再開の Route Handler で `canAccessInstagram(role)` を検証し、投稿・ジョブの `user_id` が本人であることを確認する。`after()` の中の処理は、開始時に確定した `userId` だけを使う。
  - `instagram_blog_draft_jobs` / `instagram_media` / `content_annotations` / `chat_sessions` の読み書きは `user_id` で絞る。
  - `headingFlowService` の `initializeHeadingSections` / `getHeadingSections` / `saveHeadingSection` / `getCombinedContentForPrompt` / `getStep7UserLead` は `session_id` だけで絞り `user_id` では絞らない（所有の確認は Server Action 側の `verifySessionReadAccess` が担っている）。自動作成では、**各ステップの実行前に、ジョブ行の `user_id` と `session_id` で `chat_sessions` の所有（`getChatSessionById(sessionId, userId)`）を確認してから**これらを呼ぶ。

## 11. トレードオフ判断

### ALT-001: 自動作成の実行方式

- 判断: 数分かかる複数回の AI 呼び出しをどこで実行するか
- 比較した案:
  - 案A: Route Handler の `after()` で応答後に実行し、1回の実行時間を超えそうなら自分で次の処理を起動して引き継ぐ（採用。当初は「ユーザーの［続きを作成］で再開」としていたが、一括作成（ALT-006）で10件を手で再開させるのは成り立たないため 2026-09-27 に自動の引き継ぎへ変更）
  - 案B: ジョブを積み、既存の一括 AI 要約と同じ GitHub Actions の10分間隔の定期実行（cron）で処理
  - 案C: ブラウザが1ステップずつ API を呼んで進める
- 採用案: 案A
- 採用理由: 押してすぐ始まり、定期処理・キュー基盤を新設しない。1回の実行（740 秒）で終わらない分は、自分で次の処理を起動して自動で引き継ぐ（FR-006。上限30回）。
- 却下した案と理由:
  - 案B: 始まるまで最大10分以上待つ。GitHub Actions の schedule は 2026-08-26 以降大幅に間引かれており、起動間隔を当てにできない。
  - 案C: タブを閉じると止まる。「作って提案しました」（ユーザーは作成を見張らない）に合わない。
- 影響: 1回で終わらない分は自動で引き継ぐ（R-002）。引き継ぎが途切れると待機中で止まり、20 分後に「失敗」と表示される（R-012）。
- 将来変更する条件: 引き継ぎの途切れが頻発したら、案B の cron で止まった `queued` を拾う経路を足す（本書のテーブルはそのまま使える）。
- 判断者・判断日: 遠藤・2026-09-26

### ALT-002: 作成のきっかけと自動化の範囲

- 判断: どこまでをユーザー操作にし、どこからを自動にするか
- 比較した案:
  - 案1: ボタンでキーワード案と行・チャットだけを作り、step1 以降は既存フローで手動
  - 案2: ボタンで step1〜5（構成案）まで自動、本文は手動
  - 案3: ボタンで本文の完成形まで自動（採用）
  - 案4: ［最新化］で目標達成の投稿を検出し、完成形まで自動
- 採用案: 案3
- 採用理由: 2026-09-26 遠藤判断「最初のコンテンツ選択はユーザーがやって、そのあとは、ブログコンテンツが自動生成されるまで自動化するのが良い」。案1 は操作回数がほとんど減らない。MTG の「勝手に作っちゃうみたいな作って提案しました…この中にポコッと入る」に最も近いのは案3・案4 で、どの投稿を記事にするかの判断はユーザーに残す。
- 却下した案と理由:
  - 案1・案2: 手動の操作が残り、効率化にならない（同日遠藤指摘「案1だと実装してもあまり効率化されない」）。
  - 案4: 記事にする投稿の選択をユーザーから奪う。［最新化］ごとに API 費用が発生し、重複の防止と費用の上限の設計が別に要る。
- 影響: 途中の出力をユーザーが確認しないまま次のステップへ進む。品質は既存テンプレートに依存する（R-004）。
- 将来変更する条件: 選ぶ手間が問題になったら案4 を検討する。
- 判断者・判断日: 遠藤・2026-09-26（開発方針としての決定は Q-002。クライアントの合意は §14 の実装前ゲート「UIたたき台・要件合意」で取る。2026-03-03「やるなら事前に許可をとっていただきたいです」）

### ALT-006: 複数の投稿をまとめて作る方式

- 判断: 複数の投稿を選べるようにしたとき、UI と処理をどう組むか
- 比較した案:
  - 案A: ブログ一覧と同じチェック列＋ツールバーのボタン。1回最大10件、同時に3件並行、時間の上限は自動で引き継ぐ。結果はまとめてメール1通（採用）
  - 案B: 投稿ごとのボタン（前版）のまま
  - 案C: 選んだ投稿を1件ずつ順番に処理する
- 採用理由: 2026-09-27 遠藤決定「複数記事作れるようにブログ記事同様に、チェックボックス形式にしてボタンクリックするのが良い」「UIも合わせて」。ブログ一覧の一括操作と同じ操作にそろう。
- 却下した案と理由:
  - 案B: 複数件を作るたびに1件ずつ押す必要がある。
  - 案C: 10件で数時間かかる。3件並行なら所要時間はおよそ3分の1になり、同時の AI 呼び出しも3本に収まる。
- 影響:
  - 前版の「時間の上限で一時停止し、ユーザーが［続きを作成］で再開する」は、10件ぶん手で押させることになり成り立たない。自分で次の処理を起動する自動の引き継ぎ（FR-006）に変えた。これに伴い「一時停止」の表示・メールは無くなった。
  - メールは投稿ごとではなく、まとまりが全件終わったときに1通（BR-008）。
  - 全選択はブログ一覧と違い表示中のページだけ（1回10件までのため）。
- 将来変更する条件: 10件ずつ選ぶ手間が問題になったら上限を見直す。
- 判断者・判断日: 遠藤・2026-09-27

### ALT-003: ステップの出力を「メモ・補足情報」に保存するか

- 判断: 手動フローでユーザーが転記している項目を、自動作成で埋めるか
- 比較した案:
  - 案A: 各ステップの出力をそのまま対応する項目に保存（採用）
  - 案B: 出力を AI で要約してから保存
  - 案C: 保存しない
- 採用案: 案A
- 採用理由: step2 以降のプロンプトと step7 の見出し作成がこの値を読む（BR-005、`useHeadingFlow.ts:221`）。案B は AI 呼び出しが6回増える。
- 却下した案と理由: 案C は後のステップのプロンプト変数が空になり、見出しも作れない。
- 影響: 項目には各ステップの出力全文が入り、ユーザーが手で書く場合より長くなる。コンテンツ一覧の表示は既存の `TruncatedText`（3行で省略）で崩れない。

- 判断者・判断日: 遠藤・2026-09-26

### ALT-004: 内部リンク提案を作るタイミングとリンク先 URL の扱い

- 判断: 記事に URL が無い作成時点で提案を作るか、URL の登録後に作るか
- 比較した案:
  - 案A: 記事の作成の最後に提案を作り、リンク先 URL は表示時に当てはめる（採用）
  - 案B: 記事の URL が登録された時点で提案を作る
  - 案C: 詳細画面にボタンを置き、ユーザーが押したときに作る
- 採用理由: 2026-09-27 遠藤「ブログ記事を作る時に必要だから」。作成と同時に「どこからリンクされるか」が分かる。URL は提案の中身（どの文のどの語か）に影響しないため、後から当てはめられる。
- 却下した案と理由:
  - 案B: URL の登録は既存の編集操作で、そこに AI 処理のきっかけを足すと既存の保存処理に待ち時間と失敗が入る。
  - 案C: 押す操作が1つ増え、「作って提案しました」から外れる。
- 影響: 作成から公開までの間に過去記事が変わると、提案が古くなる（誤読しやすい罠）。
- 将来変更する条件: 提案が古くなる問題が実際に出たら、案C のボタンで作り直せるようにする。
- 判断者・判断日: 遠藤・2026-09-27

### ALT-005: 内部リンクの候補の探し方

- 判断: 過去記事からどう候補を絞るか
- 比較した案:
  - 案A: AI が出した語（`link_terms`）の部分一致で最大10本に絞り、候補だけを AI に読ませる（採用）
  - 案B: 全過去記事を AI に読ませる
  - 案C: 埋め込みベクトルで意味の近い記事を探す
- 採用理由: 新しい依存・索引を足さずに、費用を候補数（最大10回）で抑えられる。MTG の例（「魚粉について触れてるから」）は語の一致で拾える。
- 却下した案と理由:
  - 案B: 過去記事の数だけ AI を呼ぶ（数百回）。
  - 案C: 埋め込みの生成・保存・更新の仕組みが新たに要る（MVP の範囲外）。
- 影響: 同じ意味でも違う言い方の記事は拾えない（R-009）。`link_terms` に言い換えを含めるようテンプレートで指示して緩和する。
- 将来変更する条件: 拾い漏れが問題になったら案C を検討する。
- 判断者・判断日: 遠藤・2026-09-27

  - 自動作成サービス: `stage` の順序、各ステップの保存先（BR-005 の表）、時間上限での待機中への戻しと引き継ぎ（`chain_count` の加算。境界は 29→30 は引き継ぐ、30 のときは引き継がず `CHAIN_LIMIT`）、ワーカーの取り出しの排他（2つのワーカーが同じ行を進めない）、同時3件まで、再開位置の判定（FR-007 の表の4通り。`continuation_count` と最後の assistant メッセージの `model`）、`keywords` からの再開でチャットと行を二重に作らないこと（ジョブの `session_id` の再利用・`content_annotations` の `session_id` での upsert）、`headings` からの再開で書き出しの user メッセージを2件にしないこと（`getStep7UserLead`）、見出し0件・`max_tokens`・AI 失敗時の `failed` と `error_code`、自分の `running` の行の更新が0件（連携解除で消えた）ならその投稿を止めること、まとまりの行が0件ならメールを送らず `notified_at` だけ埋めること
  - キーワード案の JSON 検証（正常・空・形式不正）
  - 止まった `running` / `queued` の判定（`updated_at` 20 分）。ワーカーの起動時にまとまりの `queued` の行すべての `updated_at` が進むこと（待っているだけの行を「失敗」と判定しない）
  - 権限と開始の拒否: trial は 403。他人の投稿・存在しない ID・作成あり・キャプションなしは対象外として除外（全件対象外なら 400）。作成中・待機中のまとまりありは 409。再開できない状態の再開は 409

  - 内部リンク提案: `normalizeArticleText`（エンティティ・連続空白・日本語に挟まれた空白）と切り出し（前後 500 文字・重なりの結合・合計 3,000 文字）、候補ごとの時間判定、`link_terms` の範囲外を捨てても FR-002 が失敗しないこと、RPC の順位付け（一致した語の種類数→`updated_at`）と今回の記事の除外、`quote` が本文に無い提案・`anchor_text` が `rewritten` に無い提案を捨てること、候補1本の失敗で他の候補と記事の完成が止まらないこと、`links` からの再開、表示時の URL の当てはめとコピー（`text/html` に `<a href>`、`text/plain` にリンク無しの文）、URL 未登録時にコピーできないこと、RLS（本人以外は select できない）
  - 一括作成: 0件・11件以上・作成中のまとまりありの拒否、対象外（他人の投稿・キャプションなし・作成済み）の除外と内訳、引き継ぎの受け口の `CRON_SECRET` 認証と権限の読み直し（`ROLE_REVOKED`）、［続きを作成］で新しいまとまりへ付け替えること、止まった `queued` の判定
