## 1. 背景・目的・成功指標

### 背景・解決したい課題

- 現在、誰が、どの業務で困っているか:
  - 利用者（クライアント）は、GrowMate の外で自前のコードや AI を使って大量のページを作り、WordPress に公開している（`client-vision-from-lark.md` §1.9.3。生産量は月1000〜2000本規模、§1.9.1）。
  - そのコンテンツ情報（キーワード・表示回数・ペルソナなど9項目）を GrowMate に入れる手段が、1件ずつの手入力か、GrowMate の AI 要約しかない。
  - AI 要約は API 費用がかかるため、2026-10-17 から一時的に `admin` 限定にしている（`src/authUtils.ts` の `canUseContentAnnotationSummary`）。
- 放置した場合の影響: 外部で作った記事のコンテンツ情報が入らず、GSC 改善提案などコンテンツ情報を材料にする機能が十分に働かない。AI 要約に戻すと API 費用がかかる。

### 目的

- この開発で実現する状態: 利用者が、自分のコードや AI で作った CSV を1回アップロードするだけで、多数の記事のコンテンツ情報をまとめて登録・更新できる。
- 利用者・事業にとっての価値: AI 要約（GrowMate 側の API 費用）を使わずに、コンテンツ情報を揃えられる。

### 成功指標

| 指標 | 現状 | 目標 | 測定方法 | 測定時期 |
| --- | --- | --- | --- | --- |
| CSV でのコンテンツ情報の登録 | 手段なし | 月1000〜2000本規模（§1.9.1）の CSV を1回のアップロードで最後まで取り込める | 2000行の CSV で手動確認 | リリース前 |
| AI 要約の利用 | admin 限定で停止中 | CSV 取り込みで代わりになり、paid に戻す必要がない | クライアントの運用で確認 | リリース後1か月 |

## 2. 利用者・関係者・利用シナリオ

| 区分 | 対象 | 期待すること・責任 |
| --- | --- | --- |
| 利用者 | `admin` / `paid` | テンプレートの列に沿って CSV を作り、アップロードする |
| 運用担当 | 開発者 | 取り込みの失敗をログで確認する |
| 管理者・承認者 | クライアント（繁田） | 画面のたたき台・事前共有の制約を確認する |
| 外部サービス・連携先 | 利用者が使う AI（ChatGPT・Claude など） | GrowMate とは連携しない。利用者が自分で CSV を埋めるのに使う |

### 主な利用シナリオ

1. **paid の利用者が**、**自前のコードで数千ページを作っている状態で**、**テンプレートの列の定義に合わせて CSV を書き出し、アップロードしたい**。
2. **paid の利用者が**、**手元に記事だけがある状態で**、**テンプレートと記事を自分の AI に渡して CSV を埋めてもらい、アップロードしたい**。
3. **paid の利用者が**、**取り込みのあと**、**件数とスキップした行の理由を確かめ、一覧で項目が入ったことを確認したい**。

## 3. 業務要件と業務フロー

### 現状（As-Is）

```text
外部で記事を作る → WordPress に公開 → GrowMate の WordPress 取り込みで記事が並ぶ
→ コンテンツ情報（9項目）は1件ずつ手入力、または AI 要約（現在 admin 限定）
```

### 導入後（To-Be）

```text
/analytics（ブログタブ）の「CSV で取り込む」を開く
→ テンプレート CSV をダウンロード（列の定義を確認）
→ 自前のコード、または自分の AI で CSV を作る
→ CSV を選ぶ（ブラウザで解析し、読めない場合はその場で理由を表示）
→ 取り込む: URL で照合し、GrowMate にある記事は値のあるセルだけ上書き / 無い URL は新規作成
→ ダイアログに結果（件数とスキップした行の理由）を表示し、一覧を再読み込み
→ 評価サイクルは自動では始まらない。必要なら一覧の一括操作で始める
```

### 業務ルール

- BR-01: 照合キーは URL。CSV の URL を整えたうえで（§6 FR-002 の「URL の整え方」）、正規化（`src/lib/normalize-url.ts` の `normalizeUrl` と同じ処理。小文字化・`http(s)://` の除去・先頭 `www.` の除去・末尾 `/` の除去。クエリ文字列と `#` 以降は残す）した値で、ログインユーザーのコンテンツと照合する。
- BR-02: GrowMate にある記事は、CSV で値のあるセルだけ上書きする。空のセルは今の値を残す（ユーザー指示「既存コンテンツは基本は上書き」・10-18 の合意）。
- BR-03: GrowMate に無い URL は、その URL と CSV の値を持つコンテンツとして新規作成する（10-19 回答）。
- BR-04: 取り込みでは、正規化した URL が同じ記事を新しく作らない（取り込み処理の中で照合して防ぐ。DB の一意制約は足さない。Claude案、Q-004 で承認済み）。

### 影響する既存機能（CSV で新規作成した記事は、WordPress と紐付くまで URL と9項目だけを持つ）

| 機能 | 影響 |
| --- | --- |
| 一覧・チャットを開く | 影響なし。一覧の RPC は投稿 ID で絞らず、チャットは記事 ID からセッションを作る（`ensureAnnotationChatSession`） |
| GSC の日次取り込み・評価 | 正規化 URL で記事を引くので対象にできる（`gscImportService.ts`）。評価サイクルは自動では始まらない |
| GSC 改善提案 | 投稿 ID が無いと本文・タイトル・説明文を WordPress から取らない（`fetchWpPostContentWithCache`）ため、段階1（タイトル・説明文）と段階3（本文）は既存のスキップ表示になる。WordPress 取り込みで紐付くと出る |
| GA4 評価 | 本文が空だと「未評価」になる（`ga4ContentEvaluationService.ts`）。WordPress 取り込みで紐付くと評価できる |
| AI 要約（admin 限定） | URL があるので「連携済み」とみなされ、連携先の WordPress に同じ URL があれば要約できる。無ければ既存のエラー表示 |
| 未要約フィルタ | URL があり8項目が空の記事は「未要約」に入る（既存の判定どおり） |

| 対象外にするもの | 理由 | 将来検討する条件・時期 |
| --- | --- | --- |

### FR-001 テンプレート・列の定義

- テンプレート CSV（ブラウザで作ってダウンロードする）:
  - ファイル名は「コンテンツ情報_取り込みテンプレート.csv」（利用者が保存先で見て何のファイルか分かる名前にする。英語や内部の名前は使わない）。
  - 文字コードは UTF-8（BOM 付き。Excel で開いても文字化けしないため）。
  - 1行目の見出しだけを持つ。9項目の見出しは一覧の列名（`src/lib/constants.ts` の `ANALYTICS_COLUMNS`）に揃える。照合キーの列だけは、一覧の列名「URL」ではなく「記事URL」にする（「URL」だけでは管理画面やプレビューの URL と迷い、AI が URL を作ってしまうおそれがあるため。2026-10-19 ユーザー承認）。

  | 見出し | 取り込み先 | 必須 | 列の定義（ダイアログに表示） |
  | --- | --- | --- | --- |
  | 記事URL | 照合キー（`canonical_url`） | 必須 | 公開中の記事ページの URL（ブラウザで開いたときのアドレス。`http://` または `https://` から）。管理画面やプレビューの URL ではない |
  | 主軸kw | `main_kw` | 任意 | 記事の主となる検索キーワード |
  | kw（参考） | `kw` | 任意 | 関連する検索キーワード（複数は改行区切り） |
  | 表示回数 | `impressions`（テキスト列。文字列のまま保存） | 任意 | 表示回数や検索ボリュームの情報（入力欄の説明 `AnnotationFormFields.tsx` と同じ） |
  | ニーズ | `needs` | 任意 | 検索する人が知りたいこと |
  | デモグラ・ペルソナ | `persona` | 任意 | 想定する読者像 |
  | ゴール | `goal` | 任意 | 読み終えた読者に取ってほしい行動 |
  | PREP | `prep` | 任意 | 主張・理由・具体例・結論 |
  | 基本構成 | `basic_structure` | 任意 | 導入や見出しの構成 |
  | 書き出し案 | `opening_proposal` | 任意 | 書き出しの方向性や冒頭で伝えたい内容 |

  - 9項目は今コンテンツ情報として入力する項目すべて（`src/types/annotation.ts`、`src/components/AnnotationFormFields.tsx`）。ユーザー定義の項目は無い。
  - 列の定義は、自前のコードで CSV を書き出す利用者向けに、ダイアログ上で表として見られるようにする。
- 「テンプレート（CSV）」ボタンの横に「ⓘ」を置き、マウスを乗せると次の説明を出す（2026-10-19 ユーザー指示）:
  - 1行目の見出しは変えないでください。1記事につき1行です。
  - 記事URL には、公開中の記事ページの URL を書いてください。
  - 分からない項目は空欄のままにしてください。
  - Excel で保存するときは、ファイルの種類で「CSV UTF-8 (コンマ区切り)」を選んでください。

### FR-002・FR-003 取り込み

- 解析（ブラウザ）:
  - 数十行の自前実装で、引用符・セル内改行・BOM に対応する。新しい依存は入れない（`AGENTS.md` の実装ラダー）。
  - 文字コードは `TextDecoder('utf-8', { fatal: true })` で判定し、読めなければエラー（「Excel の場合は『CSV UTF-8』で保存し直してください」と案内）。
  - 1行目の見出しで列を対応づける。見出しは前後の空白を除き、NFKC で正規化してから照合する（AI が「kw（参考）」を「kw(参考)」で出しても対応づける）。列の並びは問わない。知らない見出しの列は無視する。照合キーの列は「記事URL」と「URL」のどちらの見出しでも受け付ける（一覧の列名に合わせて書いた CSV も取り込めるようにするため）。どちらも無ければエラー。
  - 最大 20,000行（Claude案、Q-006 で承認済み）。超えたらエラー（「ファイルを分けて順に取り込んでください。同じ行を何度取り込んでも結果は同じです」と案内）。
  - 同じ URL（正規化後）が複数行ある場合は後の行を採用し、結果に「重複」として件数を出す（Claude案、Q-007 で承認済み）。分割して送る前にファイル全体で行う。
  - 結果に出す行番号は、表計算ソフトで開いたときの行番号（見出しが1行目、データは2行目から）。
- URL の整え方（ブラウザ。保存する `canonical_url` にもこの値を使う）: 前後の空白を除き、`new URL(url).href` を通す（日本語などをパーセントエンコードに揃える。既存の `upsertContentAnnotationBySession` の URL 比較と同じ方法）。`http://` / `https://` で始まらない、または `URL` として解釈できない場合はスキップ（理由: URL が不正）。
- セルの値: 前後の空白を除く。空白だけのセルは空として扱う。
- 送信: 行をまとめて Server Action に順に送る（Server Action の受信上限は既定で 1MB。`next.config.ts` では変えていない。この上限はバイト数に効く）。
  - 1回分は、送る内容を直列化した UTF-8 のバイト数（`TextEncoder` で測る）が 800KB 未満で、かつ 2,000行以下になるようにまとめる（日本語は UTF-8 で1文字3バイトなので、文字数では測らない。2,000行はサーバーの Zod が1回に受け付ける上限）。
  - セルの文字数超過（1セル 20,000文字まで）はブラウザでも判定してスキップし（理由: 文字数超過）、送らない。これで1行は最大でも約 660KB（11セル × 20,000文字 × 3バイト）に収まり、どの行も1回分に入る。
  - サーバーの Zod は信頼境界として、1回の行数（2,000行まで）と1セルの長さ（20,000文字まで）を検証する。行数の上限を超えた回は拒否する。セルの長さは行ごとに検証し、超えた行だけをスキップする（理由: 文字数超過。その回全体は拒否しない）。
- 行ごとの判定（サーバー）:

  | 状態 | 扱い | 結果の区分 |
  | --- | --- | --- |
  | URL が不正、またはセルの文字数超過 | 何もしない | スキップ（理由つき） |
  | 正規化した URL に一致する記事が1件あり、値のあるセルがある | 値のあるセルだけ上書き。`updated_at` を更新。`canonical_url` は書き換えない | 更新 |
  | 一致する記事が1件あり、値のあるセルが無い | 何もしない | 変更なし |
  | 一致する記事が2件以上ある（既存データに正規化 URL の重複がある場合） | 何もしない（どれを更新すべきか決められない） | スキップ（理由: 同じ URL の記事が複数ある） |
  | 一致する記事が無く、値のあるセルがある | CSV の URL を `canonical_url` に、値のあるセルを各項目に入れて新規作成（`wp_post_id`・`session_id` は空） | 新規作成 |
  | 一致する記事が無く、値のあるセルも無い | 何もしない（URL だけの空の記事は作らない） | スキップ（理由: 値が無い） |

  - 「更新」は値のあるセルを書き込んだ行の数で、今の値と同じかどうかは比べない。
- 照合・更新・作成は、分割した1回分（jsonb）につき RPC を1回呼んでまとめて行う（URL の一覧を IN 句で渡すとリクエストが長くなりすぎ、1行ずつでは遅すぎるため）。
- RPC の作り方（既存の Service Role 専用 RPC と同じ。例: `supabase/migrations/20260826000300_harden_list_due_ga4_content_evaluations.sql`）:
  - `security definer`、`set search_path = public`、冒頭で `auth.role() <> 'service_role'` なら例外。
  - `revoke execute ... from public, anon, authenticated` と `grant execute ... to service_role`。
  - Server Action がロールを確認したあと Service Role から `p_user_id`（uuid）を渡して呼ぶ。`content_annotations.user_id` は text なので `p_user_id::text` で比べる。
  - jsonb からは URL と9項目のキーだけを読み、`user_id`・`wp_post_id`・`session_id` などは受け付けない。
  - 結果（区分ごとの件数とスキップした行の一覧）は jsonb の1値で返す（行の集合で返すと、1リクエストの返却行数の上限 1000行で黙って欠けるため。`docs/context/db-row-limits-and-data-truncation.md`）。
- 新規作成と CHECK 制約: 本番の `content_annotations` には `content_annotations_key_presence_chk CHECK (wp_post_id IS NOT NULL OR session_id IS NOT NULL)` があり、URL だけの記事は作れない（2026-10-19、本番の読み取りで確認。この制約はリポの migration に無い）。これを `CHECK (wp_post_id IS NOT NULL OR session_id IS NOT NULL OR canonical_url IS NOT NULL)` に広げる migration を足す（Claude案、Q-004 で承認済み。記事ごとにチャットのセッションを作る案は、2万件の不要なセッションができるため採らない）。
- 重複作成の防止（BR-04）: RPC の中で正規化した URL で照合してから作る。同じ利用者が同時に2回取り込んだ場合だけ重複しうる（上限。ダイアログは取り込み中に二重実行できない）。照合のため `(user_id, normalized_url)` に通常の索引を足す。
- 途中の回で失敗した場合は、その回で止めて処理済みの件数と理由を出す。同じファイルで取り込み直してよい。

### FR-004 結果表示

### FR-005 WordPress 取り込みとの関係

- 今の WordPress 取り込み（`src/server/services/wordpressImportService.ts`）は、既存記事を「生の canonical_url の完全一致 → WordPress の投稿 ID」の順に探し、無ければ新規作成する。
- CSV で作った記事は投稿 ID を持たず、URL の書き方（末尾の `/`、`www` の有無など）が WordPress の URL と違うことがある。今のままだと、WordPress 取り込みが同じ記事を別に新規作成する。
- このため、照合に「正規化した URL の一致」を足す（`listContentAnnotationKeys` は既に `normalized_url` を取っている）。正規化 URL で照合する相手は、まだ投稿に紐付いていない記事（`wp_post_id` が空）に限る（別の投稿に紐付いた記事の投稿 ID を上書きしないため）。一致した場合は新規作成せず、その記事に WordPress の投稿 ID・タイトル・本文などを書き込む（今の「既存あり」の更新と同じ扱い。CSV で入れた9項目は WordPress 由来の項目ではないので上書きされない）。
- 照合の決め方（Claude案、Q-005 で承認済み）:
  1. 投稿 ID で当たる記事（A）があれば、それを更新先にする。1回の取り込みの中では2段階で照合する。まず全投稿を投稿 ID で照合して更新先を確保し、そのあと残りの投稿を、2.の生の URL → 正規化 URL の順で照合する。これにより結果は投稿の処理順で変わらない（今の照合ループは1回だけで、投稿の到着順に照合している。`wordpressImportService.ts:249-293`）。
  2. 無ければ、生の URL の完全一致 → 正規化 URL の一致（`wp_post_id` が空の記事のみ）の順に探す。生の URL の一致は投稿 ID の有無を問わない（今と同じ。紐付いていた記事の投稿 ID は付け替わる。未紐付けに限ると、その投稿が新規作成に回り、生の URL の一意索引に当たるため）。
  3. どれにも当たらなければ新規作成する。正規化 URL で2件以上当たった場合は、新規作成も更新もせず `console.warn` に残す（取り込み全体は失敗させない）。
  4. 1回の取り込みの中で、すでに更新先になった記事に2つ目の投稿が当たった場合（スラッグの入れ替え、正規化 URL が同じ別々の投稿など）は、その投稿は更新も新規作成もせず `console.warn` に残す（新規作成に回すと、更新より先に走る新規作成が生の URL の一意索引に当たりうるため）。その投稿は次に取り込まれた回（変更・公開時か全件取り込み）に改めて照合される。
  - 3.（正規化 URL で2件以上当たる）と 4. で見送った投稿は、取り込み結果の既存の件数「重複スキップ」（`duplicatePosts`。`wordpressImportService.ts:246,261`、画面は `app/wordpress-import/WordPressImportClient.tsx:256-259`）に数える。
- 投稿 ID で A に当たり、URL では別の記事 B（CSV で作った記事など）に当たる場合（WordPress でスラッグを変えたあと、新しい URL を CSV で作った場合など）: A を更新する。ただし A の新しい URL が B の生の URL と同じなら、A の `canonical_url` だけは書き換えずに `console.warn` に残す（`idx_content_annotations_user_canonical_unique` に当たって取り込み全体が失敗し、日次取り込みが毎回止まるのを防ぐ）。B に投稿 ID は書かない（`content_annotations_user_id_wp_post_id_key` に当たるため）。A と B はどちらも残る。生の URL まで同じ形では A は古い URL のままなので、A と B の正規化 URL は違い、CSV 取り込みの「同じ URL の記事が複数ある」スキップには入らない（取り込みのたびに `console.warn` が出る。GSC の数値は新しい URL の B に付く）。利用者が B を削除すると、その投稿が次に取り込まれた回に A の URL が新しくなる。正規化 URL だけが同じ形では、A と B の正規化 URL が同じになり、CSV 取り込みでは「同じ URL の記事が複数ある」でスキップする。
- 今の照合順は「生の URL → 投稿 ID」で、上の1.で投稿 ID を先にする（2段階）。違いが出るのは、生の URL と投稿 ID が別の記事に当たる場合だけで、その場合は今でも投稿 ID の一意制約に当たって取り込みが失敗している。
- 差分取り込み（基準日以降に変更・公開された投稿だけを処理する回）では、古い投稿は紐付かない。紐付くのは全件取り込みの回か、その投稿が変更・公開された回。

### 入力・出力・状態遷移

## 13. テスト・リリース・ロールバック

### テスト方針

- 単体:
  - CSV 解析（引用符・セル内改行・BOM・文字コード・見出しの並び替え・NFKC・知らない列・行数上限・重複行・行番号）
  - 分割送信（1回分が UTF-8 のバイト数で 800KB 未満かつ 2,000行以下になる。日本語の多い行と URL だけの行の両方で確かめる。20,000文字を超えるセルの行はブラウザでスキップされ、送られない）
  - URL の整え方（日本語 URL・空白・不正な URL）
  - 行ごとの判定（更新・変更なし・複数一致・新規作成・値が無い・文字数超過）、冪等性
  - 権限（trial の拒否）、RPC が `anon` / `authenticated` から実行できないこと（既存の migration の確認方法に倣う）
  - WordPress 取り込みの照合（正規化 URL で紐付く・`wp_post_id` のある記事には正規化 URL で紐付かない・正規化 URL で2件当たる・投稿 ID と URL が別の記事に当たる場合（生の URL まで同じ形を含む）・1回の中で同じ記事に2つの投稿が当たる場合で、取り込み全体が失敗しない）
  - WordPress 取り込みの2段階照合: スラッグの入れ替え（新しい投稿2が、投稿1に紐付く記事 A の旧 URL を持つ）で、投稿1・投稿2のどちらを先に処理しても、A は投稿1で更新され、投稿2は見送られて「重複スキップ」（`duplicatePosts`）に数えられる
- 実画面確認: ダイアログの5状態、テンプレートのダウンロード（Excel で開いて文字化けしない）、2000行と2万行の取り込み。

### リリース方針

- リリース単位・段階展開: 一括でリリースする（段階展開はしない）。
- Feature Flag / allowlist: 作らない（`AGENTS.md` Core Rules の MVP。止めるときはデプロイを1つ前に戻す）。
- DB 変更の適用順序: migration（CHECK 制約・索引・RPC）→ アプリ。適用前後に advisors（security・performance）を取り、本番の `list_migrations` とリポの差分を確かめる。本番適用はユーザー承認後。
- 本番確認項目: 数行の CSV で更新・新規作成・スキップが期待どおりになる。
- README: §🚀主な機能の「コンテンツ分析」（`README.md:23`）と「WordPress 連携」（`README.md:24`。照合の変更）の更新が発生しそう。要否は spec-to-pr の readme_sync で判断する。

- PostgREST の返却行の上限（Max rows）: 確認済み（回1-1 では公式に記述が見つからず未確認としていた）。
  - 参照: https://docs.postgrest.org/en/stable/references/configuration.html （確認日 2026-10-19）
  - 原文: "A hard limit to the number of rows PostgREST will fetch from a view, table, or function."
  - 解釈: 上限は返す「行」の数に効く。本書の RPC は結果を jsonb の1値（1行）で返すので、上限があっても結果は欠けない（§6 FR-002・FR-003、リポ内の正本 `docs/context/db-row-limits-and-data-truncation.md`）。
