## 1. 背景・目的・成功指標

### 背景・解決したい課題

- 現在、誰が、どの業務で困っているか:
  - `/analytics` の「AIで要約」を利用者（`paid` / `admin`）が実行すると、**1回で完了するのは約24件**にとどまる。Vercel 関数の実行枠（`app/analytics/page.tsx` の `maxDuration = 800` 秒、うち着手可能なのは 730 秒）を、1件あたり実測約30秒の直列処理で使い切るため。
  - 実測: 327件を選択した実行で「24件成功 / スキップ60件 / **未実行243件**」。残りを消化するには同じ操作を約10回繰り返す必要があり、1回あたり約12分の待機が発生する。クライアントから「めちゃ手間」との申告あり（2026-09-04）。
- 放置した場合の影響:
  - 記事数100〜300件規模の利用者が、初期セットアップ（要約の一括生成）を完了できず、要約を前提とする後続機能（評価・提案）の価値に到達しない。
  - 待機中はブラウザのタブを閉じられない。閉じると成功分は保存済みだが、未実行分の再開は利用者の手動操作に依存する。

### 目的

- この開発で実現する状態:
  - 利用者は「AIで要約」を**1回押すだけ**で、選択した全件（最大1000件）が完了まで処理される。押した直後に画面は応答を返し、タブを閉じてよい。
  - 完了したらメールで通知が届く。
- 利用者・事業にとっての価値:
  - 初期セットアップの所要操作が「10回の再実行・約2時間の張り付き」から「1回の操作・放置」に変わる。

### 成功指標

| 指標 | 現状 | 目標 | 測定方法 | 測定時期 |
| --- | --- | --- | --- | --- |
| 300件の要約完了に必要な利用者の操作回数 | 約10回 | **1回** | 実データでの手動確認 | リリース直後 |
| 300件の要約完了までの所要時間 | 約2時間（張り付き） | **約30〜45分**（放置可） | cron 実行ログの `batch_completed` | リリース直後 |
| 実行後にタブを開いたまま待つ必要 | あり（約12分/回） | なし | 手動確認 | リリース直後 |

## 2. 利用者・関係者・利用シナリオ

| 区分 | 対象 | 期待すること・責任 |
| --- | --- | --- |

### 主な利用シナリオ

1. **`paid` の利用者が**、**WordPress インポート直後（未要約が267件ある状態）で**、一覧の全選択から「AIで要約」を実行し、画面を閉じる。
2. **同じ利用者が**、**約30〜45分後に届いたメールで**、成功・失敗・スキップの件数を確認する。
3. **同じ利用者が**、**処理中に `/analytics` を開いたとき**、実行中である旨と進捗（処理済み/全体）を確認する。

## 3. 業務要件と業務フロー

### 現状（As-Is）

```text
利用者 → [AIで要約] 押下
        → Server Action が同期実行（最大760秒）
        → 時間予算切れで打ち切り、「24件を要約しました（未実行243件）」を表示
        → 利用者が同じ操作を繰り返す（約10回）
```

### 導入後（To-Be）

```text
利用者 → [AIで要約] 押下
        → Server Action はジョブを1件起票して即応答（「バックグラウンドで実行します」）
        → 利用者はタブを閉じてよい

10分ごと → GitHub Actions → /api/cron/content-annotation-summary
        → 未処理ジョブを1件 claim（排他）
        → 時間予算(730秒)の範囲で、並列3で要約を実行し、進捗をジョブ行へ保存
        → 全件終わっていなければ pending に戻し、次回の起動で続きから処理
        → 全件終わったら completed にし、完了メールを1通送信
```

### 業務ルール

- ルール ID: **BR-B01 実行単位はジョブ**
  - ルール: 「AIで要約」の押下は、対象記事 ID の集合を持つ**ジョブを1件作る**ことを意味する。要約処理そのものは cron が行う。
  - 例外: なし。
- ルール ID: **BR-B02 対象の解決は起票時に1回だけ**
  - ルール: 全選択（`mode: 'all'`）の母集団解決（親仕様 BR-05 / 評価親 BR-07）は**起票時に1回**行い、解決した ID 配列をジョブに保存する。cron は保存済みの ID だけを処理する。
  - 理由: 母集団は `updated_at` 降順・上限1000件で解決されるため、実行のたびに `updated_at` が動く現行方式では、再実行のたびに対象が入れ替わり同じ記事を処理し続ける（親仕様 R-006）。起票時に固定すれば、この問題は本仕様の範囲では発生しない。
  - 例外: 起票後に削除された記事は、処理時点で「所有者不一致・不在」として失敗に計上する（親仕様の `NOT_OWNED` を踏襲）。
- ルール ID: **BR-B03 同時に走るジョブは1利用者につき1件**
  - ルール: `pending` または `processing` のジョブを持つ利用者は、新しいジョブを起票できない。実行中である旨を返す。
  - 理由: 二重起票は同じ記事への二重課金と、進捗表示・完了メールの意味の破壊を招く。
- ルール ID: **BR-B04 1回の cron 起動で使う時間は現行の予算を踏襲する**
  - ルール: 1回の起動で使える時間は 730 秒（`maxDuration` 800秒 − 返却バッファ40秒 − LLM後バッファ30秒）。1件あたりの上限240秒・着手下限90秒（`CONTENT_ANNOTATION_BULK_SUMMARY_*`）は変更しない。
  - 例外: 予算切れ時はジョブを `pending` に戻し、未処理の位置（カーソル）を保存する。
- ルール ID: **BR-B05 並列数は3**
  - ルール: 1回の起動内では最大3件を同時に処理する。既存の `GscEvaluationService.EVALUATION_CONCURRENCY = 3`（`src/server/services/gscEvaluationService.ts:20`）と揃える。
  - 例外: Anthropic のレート制限（429）が観測された場合の調整は定数1箇所で行える形にする。
- ルール ID: **BR-B06 通知は全件完了後に1通だけ**
  - ルール: ジョブが `completed` になった時点で、**成功・失敗・スキップの件数と失敗理由の内訳**をメールで1通送る。文面は現在トーストで表示している内容（`src/lib/content-annotation-bulk-summary-display.ts` の `getBulkSummaryToastMessage`）と同じ情報とする。
  - 例外: `users.email` が未登録の利用者には送らない（送信スキップとしてログに残す）。cron の再実行で二重送信しないよう、送信済みを記録して冪等にする。
- ルール ID: **BR-B07 途中経過は画面に出す**
  - ルール: 実行中のジョブがある利用者が `/analytics` を開いたとき、「要約を実行中（処理済み N / 全 M 件）」を表示する。
  - 例外: 自動更新（ポーリング）はしない。ページを再読み込みしたときに最新化される。

## 4. 対象範囲と Non-goals

### 対象範囲

- 画面・操作: `/analytics` の「AIで要約」ボタンの挙動変更（同期実行 → ジョブ起票）、実行中の進捗表示（詳細は「6. 機能要件」の画面設計）
- サーバー: ジョブ起票用 Server Action、cron ルート、ジョブ処理サービス、完了メール送信
- データ: ジョブテーブル1つと、排他取得用 RPC 1つ（マイグレーション）
- 定期実行: 10分間隔の GitHub Actions ワークフロー1本

### Non-goals（今回の対象外）

- **キャンセル・停止導線**: 実行中ジョブを利用者が止める手段は作らない。クライアント判断（2026-09-04）で「不要」と合意済み。BR-B03 の1利用者1ジョブ制限により、暴走の上限は「1ジョブ＝最大1000件」に閉じる。
- **Claude Sonnet 5 への移行**: 判断を保留（クライアント指示: 一旦ステイ）。本仕様は現行の `claude-sonnet-4-6` のまま実装する。移行する場合も本仕様の構造は変わらないため、別途決定してよい。
- **進捗のリアルタイム更新**: WebSocket / SSE / 自動ポーリングは作らない。BR-B07 のとおり再読み込み時の表示にとどめる。
- **Message Batches API（50%割引）の利用**: 投入・ポーリング・結果回収が別実装になるため今回は採らない。コスト削減が要件化された場合に再検討する。
- **評価サイクル一括開始のバックグラウンド化**: LLM を使わず1回で1000件処理できるため不要。
- **停止機構（feature flag / 環境変数 / 専用設定テーブル）**: 要件・クライアント合意になく、既存手段（デプロイ巻き戻し、当該ボタンの非表示）で止められるため作らない（`CLAUDE.md` Core Rules / MVP 最優先）。
- **複数ジョブの同時実行・優先度制御**: BR-B03 により1利用者1ジョブ。利用者間の順序は claim 順（作成日時順）とし、優先度は持たない。
- **失敗した記事の自動リトライ**: 決定的失敗（本文サイズ超過など）は再実行しても同じ結果になるため、自動リトライはしない。利用者が再度実行する。

## 6. 機能要件

### 入力・出力・状態遷移

**入力（起票時）**: 現行 Server Action と同じ。`{ mode: 'ids', contentAnnotationIds: string[] }` または `{ mode: 'all', excludedIds?: string[] }`。

**ジョブの状態遷移**:

```text
（起票）→ pending
pending --[cron が claim]--> processing
processing --[時間予算切れ・未処理あり]--> pending（カーソル保存、次回続行）
processing --[全件処理済み]--> completed（完了メール送信）
processing --[想定外の例外 / 試行上限超過]--> failed（完了メール送信。件数は途中まで）
```

**出力（完了メール / 進捗表示に使う集計）**: 現行の `BulkSummaryResult` と同じ4区分（成功・失敗・スキップ・未実行）＋失敗理由の内訳（`failedByCode`）。表示文言の生成は既存の `getBulkSummaryToastMessage` を共用する。

### 画面設計

対象は `/analytics`（`app/analytics/AnalyticsClient.tsx`）。既存のチェック列・ツールバーは変更しない。

| 状態 | 表示 | 備考 |
| --- | --- | --- |
| 実行直後 | トースト「バックグラウンドで実行します。完了したらメールでお知らせします。」 | 既存の実行中トーストを置き換える |
| 実行中にページを開いた | ツールバー付近に「要約を実行中（処理済み N / 全 M 件）」 | BR-B07。自動更新なし |
| 実行中に再度押した | トースト「すでに要約を実行中です。完了までお待ちください。」 | BR-B03 |
| 完了後にページを開いた | 通常表示（実行中の表示は消える） | 結果はメールで確認する |

- 文言は `.agents/skills/growmate-ui-ux/ui-text.md` の辞書に追加し、`scripts/check-ui-text.sh` を通す。
- 「実行中」の表示中もチェック列と他のボタン（評価サイクル開始）は従来どおり使える。

### 権限

- ジョブ起票: `admin` / `paid` のみ（既存の `canWriteGa4` を流用。`trial` / `unavailable` は拒否）。UI だけでなく Server Action 側でも検証する。
- cron 実行: 既存 cron と同じ認証（`/api/cron/*` の共通ガード）。処理は Service Role で行い、**ジョブ行の `user_id` を明示的にスコープ**して他人の記事に触れないようにする。

## 8. 非機能要件

| 項目 | 要件 | 根拠・備考 |
| --- | --- | --- |
| 1回の cron 起動の実行時間 | `maxDuration = 800` 秒、時間予算 730 秒 | 既存 `CONTENT_ANNOTATION_BULK_SUMMARY_*` を踏襲 |
| 起動間隔 | 10分（`*/10 * * * *`） | 267件を約30〜45分で完了させるため |
| 1回の処理件数 | 並列3で 60〜70件（1件約30秒の実測ベース） | 実測値: 730秒 ÷ 24件 ≒ 30.4秒/件（直列時） |
| 1ジョブの上限 | 1000件（`MAX_BULK_SUMMARY_TARGETS`） | 既存の上限を踏襲。`db-max-rows = 1000`（`docs/context/db-row-limits-and-data-truncation.md`）とも整合 |
| LLM コスト | 1件あたり 4〜13円（`claude-sonnet-4-6`）。267件で約1,860円、1000件で約6,980円 | 入力 $3 / 出力 $15 per 1M。本文8,000字換算で1件約7円 |
| ジョブ行のサイズ | 対象ID配列は最大1000件（約16KB） | 配列で保持する。別テーブルへの正規化はしない（MVP） |
| 失敗時の再実行 | 予算切れは次回起動で続行。想定外の例外は試行回数上限（3回）で `failed` | 既存 `claim_gsc_suggestion_jobs` のスタック回収（15分）と同型 |
| 外部依存が壊れたときの表示 | 失敗理由コードごとの内訳を完了メールに出す（既存の文言生成を共用） | 停止機構は作らない（Non-goals 参照） |

### AI機能の追加観点

- プロンプト・モデル・出力形式は現行のまま変更しない（`content_annotation_ai_summary` テンプレート、`claude-sonnet-4-6`、`maxTokens: 8000`）。
- 本文サイズ上限（80,000文字）も変更しない。
- 1件あたりの LLM タイムアウトは残り時間から算出する現行ロジック（`computeSummaryItemBudgetMs`）を流用する。

## 11. トレードオフ判断

### 判断 1: 実行モデル（同期のまま並列化 vs バックグラウンド化）

- 選択: **バックグラウンド化（キュー + cron）**。
- 理由: 並列化だけでは1回60〜70件が上限で、267件なら依然4回の操作が必要。「1回で完了」という要件を満たさない。
- 代償: DB・cron・通知の実装が増える（同期の並列化のみなら1.5〜2人日、本方式は5.5人日）。

### 判断 2: 起動間隔（毎時 vs 10分）

- 選択: **10分間隔の新規ワークフロー**。
- 理由: 既存の毎時 cron に相乗りすると267件で約11時間かかり、「その日のうちに終わる」体験にならない。
- 代償: ワークフローが1本増える。空振り起動が1日約144回発生するが、public リポジトリのため課金されず、pending 0件なら即座に返る。

### 判断 3: 対象IDの保持方法（起票時に固定 vs 実行時に再解決）

- 選択: **起票時に解決して配列で保存**。
- 理由: 実行のたびに再解決すると、`updated_at` 降順の母集団が処理のたびに入れ替わり、同じ記事を処理し続けて前進しない（親仕様 R-006 と同じ罠）。
- 代償: 起票後に追加された記事は対象に入らない。利用者は次回の実行で拾う。

### 判断 4: 通知手段（画面のみ vs メール）

- 選択: **完了時にメール1通**（クライアント合意 2026-09-04）。
- 理由: 放置が前提の機能なので、画面に戻ってこない利用者に結果が届かない。
- 代償: `users.email` 未登録の利用者には届かない（AC-B06 でスキップと定義）。

### リスク
