## 1. 背景・目的・成功指標

### 背景・解決したい課題

- 現在、誰が、どの業務で困っているか:
  - `admin` / `paid` 利用者が `/wordpress-import` で WordPress 記事を一括インポートすると、`/analytics` のコンテンツが一気に増える。
  - 検索順位評価サイクルの開始は記事詳細（`/analytics/[annotationId]`）のボタンを **1件ずつ** 開いて行う必要がある（実ラベルは `app/analytics/[annotationId]/EvaluationSettings.tsx` の `{isUpdateMode ? '設定を変更' : '評価サイクルを開始'}`。~~`評価を開始`~~ **2026-08-26 に「評価サイクルを開始」へ改称**。同カードに「今すぐ評価を実行」が並ぶようになり即時実行と区別が付かなくなったため。`ga4-content-evaluation-spec.md` §10.8）。
  - クライアント運用では 100〜200 件規模の手動開始が発生し、負荷が高い（`client-vision` §1.9.3）。
- 放置した場合の影響:
  - インポート済みでも評価サイクルが未開始のまま残り、定期バッチが回らず改善提案が生まれない。
  - 「評価が始まっていない」状態の把握は既存の「評価未設定」フィルタで可能だが、開始操作そのものの手間は残る。

### 目的

- この開発で実現する状態:
  - コンテンツ一覧で複数記事を選び、一度の操作で **検索順位・コンテンツ評価サイクル**（統合後は `gsc_article_evaluations` 1行）を登録できる。
  - 登録後は既存の定期評価バッチ（GSC 計測・比較評価、GA4 コンテンツ評価）が自動で回り、利用者は記事詳細を1件ずつ開かなくてよい。
- 利用者・事業にとっての価値:
  - WordPress 由来の大量記事でも、評価サイクル開始のオペレーションコストを下げ、PDCA（検索順位の追跡・提案）に早く入れる。

### 成功指標

| 指標 | 現状 | 目標 | 測定方法 | 測定時期 |
| --- | --- | --- | --- | --- |
| 評価サイクル開始の操作回数 | 対象 N 件なら記事詳細を N 回開く | 「評価未設定」フィルタ下で、対象を全選択し 1 回の操作で N 件登録できる（上限あり） | 手動確認（一括開始の成功件数） | 受入時 |
| 未開始記事の発見〜開始までの導線 | フィルタは既存、開始は詳細のみ | チェック常時 →（推奨）「評価未設定」ON → 選択／全選択 → 「評価サイクルを開始」 | 画面確認 | 受入時 |

## 3. 業務要件と業務フロー

### 現状（As-Is）

```text
WordPress 一括インポート
  -> コンテンツ一覧に記事が増える
  -> 記事詳細（/analytics/[annotationId]）を1件開く
  -> 「評価サイクルを開始」で基準日・サイクル日数・実行時刻を指定して保存
  -> （必要なら）次の記事詳細へ… を繰り返す
  -> 登録済み記事は既存の定期バッチが初回計測→初回評価→以降を自動実行
```

### 導入後（To-Be）

```text
WordPress 一括インポート
  -> コンテンツ一覧で行チェック／全選択で対象を選ぶ（チェック列は GSC 連携済みなら常時表示）
  -> 「評価未設定」フィルタを ON にする（ボタン活性の条件。OFF のまま選択しても開始ボタンは出ない／disabled＋理由表示）
  -> 「評価サイクルを開始」を押す
  -> システムが基準日＝当日・cycle_days=30・evaluation_hour=12 でサイクル登録（GA4 コンテンツ評価も同周期で due になる）
  -> 成功件数を通知し、一覧を再取得する（「評価未設定」ON なら開始済みはフィルタ結果から消える）
  -> 以降は既存バッチが自動実行（当日の強制計測はしない）
```

### 業務ルール

- ルール ID: BR-01
- ルール: 一括開始の対象は、利用者がチェックした記事のうち **検索順位評価サイクルが未登録** の記事のみとする。UI 上は「評価未設定」フィルタ ON 時に開始ボタンを出すため、推奨導線では表示行＝未開始である。フィルタ OFF でもチェックは可能だが、開始ボタンは出さない（BR-06）。
- 例外: API に既登録 ID が混在した場合はスキップし、新規分のみ成功として件数を返す（全体失敗にはしない）。

- ルール ID: BR-02
- ルール: 一括開始は **サイクル登録のみ**とする。押下時点で順位計測・比較評価・改善提案生成は行わない。初回計測・初回評価のタイミングは既存仕様どおり（基準日 + 1サイクル / + 2サイクル）。
- 例外: なし。

- ルール ID: BR-03
- ルール: 基準日は一括開始実行日（日本時間の日付）固定。`cycle_days=30`、`evaluation_hour=12`（日本時間）固定。一覧一括では変更 UI を出さない。個別に変えたい場合は記事詳細の「設定を変更」を使う。
- 例外: なし。

- ルール ID: BR-04
- ルール: GSC 未連携（`gsc_credentials.property_uri` が無い）場合、一括開始 UI は **出さない**（既存記事詳細と同型: `OverviewTab` は `propertyUri` が無いとき `EvaluationSettings` を描画しない）。部分スキップ方式は採らない。サーバーでも未連携なら登録を拒否する。
- 判定手段: `property_uri` の取得は **「未連携（null）」と「取得失敗（DB エラー）」を区別できる経路**で行う。`SupabaseService.getGscCredentialByUserId`（`supabaseService.ts`）は DB エラー時も `null` を返すため、これ単独で判定してはならない。既存の `SupabaseService.resolveGscPropertyUri` が区別済みの実装（同ファイル。コメント「`getGscCredentialByUserId` は DB エラー時も null を返すため、障害を未連携と誤認しないようにする用途。」）であり、これを再利用する（現在 `private` のため public 化が必要。§5 に計上）。
- 例外（取得失敗）: DB エラーで `property_uri` を解決できない場合は **「未連携」として一括 UI を黙って消さない**。一覧側は利用者に分かる通知を出し、サーバー側は登録を拒否してエラーを返す。障害で機能が黙って消えることを許容しない。
- 例外の表示先（実装上の指定・必須）: `/analytics` には観測可能な挙動が正反対のエラー表示が2系統あるため、**どちらに載せるかを仕様として固定する**。
  - `app/analytics/AnalyticsClient.tsx` の `error` prop は `<ErrorAlert>` を出すだけでなく、`{!error ? (<AnalyticsTable ... />) : null}` のゲート条件になっており、**`AnalyticsTable` 自体が描画されずコンテンツ一覧が丸ごと消える**。
  - 同ファイルの `ga4Error` prop は通知ブロックを出すだけで、上記ゲート条件には入らず一覧は描画され続ける。
  - **`property_uri` の取得失敗は `ga4Error` と同型の非ブロッキング通知とする**。`app/analytics/page.tsx` から `error` とは**別の prop**（例: `gscCredentialError`）で渡し、`ga4Error` と同じ位置に通知を出す。**`error` prop および `AnalyticsTable` の描画ゲートには載せない。**
  - すなわち **`property_uri` の取得失敗でコンテンツ一覧の描画を止めてはならない。止まるのは本仕様の一括 UI だけである。**
  - **2026-08-27 訂正（共有チェック列の範囲）**: 非表示にするのは **「評価サイクルを開始」ボタンと評価側の理由表示**である。**チェック列・全選択は、AI 要約一括（`content-annotation-bulk-ai-summary-spec.md` BR-04 / FR-002 / AC-02）と同居する場合は常時表示とし、GSC の連携状態・取得失敗で隠さない。** 要約一括は WordPress 連携（同仕様 BR-02）が前提で GSC とは無関係のため、共有列に GSC 条件を掛けると GSC 未連携かつ WordPress 連携済みの `paid`/`admin` が要約一括を1件も実行できなくなり、承認済みの同仕様 AC を上書きしてしまう。PO 回答（§12 Q-003）の逐語は「GSC 未連携時の**ボタン**見た目」であり、チェック列まで含む判断ではない。**本仕様が単独で先行し要約一括が未実装の期間**は、共有列に載る操作が評価だけになるため従来どおりチェック列も非表示でよい（FR-005 / AC-05）。共有 UI 契約は `docs/plans/analytics-bulk-actions-impl-note.md` §3.1。
- 判定の限界（既知・受容）: 本判定は `property_uri` 行の有無のみを見る。**OAuth トークン失効や Google 側での連携解除は検知しない**（`gsc_credentials.property_uri` は失効後も残る）。詳細と根拠は「9. データ・外部連携」の外部連携と §12 R-005 を参照。既存の単記事開始も同じ判定であり、本仕様で判定を厳格化しない。

- ルール ID: BR-05
- ルール: 実行可能なロールは `admin` / `paid` のみ。**サーバー側（一括 Server Action）で必ず拒否する**。画面側は `/analytics` の既存ルートゲート（`proxy.ts` の `PAID_FEATURE_REQUIRED_PATHS`）で到達自体が `admin` / `paid` に限定されるため、一覧コンポーネントに新規のロール分岐は追加しない（§6 権限の実装方針）。
- 例外: `trial` / `unavailable` は対象外。

- ルール ID: BR-06
- ルール: **行チェック・全選択は GSC 連携済みなら常時表示**する（フィルタ OFF でも可）。**「評価サイクルを開始」ボタンは「評価未設定」フィルタ ON かつ選択≥1 のときだけ**活性表示する。フィルタ OFF で選択≥1 のときは開始ボタンを出さず、ツールバーに理由を1行出す（例: 「評価未設定フィルタを ON にすると開始できます」）。フィルタ OFF・未選択ではチェック列のみ（ツールバーの開始操作なし）。
- 例外: GSC 未連携／`property_uri` 取得失敗時は、**「評価サイクルを開始」ボタンと評価側の理由表示を非表示**にする（BR-04）。チェック列・全選択は、AI 要約一括が同居する場合は常時表示のまま隠さない。本仕様が単独で先行する期間はチェック列ごと非表示でよい（BR-04「2026-08-27 訂正」）。

- ルール ID: BR-07
- ルール: 「全選択」の対象は、**その時点で一覧に適用されている全フィルタ条件の AND 結果の全件**（ページを跨ぐ）とする。対象条件はカテゴリ名・未分類・改善提案あり・評価未設定で、一覧 RPC `get_filtered_content_annotations` の `filtered` CTE（`supabase/migrations/20260809100000_add_gsc_unstarted_evaluation_filter.sql`）が AND 結合する条件と一致させる。すなわち「評価未設定 ON かつカテゴリ X 選択中」の全選択は **評価未設定 ∧ カテゴリ X の全件**であり、一覧の総件数表示（`total_count`）と一致する。
- ルール（上限）: 1回の開始上限は **1000件**。根拠は WordPress 一括インポートの上限に揃えること。加えて、全選択の ID 解決（read）は PostgREST の `db-max-rows`（GrowMate では 1000）で無言クランプされるため、1リクエストで安全に解決できる件数の上限とも一致する。**`db-max-rows` は insert 側の制約ではない**（公式引用は §9 参照）ので、insert 件数の安全性は R-002 の件数突合で担保する。
- 例外: 超過時は登録せずエラーとし、件数を減らして再実行を促す。

## 4. 対象範囲と Non-goals

> **判断軸: GrowMate は MVP 開発を最優先とする**（`CLAUDE.md` Core Rules）。範囲に迷ったらこれを軸の1つにする。要件に無い機能は入れない。とくに安全機構（Kill Switch・feature flag・専用の設定テーブル・監視ダッシュボード・冗長化・リトライ基盤）は、**要件かクライアント合意に明示がある場合のみ**対象範囲に入れる。レビュー用チェックリストを満たすことは、要件を発明する根拠にならない。作らないと決めたものは下の Non-goals に理由付きで書く。

### 対象範囲

- 画面・操作: `/analytics` コンテンツ一覧への行選択（チェック・全選択）と一括「評価サイクルを開始」。詳細は「6. 機能要件」の「画面設計」。
- 画面へのデータ配線（新規）: `app/analytics/page.tsx` は現在 GSC の `property_uri` を一切取得していない（同ファイルに `gsc_credentials` / `propertyUri` の参照なし）。BR-04 / FR-005 の表示条件のため、`property_uri` の解決結果を `page.tsx` → `AnalyticsClient` → `AnalyticsTable` へ新規に渡す配線を対象範囲に含める。取得失敗（DB エラー）を伝える通知用の値も、**既存の `error` prop（一覧の描画ゲートを兼ねる）とは別の prop** で渡す（BR-04「例外の表示先」）。
- ロールの取得: **一覧側に `role` を新規配線しない**。`/analytics` は `proxy.ts` の `PAID_FEATURE_REQUIRED_PATHS` に含まれ、`hasPaidFeatureAccess`（`admin` / `paid` のみ true）を満たさないと `/unauthorized` へリダイレクトされるため、この画面に到達した時点で `admin` / `paid` に限定されている。UI 側の追加ロール分岐は要件を満たすうえで不要（MVP 最優先）。サーバー側の認可は別途必須（§6 権限）。
- API・外部連携: 新規の GSC API 呼び出しはしない。既存の評価登録（`gsc_article_evaluations` insert）を複数件向けに呼ぶ／まとめる。
- データ・DB: 既存テーブル `gsc_article_evaluations` への insert のみ。スキーマ変更なし。
- 権限・ロール: `admin` / `paid`。**一括経路のサーバー側で新規に強制する**（単記事の `registerEvaluation` は 2026-08-26 以降 `canWriteGa4` で強制済み。Route Handler のみ未強制。§6 権限を参照）。
- 運用・監視: 既存の検索順位評価バッチに変更なし。新規の監視ダッシュボード・Kill Switch は作らない。

### Non-goals（今回の対象外）

| 対象外 | 理由 | 将来検討する条件・時期 |
| --- | --- | --- |
| WordPress インポート時の評価サイクル自動開始 | 2026-08-05 定例で「外部取り込み時の自動処理は後回し」合意。本仕様は一覧一括で手動負荷を下げる代替 | クライアントが後回し合意を明示撤回し、件数上限・コストに合意したとき |
| 一括開始時の当日強制計測／即時評価実行 | 利用者は「開始後は自動で回ればよい」と確認済み。既存バッチに任せる | 開始直後にベースラインが欲しいという別要件が出たとき |
| 一覧一括での基準日・サイクル日数・実行時刻の編集 UI | MVP は固定値で足りる。詳細の既存 UI で変更可能 | 一括でも個別設定が必要というフィードバック時 |

### 入力・出力・状態遷移

- 入力値・形式・必須条件:
  - `contentAnnotationId[]`（1件以上、**最大1000**。サーバーでも上限を検証する）
  - または「現在の評価未設定条件の全件」をサーバー側で解決する指定（実装はどちらでもよいが、結果はフィルタ全件と一致すること）
  - `propertyUri` はサーバー側で利用者の GSC 連携から解決する（クライアント任意入力にしない）
  - 基準日・cycle・hour はサーバー側で固定付与（クライアント改ざんを信じない）
- 正常時の出力:
  - `{ success: true, data: { registeredCount, skippedAlreadyRegisteredCount, failedCount? } }` 相当
  - UI: トースト等で「N件の検索順位・コンテンツ評価サイクルを開始しました」（スキップがあれば併記）
  - 一覧を再取得し、評価未設定フィルタ適用中なら開始済み行は結果から消える
- エラー時の出力:
  - 未認証 / 権限なし / GSC 未連携 / 選択0件 / 1000件超 / サーバーエラーを区別可能なメッセージ（`ERROR_MESSAGES` に追加する場合は本仕様の対象）
- 状態と遷移条件:
  - 未登録 →（一括開始成功）→ `gsc_article_evaluations.status = 'active'`（既存単記事開始と同値）
  - 既登録 → 変更なし（スキップ）
- 冪等性・重複実行時の挙動:
  - 同一記事への再実行は insert せずスキップ（既存 `ARTICLE_ALREADY_REGISTERED` 相当を件数に集約）。部分成功を許容する。

  - 「全選択」は BR-07 の定義（適用中フィルタ条件の AND 結果の全件・ページ跨ぎ）である。

#### 誤読しやすい罠

- 「評価サイクルを開始」＝その場で順位比較結果や GA4 スコアが出る、ではない。登録後、初回 GSC 計測は約30日後・初回 GSC 評価は約60日後（既定値）。GA4 コンテンツ評価も同じサイクル日数で due 判定される（初回は軽量パスから）。
- チェック列は常時だが、開始できるのは「評価未設定」ON のときだけ。フィルタ OFF で選んでも開始ボタンは出ず、理由表示が出る（「選んだのに何も起きない」を防ぐ）。
- 「評価未設定」フィルタは **統合後の評価サイクル未登録** を指す（`gsc_article_evaluations` に active 行が無い記事）。2026-08-26 の GA4 サイクル統合で GSC/GA4 は1本化され、GA4 専用フィルタは撤去済み（`CategoryFilter.tsx` の状態フィルタは「評価未設定」と「改善提案あり」の2つ。見出しは「状態でフィルター」）。本一括開始は **`gsc_article_evaluations` への insert のみ**で、追加の GA4 専用操作は不要だが、**副作用として GA4 コンテンツ評価も同周期で開始される**（§4 Non-goals の旧「GSC のみ」記述は失効済み）。
- 開始成功の確認は、専用ステータス新設ではなく **「評価未設定」フィルタ結果から行が消えること**（同フィルタ ON 時）と件数トーストで行う。
- フィルタ OFF で全選択すると、未開始以外も含む母集団が選ばれる。サーバーは既登録をスキップするが、開始ボタン自体は「評価未設定」ON が無いと出ないため、通常はこの経路で登録は走らない。

#### 認可の実装方針（既存の事実と、今回新規に作るもの）

既存コードの事実（2026-08-27 時点）:

- 単記事登録 `registerEvaluation`（`src/server/actions/gscDashboard.actions.ts`）は **`canWriteGa4` で role を強制している**（`admin` / `paid` のみ）。GA4 サイクル統合後、GSC 評価登録も同 Action 経由のため、命名は `canWriteGa4` のままだが実質は統合評価サイクルの write 権限である。
- `app/api/gsc/evaluations/register/route.ts`（POST）は **依然として `authMiddleware` の認証のみ**で role チェックが無い（§4 Non-goals 据え置き）。
- `/analytics` は `PAID_FEATURE_REQUIRED_PATHS` に含まれ、`/analytics/[annotationId]` もプレフィックスマッチで保護される。

今回の方針:

1. 一括開始のサーバー側認可は **新規に強制する**（一括 Action は未実装のため）。`getAuthUserId` が返す `role` を **`registerEvaluation` と同じ `canWriteGa4({ role })`** で判定する。別モジュール `canWriteGsc` の新設は **行わない**（2026-08-23 spec-review 時点の `gsc-permissions.ts` 案は、GA4 統合後の `registerEvaluation` 実態に合わせて **2026-08-27 に撤回**）。
2. role チェックは **一括エントリポイント（`registerEvaluationsBulk`）側に置く**。既存 `registerEvaluation` と共通化する場合も、共通の登録コアには入れない（Route Handler の据え置き方針は §4 Non-goals 参照）。
3. UI 側は追加のロール分岐を作らない。`/analytics` 自体が `proxy.ts` で `admin`/`paid` に限定されているため、この画面に到達した時点で条件を満たす（§4 対象範囲）。

#### 連携ライフサイクル（トークン失効時の扱い）

BR-04 の判定は `gsc_credentials.property_uri` の有無のみであり、**Google 側での認可失効・連携解除は検知しない**（`property_uri` 行は失効後も残る）。この扱いを選ぶ根拠として、失効が正常系として起こりうることを公式ドキュメントで確認した。

- 参照 URL: `https://developers.google.com/identity/protocols/oauth2`
- 確認日: 2026-08-23
- 公式ページ本文の verbatim 引用:
  - "You must write your code to anticipate the possibility that a granted refresh token might no longer work."
  - "The user has revoked your app's access."
  - "The refresh token has not been used for six months."

引用から導いた解釈（引用とは分けて記載）: refresh token は正常系として無効化されうるので、`property_uri` の存在は「今 GSC を呼べる」ことを保証しない。したがって失効中でも本機能の一括 UI は表示され、最大1000件の登録も成功しうる。ただし **本仕様では検知を追加しない**（既存の単記事開始と同じ判定に揃える。§4 Non-goals）。実際に失敗するのは登録から約1サイクル後の既存バッチ側であり、結果は既存の `import_failed` 表示に現れる（§12 R-005）。GSC 連携全体の失効検知（`needsReauth` の常時反映）は本仕様の責務外とする。

## 付録 A. 設計メモ（実装者向け・要件ではない）

実装時の指針。要件の変更権限は持たない。

- 新規 Server Action 案: `registerEvaluationsBulk`（`gscDashboard.actions.ts` または専用 actions）。内部で既存登録ロジックをループ／共通関数化。共通化する場合は `app/api/gsc/evaluations/register/route.ts` も同じコアに寄せられる（必須ではない。§10）。role チェックは共通コアではなく一括エントリポイント側に置く（§6 権限）。
- 認可: 一括エントリポイントで **`canWriteGa4({ role })`** を `registerEvaluation` と同型に適用する。
- 1リクエスト上限: **1000**。超過は 400。取得件数と `total_count` の突合必須（`items.length >= limit` での検知は不可。`db-max-rows` でクランプされると `length < limit` になる）。
- 全選択の実装案: (a) クライアントが適用中フィルタ条件でページングして ID を集め送信、(b) サーバーが同条件の全件を解決して登録。どちらでも AC-02 / AC-02b / AC-11 を満たせばよい。母集団の定義は BR-07。
- 基準日: JST の `YYYY-MM-DD`。`formatJstDateISO`（`src/lib/date-utils.ts`）を使う（R-004）。
- UI 主な変更ファイル: `src/components/AnalyticsTable.tsx` / `CategoryFilter.tsx` / `app/analytics/AnalyticsClient.tsx`、および `property_uri` を渡すための `app/analytics/page.tsx`。チェック列の表示条件は、AI 要約一括が同居する場合は**常時**（`propertyUri` を条件に入れない。BR-04「2026-08-27 訂正」）、本仕様が単独で先行する期間のみ **`propertyUri`**。開始ボタンの表示条件は **`hasUnstartedGscEvaluation && propertyUri && selectedCount >= 1`**（`canWrite` は条件に入れない。`/analytics` は `proxy.ts` で `admin`/`paid` に限定済み。§4 / §6）。フィルタ OFF・選択ありは理由1行。
- 取得失敗の通知を足す位置: `AnalyticsClient.tsx` の `ga4Error` ブロックと同じ位置。`error` の分岐（`<ErrorAlert>` ＋ `{!error ? (<AnalyticsTable ... />) : null}`）には**絶対に載せない**。載せると一時的な DB エラーでコンテンツ一覧が丸ごと消える（BR-04「例外の表示先」）。
- 「選択 N / 対象総数 M」を出す場合: `total` は `app/analytics/page.tsx` から `AnalyticsClient` までは渡っているが `AnalyticsTable` には渡っていない（`Props` に `total` が無い）。plumbing を1本足す必要がある。要件ではない（§6 項目定義）。
- GSC 未連携の既存正本: `app/analytics/[annotationId]/components/OverviewTab.tsx`（移設後）の `{detail.credential?.propertyUri && (<EvaluationSettings .../>)}`。
- README 更新の予告: 「主な機能」に一覧一括開始が載る可能性がある。最終判断は実装時の `readme_sync`。
