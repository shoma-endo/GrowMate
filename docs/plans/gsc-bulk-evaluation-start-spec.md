## 1. 背景・目的・成功指標

### 背景・解決したい課題

- 現在、誰が、どの業務で困っているか:
  - `admin` / `paid` 利用者が `/wordpress-import` で WordPress 記事を一括インポートすると、`/analytics` のコンテンツが一気に増える。
  - 検索順位評価サイクルの開始は記事詳細（`/analytics/[annotationId]`）のボタンを **1件ずつ** 開いて行う必要がある（実ラベルは `app/analytics/[annotationId]/EvaluationSettings.tsx` の `{isUpdateMode ? '設定を変更' : '評価サイクルを開始'}`。~~`評価を開始`~~ **2026-08-26 に「評価サイクルを開始」へ改称**。同カードに「今すぐ評価を実行」が並ぶようになり即時実行と区別が付かなくなったため。`ga4-content-evaluation-spec.md` §10.8）。
  - クライアント運用では 100〜200 件規模の手動開始が発生し、負荷が高い（`client-vision` §1.9.3）。
- 放置した場合の影響:
  - インポート済みでも評価サイクルが未開始のまま残り、定期バッチが回らず改善提案が生まれない。
  - 「評価が始まっていない」状態の把握は既存の「評価未設定」フィルタで可能だが、開始操作そのものの手間は残る。

### 目的

- この開発で実現する状態:
  - コンテンツ一覧で複数記事を選び、一度の操作で **検索順位・コンテンツ評価サイクル**（統合後は `gsc_article_evaluations` 1行）を登録できる。
  - 登録後は既存の定期評価バッチ（GSC 計測・比較評価、GA4 コンテンツ評価）が自動で回り、利用者は記事詳細を1件ずつ開かなくてよい。
- 利用者・事業にとっての価値:
  - WordPress 由来の大量記事でも、評価サイクル開始のオペレーションコストを下げ、PDCA（検索順位の追跡・提案）に早く入れる。

### 成功指標

| 指標 | 現状 | 目標 | 測定方法 | 測定時期 |
| --- | --- | --- | --- | --- |
| 評価サイクル開始の操作回数 | 対象 N 件なら記事詳細を N 回開く | 全選択（BR-07 の母集団）で 1 回の操作でき、未登録 N 件が登録される（上限あり） | 手動確認（一括開始の成功件数） | 受入時 |

### 主な利用シナリオ

1. **誰が**、**どの状況で**、**何をしたいか**:
   - `paid` 利用者が WordPress 一括インポート直後、`/analytics` で「評価未設定」フィルタを ON にし（**推奨導線であり、開始ボタンの条件ではない**。2026-08-29 Q-007 でゲート撤廃。BR-06）、全選択して「評価サイクルを開始」したい。選ばれるのは絞り込みに関係なく全記事で（BR-07）、登録されるのはそのうち未登録分だけである。
2. **誰が**、**どの結果を確認するか**:
   - 同じ利用者が、成功件数の通知と、**評価未設定フィルタの一覧から対象が消えること**（再取得後）を確認する。以降の計測・評価は既存バッチに任せる。

## 3. 業務要件と業務フロー

### 現状（As-Is）

```text
WordPress 一括インポート
  -> コンテンツ一覧に記事が増える
  -> 記事詳細（/analytics/[annotationId]）を1件開く
  -> 「評価サイクルを開始」で基準日・サイクル日数・実行時刻を指定して保存
  -> （必要なら）次の記事詳細へ… を繰り返す
  -> 登録済み記事は既存の定期バッチが初回計測→初回評価→以降を自動実行
```

### 導入後（To-Be）

```text
WordPress 一括インポート
  -> コンテンツ一覧で行チェック／全選択で対象を選ぶ（チェック列は GSC 連携済みなら常時表示）
  -> （任意）「評価未設定」フィルタを ON にして未設定だけを一覧に出す（**開始ボタンの条件ではない**。2026-08-29 Q-007 でゲート撤廃）
  -> 「評価サイクルを開始」を押す
  -> システムが基準日＝当日・cycle_days=30・evaluation_hour=12 でサイクル登録（GA4 コンテンツ評価も同周期で due になる）
  -> 成功件数を通知し、一覧を再取得する（「評価未設定」ON なら開始済みはフィルタ結果から消える）
  -> 以降は既存バッチが自動実行（当日の強制計測はしない）
```

### 業務ルール

- ルール ID: BR-01
- ルール: 一括開始の対象は、利用者がチェックした記事のうち **検索順位評価サイクルが未登録** の記事のみとする。**開始ボタンはフィルタに依存しない**（フィルタ OFF・選択≥1 でも開始できる。2026-08-29 Q-007 でゲート撤廃。BR-06）。「評価未設定」フィルタ ON は未設定記事を見つけやすくする**推奨導線**にすぎず、選択された記事に既登録が混ざるのは正常である（下の例外・BR-07「開始対象」）。
- 判定手段: 「未登録」の判定は **`gsc_article_evaluations` に当該 `content_annotation_id` の行が存在しないこと**とする。**`status` は見ない**（`active` に限定しない）。既存 `registerEvaluation` の重複チェックが `status` 条件を持たない（`src/server/actions/gscDashboard.actions.ts:453-459`）ためであり、一覧の「評価未設定」フィルタの実装（行の有無のみ）とも一致する（§6「誤読しやすい罠」）。`active` 行の有無で判定すると `paused` / `completed` の記事へ二重 insert を試みて既存経路と挙動が食い違う。
- 実装契約（一括時の手段。**1件ずつ往復しない**）: 既登録の判定は、対象 ID 群に対する `gsc_article_evaluations` の **事前 select を1回**（`user_id` + `content_annotation_id` の `in` 条件。既存 `registerEvaluation` `:453-459` と同じ判定条件）で行い、未登録分のみを**まとめて insert** する。1件ずつ select → insert を繰り返すと1000件で往復2000回になり §8 性能の「完了は数十秒以内」を満たせない。**競合により `unique (user_id, content_annotation_id)`（`supabase/migrations/20251123090000_create_gsc_metrics_and_evaluations.sql:57`）に違反した行は `skippedAlreadyRegisteredCount` に計上**し、`failedCount` には含めない（利用者から見た結果は事前 select でスキップした場合と同じであるため）。
- 例外: API に既登録 ID が混在した場合はスキップし、新規分のみ成功として件数を返す（全体失敗にはしない）。

- ルール ID: BR-02
- ルール: 一括開始は **サイクル登録のみ**とする。押下時点で順位計測・比較評価・改善提案生成は行わない。初回計測・初回評価のタイミングは既存仕様どおり（基準日 + 1サイクル / + 2サイクル）。
- 例外: なし。

- ルール ID: BR-03
- ルール: 基準日は一括開始実行日（日本時間の日付）固定。`cycle_days=30`、`evaluation_hour=12`（日本時間）固定。一覧一括では変更 UI を出さない。個別に変えたい場合は記事詳細の「設定を変更」を使う。
- 例外: なし。

- ルール ID: BR-04
- ルール: GSC 未連携（`gsc_credentials.property_uri` が無い）場合、一括開始 UI は **出さない**（既存記事詳細と同型: `OverviewTab` は `propertyUri` が無いとき `EvaluationSettings` を描画しない）。部分スキップ方式は採らない。サーバーでも未連携なら登録を拒否する。
- 判定手段: `property_uri` の取得は **「未連携（null）」と「取得失敗（DB エラー）」を区別できる経路**で行う。`SupabaseService.getGscCredentialByUserId`（`supabaseService.ts`）は DB エラー時も `null` を返すため、これ単独で判定してはならない。既存の `SupabaseService.resolveGscPropertyUri` が区別済みの実装（同ファイル。コメント「`getGscCredentialByUserId` は DB エラー時も null を返すため、障害を未連携と誤認しないようにする用途。」）であり、これを再利用する（現在 `private` のため public 化が必要。§5 に計上）。
- 例外（取得失敗）: DB エラーで `property_uri` を解決できない場合は **「未連携」として一括 UI を黙って消さない**。一覧側は利用者に分かる通知を出し、サーバー側は登録を拒否してエラーを返す。障害で機能が黙って消えることを許容しない。
- 例外の表示先（実装上の指定・必須）: `/analytics` には観測可能な挙動が正反対のエラー表示が2系統あるため、**どちらに載せるかを仕様として固定する**。
  - `app/analytics/AnalyticsClient.tsx` の `error` prop は `<ErrorAlert>` を出すだけでなく、`{!error ? (<AnalyticsTable ... />) : null}` のゲート条件になっており、**`AnalyticsTable` 自体が描画されずコンテンツ一覧が丸ごと消える**。
  - 同ファイルの `ga4Error` prop は通知ブロックを出すだけで、上記ゲート条件には入らず一覧は描画され続ける。
  - **`property_uri` の取得失敗は `ga4Error` と同型の非ブロッキング通知とする**。`app/analytics/page.tsx` から `error` とは**別の prop**（例: `gscCredentialError`）で渡し、`ga4Error` と同じ位置に通知を出す。**`error` prop および `AnalyticsTable` の描画ゲートには載せない。**
  - すなわち **`property_uri` の取得失敗でコンテンツ一覧の描画を止めてはならない。止まるのは本仕様の一括 UI だけである。**
  - **2026-08-27 訂正（共有チェック列の範囲）**: 非表示にするのは **「評価サイクルを開始」ボタンと評価側の理由表示**である。**チェック列・全選択は、AI 要約一括（`content-annotation-bulk-ai-summary-spec.md` BR-04 / FR-002 / AC-02）と同居する場合は常時表示とし、GSC の連携状態・取得失敗で隠さない。** 要約一括は WordPress 連携（同仕様 BR-02）が前提で GSC とは無関係のため、共有列に GSC 条件を掛けると GSC 未連携かつ WordPress 連携済みの `paid`/`admin` が要約一括を1件も実行できなくなり、承認済みの同仕様 AC を上書きしてしまう。PO 回答（§12 Q-003）の逐語は「GSC 未連携時の**ボタン**見た目」であり、チェック列まで含む判断ではない。**本仕様が単独で先行し要約一括が未実装の期間**は、共有列に載る操作が評価だけになるため従来どおりチェック列も非表示でよい（FR-005 / AC-05）。共有 UI 契約は `docs/plans/analytics-bulk-actions-impl-note.md` §3.1。
- 判定の限界（既知・受容）: 本判定は `property_uri` 行の有無のみを見る。**OAuth トークン失効や Google 側での連携解除は検知しない**（`gsc_credentials.property_uri` は失効後も残る）。詳細と根拠は「9. データ・外部連携」の外部連携と §12 R-005 を参照。既存の単記事開始も同じ判定であり、本仕様で判定を厳格化しない。

- ルール ID: BR-05
- ルール: 実行可能なロールは `admin` / `paid` のみ。**サーバー側（一括 Server Action）で必ず拒否する**。画面側は `/analytics` の既存ルートゲート（`proxy.ts` の `PAID_FEATURE_REQUIRED_PATHS`）で到達自体が `admin` / `paid` に限定されるため、一覧コンポーネントに新規のロール分岐は追加しない（§6 権限の実装方針）。
- 例外: `trial` / `unavailable` は対象外。

- ルール ID: BR-06
- ルール: **行チェック・全選択は GSC 連携済みなら常時表示**する（フィルタ OFF でも可）。**「評価サイクルを開始」ボタンは GSC 連携済みかつ選択≥1 のときだけ**活性表示する。**フィルタの ON/OFF は条件に入れない**（2026-08-29 Q-007 回答）。フィルタ OFF・選択≥1 でも開始できるため、評価側の理由表示は出さない。未選択ではチェック列のみ（ツールバーの開始操作なし）。
- ルール（ゲートを外した理由）: 当初のゲートは「未設定以外を誤って一括登録しない」ことを狙っていたが、2026-08-29 に全選択の母集団をフィルタ非依存の全記事へ変更した（BR-07）ため、フィルタ ON でも母集団に既登録記事が入る。誤登録を防ぐ役目は **BR-01 の既登録スキップ**が担っており、ゲートは同じ保護を二重に持たない。
- ルール（要約側との非対称。実装メモ §3.2 に追随を要する）: AI 要約一括の「AIで要約」は **「未要約」フィルタ ON かつ選択≥1** のゲートを維持する（要約親 BR-04）。**誤実行のコストが非対称**なため揃えない。評価側の誤実行は `gsc_article_evaluations` への insert で、既登録スキップにより実質無害。要約側の誤実行は記事ごとの LLM 呼び出し（要約親 BR-03。1件あたり最長180秒）でコストと時間を消費し、取り消せない。
- 例外: GSC 未連携／`property_uri` 取得失敗時は、**「評価サイクルを開始」ボタンを非表示**にする（BR-04）。チェック列・全選択は、AI 要約一括が同居する場合は常時表示のまま隠さない。本仕様が単独で先行する期間はチェック列ごと非表示でよい（BR-04「2026-08-27 訂正」）。

- ルール ID: BR-07
- ルール（母集団の定義。**本仕様で「全選択の母集団」を定義するのはここだけ**。他節は再掲せず本ルールを参照する）: 「全選択」の対象は **利用者が所有する全記事**（`content_annotations` の `user_id` が一致する行すべて）とする。**表示中のページにも、一覧に適用中のフィルタ（カテゴリ名・未分類・改善提案あり・評価未設定）にも依存しない。** すなわち「評価未設定 ON かつカテゴリ X 選択中」でも全選択の母集団は**全記事**であり、絞り込み後の件数を示す一覧の総件数表示（`total_count`）とは**一致しない**。**ID の解決方式は下の「ID 解決の方式」ルールで定義する**（本ルールは母集団の範囲だけを定める）。
- ルール（本定義の適用範囲。**2026-08-29 Q-008 で確定**）: 本定義は `/analytics` の行チェック・全選択が **AI 要約一括と共有する1本**（`docs/plans/analytics-bulk-actions-impl-note.md` §3.1）**そのもの**に適用される。すなわち要約一括の全選択も同じ母集団（フィルタ非依存の全記事）になる。要約親 `content-annotation-bulk-ai-summary-spec.md` BR-05 の旧定義（全フィルタ条件の AND 結果の全件・件数は `total_count` と一致）は本定義へ追従改訂する。**母集団の正本は本ルール（BR-07）1つとし、要約親は本ルールを参照する。**
- ルール（開始対象）: 母集団に既登録記事が混ざるのは正常である。サーバーは BR-01 のとおり未登録のみを登録し、既登録はスキップして成功件数に混ぜない。
- ルール（上限）: 1回の開始上限は **1000件**。根拠は **WordPress 一括インポートの上限（1000）に揃えること、これ1本**とする。母集団がフィルタ非依存の全記事になったため絞り込みでは上限を下回らせられないが、超過時は下の例外のとおり**丸める**ので全選択が使えなくなることはない。
- **根拠に`しない`もの（2026-08-29 訂正）**: PostgREST の `db-max-rows`（GrowMate では 1000）を 1000 の根拠にしない。公式 verbatim は「fetch する行数」の上限であり insert 側の制約でもなければ、本機能の ID 解決経路にも当たらない（公式引用は §9 / §16 参照）。実測（2026-08-29）: 一覧 RPC は `returns table(items jsonb, total_count bigint)` の **jsonb 集約1行返し**（`20260818000300_…sql:16` `:89-90`）で `db-max-rows` に当たらない。むしろ `p_per_page` が `greatest(1, least(100, …))` で **1ページ最大100件にクランプ**され（同 `:22`）、呼び出し側 `src/server/services/analyticsContentService.ts:18` の `MAX_PER_PAGE = 100`・`:26` の同型クランプも同じ上限である。**したがって一覧 RPC を1回呼ぶだけでは最大100件しか解決できない。**
- ルール（ID 解決の方式。**サーバー側で `content_annotations` を直接1回クエリする**）: 全選択のとき、**クライアントは ID 配列も画面の絞り込み状態も送らない**。サーバーが `content_annotations` を **`user_id` 一致・`updated_at` 降順（nulls last）・`limit 1000`・件数は `count: 'exact'`** で1回引き、ID と総件数を同時に得る。取得 ID 数と総件数を突合し（総件数 ≤ 1000 なら全件一致、超過なら 1000 件）、想定と食い違えば開始せずエラーとする（R-002）。insert 件数の安全性はこの突合で担保する。
  - **既存の一覧 RPC `get_filtered_content_annotations` は母集団解決に使わない。** `p_per_page` が `greatest(1, least(100, …))` で **1回の呼び出しにつき最大100件**にクランプされる（`20260818000300_…sql:22`）ため、1000件を1回で解決できない。
  - **新規 SQL 関数（jsonb 集約1行返し）も作らない。** 直接クエリで同じ母集団を解決できるので migration を増やさない（MVP 最優先）。
  - **直接クエリと「一覧 RPC をフィルタ条件なしで呼んだ結果」は同一集合である**（2026-08-29 実測）。RPC の `filtered` CTE の基底は `from public.content_annotations ca ... where ca.user_id = p_user_id::text`（`20260818000300_…sql:33-41`）で、カテゴリ・未分類・改善提案あり・評価未設定の各述語はいずれも**未指定時に全行を通す**分岐を持つ。並び順も RPC の `order by f.updated_at desc nulls last`（同 `:72`）と一致させる。
  - **`db-max-rows` との結合（重要）**: 直接クエリは PostgREST 経由なので `db-max-rows`（GrowMate では 1000）の行数上限に当たる。**本仕様の上限1000と一致しているため `limit 1000` は無言の打ち切りにならない**が、両者は独立に決まった値である。**上限（BR-07）を 1000 より大きくするときは、`db-max-rows` の引き上げか解決方式の変更を同時に行うこと。**片方だけ変えると、上限未満の件数しか解決できないまま突合が通ってしまう。件数は `count: 'exact'` で取るため行数上限の影響を受けない。
  - **クライアントによるページング収集（`p_per_page ≤ 100` の繰り返し）は採らない。** 理由は3つ。(1) 一覧 RPC は `authenticated` から `revoke execute` 済みで `service_role` 限定（`20260818000300_…sql:93-94`）であり、クライアントから叩ける経路は存在しない（唯一の本番呼び出し元は Server Component の `app/analytics/page.tsx:142` 経由 `analyticsContentService.ts:45`）。実現には未計上の新規クライアント向けエンドポイント新設が要り MVP を逸脱する。(2) 行チェック・全選択は AI 要約一括と**1本を共有**し、要約親 §6 入力が既にサーバー側解決を唯一の実装として確定している（`content-annotation-bulk-ai-summary-spec.md`）。同じコントロールに2方式は併存しえない。(3) 下記の並び順のタイブレーク不在により、複数回のページングでは重複・欠落が起こりうる。
  - **並び順にタイブレーク列が無い**: 現行 RPC の順序は `row_number() over (order by f.updated_at desc nulls last)`（`20260818000300_…sql:72`）のみで、`updated_at` が同値の行の相対順序は保証されない。WordPress 一括インポート直後は `updated_at` が近接するため現実的な問題になる。**解決は1回のクエリで完結させ、複数回のページングで窓を組み立てないこと。**
- ルール（**全選択後の個別解除**。2026-08-31 追加）: 全選択したまま表示中の行のチェックを外したときは、**全選択を解除せず、その記事だけを母集団から除外**する。除外された記事の行だけチェックが外れ、他の行の選択は残る。ヘッダの全選択チェックは除外が1件以上あれば **indeterminate** を示す。
  - **理由（全選択を解除してはいけない）**: 母集団の ID はクライアントに無く（上の「ID 解決の方式」でサーバーが解決する）、表示中のページの ID しか持っていない。全選択を解除して選び直す実装にすると、**表示中以外の記事の選択を復元できず、1件外しただけで全解除になる**。
  - **クライアント→サーバーの受け渡し**: 全選択の入力に**除外 ID の配列を添える**（`{ mode: 'all', excludedIds: [...] }`）。サーバーは母集団を解決したあと、除外 ID を差し引いてから登録する。**R-002 の件数突合は除外を差し引く前の母集団に対して行う**（除外は利用者の意思であり、取得失敗と区別する）。
  - **ヘッダの全選択を押し直したときは除外を捨てて全選択に戻す**（indeterminate から checked への遷移）。フィルタ・ページ送りで一覧の中身が入れ替わったときは、選択と同様に除外も破棄する（実装メモ §3.1 の選択スコープ）。
  - **全件を除外した場合**は選択件数が 0 になり、開始ボタンは出ない（BR-06 の「選択≥1」）。サーバーへ届いた場合も対象 0 件としてエラーを返す。
  - **上限1000件と併用したときの表示**: 母集団が1000件を超えるとき、除外された記事が丸めた窓（`updated_at` 降順の先頭1000件）の中にあるとは限らない。この場合の選択件数表示は丸め表記「1000 / 全 M 件」のままとし、実際に登録される件数はサーバーが ID で突き合わせて確定する。**MVP ではこの数件のズレを受容する**（`client-vision` §1.9.3 の運用規模は100〜200件で、1000件超は現実の運用に現れない）。
- ルール（母集団の件数 M の取得失敗。**0件と同じ扱いにしない**）: 選択件数表示の M と全選択の可否は、フィルタ非依存の全記事件数（`countAllAnnotations`）に依存する。この取得が失敗したときは **`0` に丸めず「取得できていない」状態として画面へ伝える**。0 に丸めると、一覧本体だけ取得できた一時障害時に「表示行のチェックは ON なのに開始ボタンが出ない」矛盾した状態になる。失敗時は **全選択（ヘッダのチェック）だけを無効化**し、行チェックによる選択・開始は従来どおり使える。BR-04 の例外表示先の指定に従い、**一覧の描画ゲート（`error` prop）には載せず**、`ga4Error` と同型の非ブロッキング通知で再読み込みを促す。
- 例外（**2026-08-29 Q-006 で確定。要約親 BR-05 例外と同型**）: 全選択の母集団が 1000 件を超える場合は、**一覧と同じ並び順（現行 RPC の `updated_at` 降順）の先頭1000件に丸める**。エラーにはしない。丸めたことは選択件数表示で **「1000 / 全 M 件」** と明示し、無言の打ち切りにしない（`docs/context/db-row-limits-and-data-truncation.md` 最重要メッセージ）。
- ルール（丸めた残りの扱い。**再実行では進まない**）: 本機能の登録は `gsc_article_evaluations` への insert のみで、**`content_annotations` を一切更新しない**（`src/server/actions/gscDashboard.actions.ts:436-442` は select のみ、`:468-481` が insert）。`content_annotations` に `updated_at` の自動更新トリガは存在しない（同テーブルの唯一のトリガは `20251105090000_add_chat_session_search.sql:126-129` で、別テーブル `chat_sessions` の検索ベクタを更新するだけ）。したがって**再実行しても `updated_at` 降順の先頭1000件という窓は動かず、2回目以降の `registeredCount` は 0 になる**。1001件目以降を開始するには、**行チェック（ページ送り）で個別に選択する**。この制約は受容する（§12 R-007。`client-vision` §1.9.3 の運用規模は100〜200件で、1000件超は現実の運用に現れない）。
- 例外（サーバー側の上限検証は残す）: 一括 Server Action は **1001 件以上の入力を実行せずエラー**にする。UI は上記の丸めにより 1000 件を超える入力を送らないため、この経路は API 直叩き対策として残す（要約親 BR-06 と同型）。

### 入力・出力・状態遷移

- 入力値・形式・必須条件:
  - `contentAnnotationId[]`（1件以上、**最大1000**。サーバーでも上限を検証する）
  - または「全選択」の指定（**ID 配列を送らず、画面の絞り込み状態も送らない**）。サーバーは **BR-07 が定義する母集団（フィルタ条件なしの全記事）** を解決し、1000件を超える場合は `updated_at` 降順の先頭1000件へ丸める。取得件数は**フィルタ無しの `total_count`** と突合する（R-002）
  - `propertyUri` はサーバー側で利用者の GSC 連携から解決する（クライアント任意入力にしない）
  - 基準日・cycle・hour はサーバー側で固定付与（クライアント改ざんを信じない）
- 正常時の出力:
  - `{ success: true, data: { registeredCount, skippedAlreadyRegisteredCount, failedCount? } }` 相当
  - UI: トースト等で「N件の検索順位・コンテンツ評価サイクルを開始しました」（スキップがあれば併記）
  - 一覧を再取得し、評価未設定フィルタ適用中なら開始済み行は結果から消える
- エラー時の出力:
  - 未認証 / 権限なし / GSC 未連携 / 選択0件 / 1000件超 / サーバーエラーを区別可能なメッセージ（`ERROR_MESSAGES` に追加する場合は本仕様の対象）
- 状態と遷移条件:
  - 未登録 →（一括開始成功）→ `gsc_article_evaluations.status = 'active'`（既存単記事開始と同値）
  - 既登録 → 変更なし（スキップ）
- 冪等性・重複実行時の挙動:
  - 同一記事への再実行は insert せずスキップ（既存 `ARTICLE_ALREADY_REGISTERED` 相当を件数に集約）。部分成功を許容する。

##### `/analytics`

- 概要: GSC 連携済みの一覧で記事を選択し、検索順位・コンテンツ評価サイクルを複数件まとめて開始できる。フィルタの状態には依存しない。

  │ [✓全] | 操作（チャット/編集/詳細/削除） | 主軸kw | kw（参考） | … │
  │ [ ]   | …                              | …     | …          | … │
  │ [✓]   | …                              | …     | …          | … │
  └──────────────────────────────────────────────────────────────────┘

#### 誤読しやすい罠

- 「評価サイクルを開始」＝その場で順位比較結果や GA4 スコアが出る、ではない。登録後、初回 GSC 計測は約30日後・初回 GSC 評価は約60日後（既定値）。GA4 コンテンツ評価も同じサイクル日数で due 判定される（初回は軽量パスから）。
- **開始ボタンはフィルタに連動しない**（2026-08-29 Q-007 でゲート撤廃）。チェック列も開始ボタンも、GSC 連携済みで選択≥1 なら「評価未設定」の ON/OFF に関わらず出る。評価側の理由表示は存在しない。**AI 要約一括の「AIで要約」だけは「未要約」ON のゲートを維持する**ので、同じ選択状態でも評価は実行でき要約は実行できない、という非対称が起きる（理由は BR-06）。
- 「評価未設定」フィルタは **統合後の評価サイクル未登録** を指す。判定は **`gsc_article_evaluations` に行が存在しないこと**であり、**`status` は見ない**（`status='paused'` / `'completed'` の行を持つ記事もフィルタ結果には出ない）。現行 RPC は `not exists (select 1 from public.gsc_article_evaluations e where e.content_annotation_id = ca.id)`（`20260818000300_…sql:57-60`。**一覧 RPC 側は `user_id` 条件を持たないが、annotation が user 所有のため実質同値**。直後の GA4 側 `:64-67` は `e.user_id = p_user_id` を持つ）。旧 migration ヘッダの verbatim も "A content annotation is considered started when a row exists in gsc_article_evaluations, regardless of its status."（`20260809100000_…sql:2-3`）。**BR-01 の既登録スキップも同じく「行の有無」で判定する**（既存 `registerEvaluation` の重複チェックと同型。`src/server/actions/gscDashboard.actions.ts:453-459` も `status` 条件を持たない）。「active 行の有無」で実装すると既存単記事経路と挙動が食い違い、`paused` / `completed` の記事へ二重 insert を試みることになる。2026-08-26 の GA4 サイクル統合で GSC/GA4 は1本化され、GA4 専用フィルタは撤去済み（`CategoryFilter.tsx` の状態フィルタは「評価未設定」と「改善提案あり」の2つ。見出しは「状態でフィルター」）。本一括開始は **`gsc_article_evaluations` への insert のみ**で、追加の GA4 専用操作は不要だが、**副作用として GA4 コンテンツ評価も同周期で開始される**（§4 Non-goals の旧「GSC のみ」記述は失効済み）。
- 開始成功の確認は、専用ステータス新設ではなく **「評価未設定」フィルタ結果から行が消えること**（同フィルタ ON 時）と件数トーストで行う。フィルタ OFF のまま開始した場合は行が消えないため、確認は件数トーストだけになる（ゲート撤廃の帰結）。
- **「全選択」は画面の絞り込みに従わない。** 「評価未設定」ON やカテゴリで絞った状態で全選択しても、選ばれるのは表示中の行ではなく BR-07 の母集団（全記事）である。選択件数が一覧の総件数より大きくなるのは正常。既登録はサーバーがスキップするため、結果として「未登録の全記事が開始される」ことになる。
- **全記事が1000件を超えても全選択は使える。** `updated_at` 降順の先頭1000件へ丸め、件数表示に「1000 / 全 M 件」と明示する（2026-08-29 Q-006 で確定。要約親 BR-05 例外と同型）。エラーにはしない。**ただし残りは「再実行すれば進む」わけではない。** 本機能の登録は `gsc_article_evaluations` への insert のみで `content_annotations.updated_at` を更新せず（`gscDashboard.actions.ts:436-442` は select のみ）、同テーブルに `updated_at` の自動更新トリガも存在しない（唯一のトリガ `20251105090000_…sql:126-129` は別テーブルを更新するだけ）ため、**窓（`updated_at` 降順の先頭1000件）は再実行しても動かず、2回目以降の `registeredCount` は 0 になる**。1001件目以降は行チェック（ページ送り）で個別に選択する（BR-07「丸めた残りの扱い」/ §12 R-007）。**丸めを無言でやらないこと**が要件であり、件数表示は Must（§6 項目定義）。

#### 認可の実装方針（既存の事実と、今回新規に作るもの）

既存コードの事実（2026-08-27 時点）:

- 単記事登録 `registerEvaluation`（`src/server/actions/gscDashboard.actions.ts`）は **`canWriteGa4` で role を強制している**（`admin` / `paid` のみ）。GA4 サイクル統合後、GSC 評価登録も同 Action 経由のため、命名は `canWriteGa4` のままだが実質は統合評価サイクルの write 権限である。
- `app/api/gsc/evaluations/register/route.ts`（POST）は **依然として `authMiddleware` の認証のみ**で role チェックが無い（§4 Non-goals 据え置き）。
- `/analytics` は `PAID_FEATURE_REQUIRED_PATHS` に含まれ、`/analytics/[annotationId]` もプレフィックスマッチで保護される。

今回の方針:

1. 一括開始のサーバー側認可は **新規に強制する**（一括 Action は未実装のため）。`getAuthUserId` が返す `role` を **`registerEvaluation` と同じ `canWriteGa4({ role })`** で判定する。別モジュール `canWriteGsc` の新設は **行わない**（2026-08-23 spec-review 時点の `gsc-permissions.ts` 案は、GA4 統合後の `registerEvaluation` 実態に合わせて **2026-08-27 に撤回**）。
2. role チェックは **一括エントリポイント（`registerEvaluationsBulk`）側に置く**。既存 `registerEvaluation` と共通化する場合も、共通の登録コアには入れない（Route Handler の据え置き方針は §4 Non-goals 参照）。
3. UI 側は追加のロール分岐を作らない。`/analytics` 自体が `proxy.ts` で `admin`/`paid` に限定されているため、この画面に到達した時点で条件を満たす（§4 対象範囲）。

#### 連携ライフサイクル（トークン失効時の扱い）

- 参照 URL: `https://developers.google.com/identity/protocols/oauth2`
- 確認日: 2026-08-23
- 公式ページ本文の verbatim 引用:
  - "You must write your code to anticipate the possibility that a granted refresh token might no longer work."
  - "The user has revoked your app's access."
  - "The refresh token has not been used for six months."

引用から導いた解釈（引用とは分けて記載）: refresh token は正常系として無効化されうるので、`property_uri` の存在は「今 GSC を呼べる」ことを保証しない。したがって失効中でも本機能の一括 UI は表示され、最大1000件の登録も成功しうる。ただし **本仕様では検知を追加しない**（既存の単記事開始と同じ判定に揃える。§4 Non-goals）。実際に失敗するのは登録から約1サイクル後の既存バッチ側であり、結果は既存の `import_failed` 表示に現れる（§12 R-005）。GSC 連携全体の失効検知（`needsReauth` の常時反映）は本仕様の責務外とする。

## 11. トレードオフ判断

### 判断 1: WP インポート自動開始 vs 一覧一括開始

- 判断: 一覧一括開始を採用する
- 比較した案:
  - 案A: インポート成功時に全新規記事へ自動でサイクル登録
  - 案B: 一覧で選択して一括開始（本仕様）
  - 案C: 現状維持（詳細で1件ずつ）
- 採用案: 案B
- 採用理由: 2026-08-05 の「取り込み時自動は後回し」合意を破らない。誤って全件登録するリスクを利用者が制御できる。手動1件ずつの最大コストは削減できる。なお §1.9.5 の原文で合意された代替手段は「ソート＋手動運用」までであり、**一覧一括開始は開発側の提案**である（メタデータ参照）。要件としての根拠は §12 Q-001 / Q-003 の PO 回答に置く。
- 却下した案と理由:
  - 案A: 合意反転・件数爆発・trial と GSC 未連携の分岐が重い
  - 案C: 100〜200 件運用の痛みが残る
- 影響（コスト・納期・品質・運用・拡張性）: 中程度の UI＋Server Action。DB 変更なし。
- 将来変更する条件: クライアントが自動開始の合意撤回と件数上限に合意したとき
- 判断者・判断日: 開発会話 / 2026-08-23

- 採用理由: PO 回答「フィルタに関係なく全記事」。利用者にとって「全選択」は文字どおり全件であり、絞り込み中に押したときだけ意味が変わる案Bは説明が要る。既登録はサーバーがスキップする（BR-01）ため、母集団を広げても登録結果は「未登録の全記事」で安定する。

## 付録 A. 設計メモ（実装者向け・要件ではない）

実装時の指針。要件の変更権限は持たない。

- 新規 Server Action 案: `registerEvaluationsBulk`（`gscDashboard.actions.ts` または専用 actions）。内部で既存登録ロジックをループ／共通関数化。共通化する場合は `app/api/gsc/evaluations/register/route.ts` も同じコアに寄せられる（必須ではない。§10）。role チェックは共通コアではなく一括エントリポイント側に置く（§6 権限）。
- 認可: 一括エントリポイントで **`canWriteGa4({ role })`** を `registerEvaluation` と同型に適用する。
- 1リクエスト上限: **1000**。超過は 400。取得件数と**フィルタ無しの** `total_count` の突合必須。`items.length >= limit` での打ち切り検知は使えない（1ページの `items` は `p_per_page` の 100件クランプで頭打ちになるだけで、母集団の総数とは関係しない）。**`db-max-rows` は当該経路の制約ではない**（一覧 RPC は jsonb 集約1行返し。BR-07「根拠にしないもの」）。
- 全選択の実装: **サーバー側の直接クエリ1本のみ**（BR-07「ID 解決の方式」）。クライアントは ID 配列も画面の絞り込み状態も送らない。実装形は次のとおり。

  ```ts
  // 母集団の解決（ID と総件数を1回で得る）
  supabase.from('content_annotations')
    .select('id', { count: 'exact' })
    .eq('user_id', userId)
    .order('updated_at', { ascending: false, nullsFirst: false })  // 一覧 RPC と同じ並び
    .limit(1000)                                                    // BR-07 上限。超過は丸め
  ```

  母集団の定義は BR-07。
  - **クライアントによるページング収集は採らない。** 一覧 RPC は `authenticated` から revoke 済みで `service_role` 限定（`20260818000300_…sql:93-94`）でクライアントから叩けず、唯一の本番呼び出し元は Server Component（`app/analytics/page.tsx:142` → `src/server/services/analyticsContentService.ts:45`）。新規クライアント向けエンドポイントの新設は §5 に未計上で MVP を逸脱する。加えて並び順は `row_number() over (order by f.updated_at desc nulls last)`（`…sql:72`）でタイブレーク列が無いため、複数回のページングでは重複・欠落が起こりうる（WP 一括インポート直後は `updated_at` が近接するので現実的）。
  - **一覧 RPC は1回の呼び出しで最大100件しか返さない**（`p_per_page` が `greatest(1, least(100, …))` でクランプされる。`20260818000300_…sql:22`）ので、既存 RPC をそのまま母集団解決に使い回さないこと。画面の絞り込み状態を送信に混ぜないこと（混ぜると案B の挙動に戻る。判断3）。
  - **新規 SQL 関数は作らない。** 直接クエリで同じ集合が得られる（BR-07「ID 解決の方式」の実測根拠）ので migration を増やさない。
  - **`limit 1000` は `db-max-rows`（1000）と一致している前提の実装である。** 上限を上げるときは BR-07 の同名の注意書きを読むこと。件数は `count: 'exact'` で取るので行数上限の影響を受けない。
