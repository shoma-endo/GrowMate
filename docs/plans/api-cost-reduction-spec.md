## 1. 背景・目的・成功指標

### 背景・解決したい課題

- 現在、誰が、どの業務で困っているか:
  - 運営（GrowMate 提供側）が、自動処理の AI 利用料を予測・管理できていない。
  - 定期処理（cron）で AI を呼んでいるのは次の3機能。どれも最初の登録・有効化はユーザー操作で、以降は自動で回り続ける。
    - GSC 改善提案（評価サイクルに登録した記事。順位が「改善」以外のとき提案を生成）
    - GA4 コンテンツ評価（同じく評価サイクル登録分）
    - Google 広告 除外キーワード提案（設定で ON にしたユーザーのみ、1日1回）
  - AI 要約（一括）もジョブを積んで cron で処理する。2026-10-17 から一時的に `admin` 限定。
- 放置した場合の影響（2026-10-17〜18 本番 DB の読み取り専用集計にもとづく推定。日本語1文字≒1トークン、Claude Sonnet 5 単価で換算）:
  - 5,000〜15,000記事規模で自動処理を全部回すと、月 700〜4,000 ドル程度。
  - GSC 改善提案は処理が1時間1件に固定されている（`src/server/services/gscSuggestionJobService.ts:9` の `JOBS_PER_INVOCATION = 1`）。発生は1日約75〜78件、処理は1日24件。未処理は 5,231件・対象 2,587記事・最古 2026-08-15（2026-10-18 時点、増加中）。費用は月150ドル前後で頭打ちだが、提案は2か月前の評価にもとづくものになっている。
  - 費用の中心は段階3以上の本文リライト（本文全体を出力、1.2万〜1.6万文字）。
  - 実際の消費量は記録しておらず、上の数字は文字数からの推定に留まる。

### 目的

- この開発で実現する状態:
  - AI を呼ぶたびに工程ごとの消費量が記録され、実測で見積もれる。
  - AI に渡す量と呼ぶ回数が、成果に必要な分だけになっている。
- 利用者・事業にとっての価値:
  - 記事数が増えても AI 利用料が読める範囲に収まる。
  - GSC 改善提案が溜まらず、最新の評価にもとづいて届く。

### 成功指標

| 指標 | 現状 | 目標 | 測定方法 | 測定時期 |
| --- | --- | --- | --- | --- |
| 工程ごとの消費量を実測できる | 記録なし（推定のみ） | AI 呼び出しごとの消費トークンが工程名つきで残る | FR-001 のログを SQL で集計 | リリース直後 |
| GSC 改善提案 1件あたりの費用 | 約0.13ドル（推定。段階4は約0.21ドル） | 半分以下 | FR-001 のログ | リリース後1か月 |
| GSC 改善提案の未処理件数（同じ記事により新しい評価履歴があるものを除く） | 最大約2,587件（同じ定義で数えた値。除く前は5,231件で増加中。2026-10-18 時点） | 増え続けない（1日の処理件数が発生件数を上回る） | `gsc_article_evaluation_history.suggestion_status` の日別集計 | リリース後1週間 |

## 2. 利用者・関係者・利用シナリオ

| 区分 | 対象 | 期待すること・責任 |
| --- | --- | --- |
| 利用者 | `admin` / `paid` | 改善提案・評価・CSV 取り込みを使える |
| 運用担当 | 開発者（shoma-endo） | 消費量のログから費用を集計・見積もる |
| 管理者・承認者 | クライアント（繁田） | 改善提案の中身（読了率の改善）、表示文言、CSV 取り込みの画面を事前に確認する |

### 主な利用シナリオ

1. **運用担当が**、**月末に**、**工程ごとの AI 消費量と費用を集計したい**。
2. **paid の利用者が**、**順位が上がらない記事で**、**読者が止まっている箇所の手前だけの修正案を受け取りたい**。
3. **paid の利用者が**、**手元のスプレッドシートにあるキーワード・ペルソナなどを**、**AI 要約を使わずに一括で登録したい**。

## 3. 業務要件と業務フロー

### 現状（As-Is）

```text
[GSC 改善提案]
評価（毎時 cron、記事ごとに評価サイクル周期）→ 順位が改善以外なら提案ジョブを積む
→ 毎時 cron が1件だけ取り出し、段階 n に応じて段階1〜n を即時に AI 呼び出し
   段階3以上では本文全体のリライト（出力 1.2万〜1.6万文字）
→ 1段階でも失敗するとジョブ全体を15分後にやり直し（最大3回）

[GA4 コンテンツ評価]
評価（毎時 cron）→ 初回・30セッション未満は AI なし → それ以外は診断が「良好」でも AI で説明文を作る

[AI 要約]
（一時的に admin 限定）単記事ボタン / 一括ジョブ → AI が記事本文から8項目を作る

[消費量]
チャット・Canvas の消費トークンだけ console に出力（`logTokenUsage`）。保存はしていない
```

### 導入後（To-Be）

```text
[GSC 改善提案]
評価（変更なし）→ 順位が改善以外なら提案ジョブを積む（変更なし）
→ 毎時 cron が未処理ジョブを1回あたり上限件数まで Message Batch にまとめて投入（半額）
→ 同じ cron が、投入済みの Batch を確認して結果を回収・保存
   「本文リライト（全文）」は「読了率の改善」に置き換え（出す段階は Q-002）:
   読了率から止まっている位置を推定し、前回の位置から今回の位置までの本文だけを AI に渡す

[GA4 コンテンツ評価]
診断が「良好」のときは AI を呼ばず、数値を差し込んだ定型文を保存。それ以外は今までどおり

[AI 要約]
admin 限定のまま。データを持っている利用者は CSV 取り込みで8項目＋表示回数を一括登録できる

[消費量]
AI 呼び出し（即時・Batch・チャットのストリーミング）の消費トークンを工程名つきで DB に記録
```

### 業務ルール

- BR-01: 評価（GSC の順位判定・GA4 の点数と診断）のロジックは変えない（クライアント回答「評価機能はこれまで通り」）。
- BR-02: 改善提案を作る条件は今までどおり「順位が改善以外（変化なし・悪化）」。「変化なし」を AI の対象から外す案は取り下げ済み（2026-10-18）。
- BR-03: 読了率の改善で AI に渡す範囲は「前回止まっていた位置 → 今回止まっている位置」。初回は冒頭から。位置は「読了率 × 本文の文字数」で推定する。
- BR-04: CSV 取り込みは URL で既存の記事に突き合わせる。同じ URL があれば上書きし、空欄のセルは上書きしない。GrowMate に無い URL はスキップして一覧で返す。

> 判断軸: GrowMate は MVP 開発を最優先とする（`AGENTS.md` Core Rules）。

### 対象範囲

- 画面・操作:
  - CSV 取り込み欄（FR-006）。置き場所は `/wordpress-import` 画面（**Claude案・未確認**。実装前にたたき台をクライアントに見せて合意する）。

- API・外部連携: Anthropic Message Batches API（GSC 改善提案）。
- データ・DB（§9）:
  - AI 消費量のログテーブルを新設（FR-001）
  - 改善提案ジョブの Batch 管理（列の追加と取得 RPC の改修、FR-002）
  - 読了率の改善で前回使った位置の保存（FR-005）
  - 読了率の改善用のプロンプトを `prompt_templates` に追加（FR-005）
- 権限・ロール: CSV 取り込みは `admin` / `paid`（サーバー側でも検証）。それ以外は既存機能の権限を変えない。
- 運用・監視: 消費量は SQL で集計する（画面は作らない）。
- 実装済み（PR #672・未マージ）: ブログ作成のモデル切り替え（FR-007）。

### Non-goals（今回の対象外）

| 対象外にするもの | 理由 | 将来検討する条件・時期 |
| --- | --- | --- |
| 思考量（effort）の指定（施策1の「思考量を low に」） | FR-007 では思考をオフ（Sonnet 5.5 は `between_tools`、Haiku 5.5 は `disabled`）にしており、拡張思考はしていない（`between_tools` はツール呼び出しの間に短い経過メモを返すことがあり、その分は出力として課金される）。effort を low にすると出力自体が短くなるおそれがあり、2026-10-19 のクライアント指示もモデルの切り替えだけだった | 試験の結果、出力の長さや費用を見て調整したくなったとき |
| CVR が上がらないことを改善提案の発生条件に加える（**Claude案・未確認**。ALT-003） | クライアント回答に含まれるが、AI の呼び出しを増やす変更で本仕様（削減）と目的が逆。順位改善の行は提案を持たない前提が通知・未読表示・既読化・絞り込み・段階説明に広くあり、作り込みが大きい。クライアントの評価枠組みでは「よく読まれているのに CV が少ない」は CTA の問題（評価エンジン仕様「R_GOOD: 次はCTAとオファーの検証へ」）で、読了率の改善と合わない場合がある | 別仕様として、CVR の定義（分母・比べる期間・0→0 の扱い）と、CTA の提案との関係を決めるとき |
| GSC「変化なし」を AI の対象から外す | クライアントの流れでは「順位が変わらない」も読了率の改善の対象のため取り下げ（2026-10-18） | — |
| GA4 コンテンツ評価の Batch 化（**Claude案・未確認**。ALT-002） | 費用が小さい（直近30日で AI 92回・約0.7ドル。15,000記事で全記事に AI を使っても月100ドル程度。FR-003 でさらに約2割減る）。指定時刻に評価・通知する今の作りを投入と回収の2段に分ける改修が要り、削減額に見合わない | GA4 評価の消費量が FR-001 のログで月100ドルを超えたとき |
| AI 要約の Batch 化 | AI 要約は admin 限定で止めているため | AI 要約を paid に戻すとき |
| インポート直後の AI 要約・初回評価の自動開始（`client-vision-from-lark.md` §1.9.3） | 2026-08-05 定例で後回しに合意済み（同 §1.9.5）。CSV 取り込みはこの要望を置き換えるものではなく、データを持っている利用者向けの手段。後回しの扱いは変えない | クライアントが後回しを撤回したとき |
| 除外キーワード提案の Batch 化 | ユーザーが指定した時刻にメールを送る機能で、Batch の最大24時間の遅れが合わない。記事数に比例せず、費用も月10〜90ドル程度（推定） | 送信時刻の仕様を見直すとき |
| 共通部分のプロンプトキャッシュ | 費用の中心は記事ごとに違う本文と出力で、共通部分は全体の数％。AI 要約は停止中、GSC の各段階は共通部分が短い（193〜970文字）、除外キーワード提案は1ユーザー1日1回でキャッシュの有効期限内に2回目が来ない | 共通部分が長いプロンプトを連続で呼ぶ機能ができたとき |
| 市場の前提・ジャーニーの使い回し | 事業者情報（`briefService`）として既にある。記事ごとのペルソナは13ユーザー・1,602記事で1,188種類あり、市場単位にまとめると内容が変わる | — |
| Web 検索結果の保存と回数上限 | 自動処理は Web 検索を使っていない。チャット・Canvas は既定で1リクエスト最大3回（`max_uses`。リクエストで上書き可能・検証なしである点は本仕様の対象外） | 自動処理で Web 検索を使うとき |
| 再試行回数の変更・失敗した段階だけの再試行 | 直近30日に完了した GSC 改善提案 529件はすべて1回目で成功しており、効果がない | 失敗が増えたことがログで分かったとき |
| 消費量の集計画面・アラート | MVP。SQL での集計で足りる | 運用担当以外が見る必要が出たとき |
| AI 呼び出しの費用上限（アプリ側） | Anthropic コンソールのワークスペース単位の支出上限で代えられる | プラン別の利用上限を設けるとき |
| CSV の Shift_JIS 対応（**Claude案・未確認**） | UTF-8（BOM あり可）に限る。Excel は「CSV UTF-8」で保存できる | 利用者から Shift_JIS での取り込み要望が出たとき |

### FR-002 GSC 改善提案の Batch 化

- 投入（毎時の `/api/cron/gsc-suggestions`）:
  - 未処理（`pending` と、再試行時刻を過ぎた `failed`）のジョブを、1回あたり **100ジョブ** まで取り出す（**Claude案・未確認**。cron の実行時間 300秒と、本文が無い記事の WordPress 取得に収める値。1日2,400ジョブで、15,000記事時の発生見込み1日約330件を上回る）。
  - 1ジョブにつき実行する段階ぶんのリクエスト（最大4件）を作り、1つの Message Batch にまとめて投入する。
  - リクエストの `custom_id` は「履歴 ID＋段階番号」から作る（64文字以内・英数字と `-` `_` のみ）。
  - 同じ記事（`content_annotation_id`）に、より新しい評価履歴（`created_at` が後。同時刻は `id` で比べる。順位が改善した行・取得エラーの行も含む）があるジョブは、取り出し候補（`pending`・再試行時刻を過ぎた `failed`・タイムアウトした Batch ID の無い `processing`）のどれであっても取り出さない（古い評価にもとづく提案のため。同じ「前回の位置」を2件が使うのも防ぐ。**Claude案・未確認**。Q-001 で「全件処理」になった場合はこの条件を外す）。
  - 取り出されないジョブは状態を変えずに残る。評価履歴の画面では「生成中」「再生成しています」ではなく「新しい評価があるため、この提案は作りません」と表示する。対象は `pending` と試行3回未満の `failed` だけ（Batch 投入済みの `processing` には出さない。あとで完了したときに食い違うため）。最新でないかどうかは、画面が持つ同じ記事の履歴一覧（`created_at` の降順、同時刻は `id`）から判定し、`getSuggestionStatusMessage` に引数で渡す。DB の変更は要らない。成功指標の未処理件数からも除く。
  - 投入に成功したらジョブに Batch ID と投入日時を保存する。投入に失敗したら、ジョブを `failed`・15分後に再試行にする。
- 回収（同じ cron の中で、投入より先に行う）:
  - Batch ID があり未回収のジョブの Batch 状態を確認する。終わっていれば結果を取り出し、`custom_id` でジョブと段階に対応づける（結果の並び順は保証されない）。
  - ジョブの全段階が `succeeded` なら、今と同じ形で `suggestion_summary` に保存して完了にする。
  - 1段階でも `errored` / `expired` / `canceled` なら、ジョブを `failed`・15分後に再試行にする（今と同じく、ジョブ全体をやり直す。最大3回）。
- 取得 RPC の改修: `claim_gsc_suggestion_jobs`（最新定義 `supabase/migrations/20260618000000_add_next_evaluation_date_to_gsc_article_evaluations.sql`）は、取り出した時点で試行回数を1つ増やし、`processing` のまま15分を過ぎたジョブを取り直す（3回目なら `failed` にする）。取得件数は最大10件。このままでは Batch 投入済みのジョブが15分ごとに再投入される（二重課金）か、結果が出る前に失敗扱いになるため、次のように改修する。
  1. 試行回数は今どおり RPC が取り出すときだけ数える（投入の成功では数えない）。
  2. 15分のタイムアウトで `failed` にする処理と、`processing` の取り直しは、どちらも Batch ID が無いジョブに限る。
  3. 投入済みのまま25時間を過ぎたジョブ（Batch の期限24時間＋余裕）は、まず Batch の状態を確認する。結果が取れれば回収し、取れなければ `failed`・再試行にする（結果は29日間取得できるので、確認せずに再投入すると二重課金になる）。
  4. RPC がジョブを取り出すときに、Batch ID と投入日時を空に戻す（再試行の途中で止まったとき、古い Batch ID が残って取り直しから外れ、回収で古い Batch を見てしまうのを防ぐ）。
  5. 取得件数の上限を FR-002 の値に合わせ、上の「同じ記事により新しい評価履歴があるジョブは取り出さない」条件を入れる（`content_annotation_id` 同士の NOT EXISTS で書ける。索引 `(content_annotation_id, evaluation_date desc)` がある）。
  - 3. の Batch 状態の確認は API 呼び出しなので、RPC ではなくアプリ側（cron）の処理として行う。
- 本文リライトのためのストリーミング（タイムアウト対策）は、Batch では不要になる。

### FR-005 読了率の改善

- 置き換え対象: 段階3の「本文の提案」（`gsc_insight_body_rewrite`）。どの段階で出すかは Q-002 で決める（案A: 今の段階設計どおり段階3・4のジョブで出す / 案B: 順位が改善しなかった毎回出す。ALT-004）。段階1（タイトル・説明文）、段階2（書き出し案）、段階4（ペルソナから全て変更）の中身は変えない。
- 設定キーは新設する（例: `gsc_insight_read_rate`）。`MODEL_CONFIGS`・`SuggestionTemplate`・表示の `TEMPLATE_ORDER` / `TEMPLATE_LABEL_MAP` に追加し、`src/lib/prompt-descriptions.ts` に説明を足す。表示の対応表は `MODEL_CONFIGS` のラベルをキーにしているため、旧キー `gsc_insight_body_rewrite` とラベル「本文の提案」は消さずに残す（過去の提案を表示し続けるため）。
- 範囲の決め方:
  1. 読了率は、同じ記事の最新の成功した GA4 評価（`ga4_content_evaluations.last_success_history_id` → `ga4_content_evaluation_history.read_rate`）を使う。
  2. 今回の位置 = 読了率 × 本文の文字数（`content_annotations.wp_content_text`）。前回の位置 = この記事で前回読了率の改善に使った読了率 × 本文の文字数（初回は0）。読了率は比率（1を超えることがある）なので、表示では100倍して整数に丸める。
  3. 範囲の端は、近い段落の切れ目に寄せる。範囲の直前の見出しを文脈として添える。
- AI への指示には、その評価の診断（冒頭で離脱 → 書き出し、途中で離脱 → 見出し構成と本文の密度、拾い読み → 結論の位置と情報密度、ミスマッチ → 集客キーワードと中身のズレ）を含める（評価エンジン仕様の「診断コードの意味」）。
- AI を呼ばない場合（**Claude案・未確認**）:

  | 状態 | 扱い |
  | --- | --- |
  | 診断が「良好」 | 呼ばない。「読了面の改善は不要です」と表示（評価エンジン仕様「R_GOOD: 読了面の改善は不要」） |
  | 読了率が100%以上 | 呼ばない。「1人あたり平均で全体を読み切れる時間が使われています」と表示 |
  | 読了率を取れない（GA4 未連携・30セッション未満・未評価） | 呼ばない。「データ蓄積中のため、読了率の改善は出せません」と表示（評価エンジン仕様の「データ蓄積中」に合わせる） |
  | 前回の改善から GA4 評価が更新されていない（前回と同じ評価履歴） | 呼ばない。「前回の改善のあと、まだ新しい評価がありません」と表示 |
  | 今回の読了率が前回以下 | 前回の修正が効かなかったとみなし、冒頭から今回の位置までを対象にする |

- 出力: 違和感のある箇所ごとに「原文」「違和感の理由」「修正案」。既存の改善提案と同じく Markdown で `suggestion_summary` の1節にする。
- 表示: 節の見出しは「読了率の改善」。本文の冒頭に「1人あたり平均で全体のX%〜Y%まで読まれている範囲」と書き、推定であることが分かるようにする（評価エンジン仕様「推定値を実測のように見せると…信用を失う」）。用語は「読了率」（滞在時間ベース）を使い、一覧の「完読率」（スクロール90%到達）と混同しない（`ui-text.md`）。

### 入力・出力・状態遷移

- GSC 改善提案ジョブ（FR-002）: `pending` → 投入済み（`processing`、Batch ID あり）→ `completed`、または `failed`（再試行時刻つき）→ 試行3回で打ち切り。状態値は既存の4値を使い、投入済みは Batch ID の有無で区別する。
- 冪等性:
  - 回収はジョブの状態（投入済み・Batch ID 一致）を条件に更新し、同じ結果を2回保存しない。

## 13. テスト・リリース・ロールバック

### テスト方針

- 単体:
  - 消費量の記録（即時・Batch・ストリーミング・途中切断・記録失敗時に処理が止まらない）
  - Batch の投入・回収・失敗・期限切れ・回収漏れ・再投入しないこと・取得 RPC の改修
  - `R_GOOD` で AI を呼ばない（通常評価と再生成）、差し込み後の文字数上限
  - 読了率の範囲計算（初回・2回目・前回以下・100%以上・取得不可・評価未更新・良好）
  - CSV の解析（引用符・セル内改行・BOM・空欄・文字コード）、照合（正規化・複数一致）、上書きと空欄、スキップ、重複、分割送信、trial の拒否
- 実画面確認: CSV 取り込み欄（状態別 UI の5状態）、評価履歴の「読了率の改善」の節と段階説明、取り出さない提案の表示。
- 外部 API: Batch API はテストではモックする。リリース後に本番の数件で完了を確認する。

### リリース方針

- FR-007 は PR #672 で実装済み（未マージ）。本番に出すかどうか（PR #672 のマージと develop→main）はユーザーが決め、出したあとクライアントに文章の品質を試してもらう。
- リリース単位: FR-001 を先に出し、変更前の実測値を取ってから FR-002・003・005 を出す（削減効果を比べるため）。FR-006 は独立して出してよい。
- DB 変更の適用順序: migration → アプリ。
- 本番確認項目: 消費量ログが記録される、改善提案の Batch が完了する、未処理件数が減る。

### ロールバック方針

- アプリ: デプロイを1つ前に戻す。
- DB: 追加は列・テーブル・行のみ。RPC は改修前の定義に戻す migration を用意する。
- 投入済みの Batch: RPC を戻す migration とアプリの巻き戻しは続けて行う（旧アプリと新 RPC の組み合わせでは、Batch ID のあるジョブが取り直しの対象から外れ、旧アプリは回収もしないため `processing` のまま残り続ける。新アプリと旧 RPC の組み合わせでは、取得件数の上限（10件）を超える指定になるため取り出しが毎回エラーになり、投入が止まる）。両方を戻したあと、投入済みで未回収のジョブは旧処理で作り直されるため、最大約25時間分（2,500ジョブ）の費用が二重になる。これを上限として受け入れる。
