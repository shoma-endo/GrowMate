## 1. 背景・目的・成功指標

### 背景・解決したい課題

- 現在、誰が、どの業務で困っているか:
  - GA4 コンテンツ評価のメール（`src/server/lib/ga4-content-evaluation-email.ts:75`）は「次の一手」を提案するが、**実行はユーザーが WordPress を開いて自分で書き換える**必要がある。提案から実行までの間で PDCA が止まる。
  - クライアントは今後の開発方針として「なるべくユーザーに操作させず、評価・改善提案・実行の循環をシステム側で回す。ユーザーには LLM が実行した履歴を追える状態を提供する」を示している（`client-vision-from-lark.md` §1.12.6）。
- 放置した場合の影響: 「AI で作れるから GrowMate は不要」という解約理由（§1.9.1・§1.12.1）に対し、「管理・提案」から一歩進んだ「実行」まで巻き取る差別化が打てない。

### 目的

- この開発で実現する状態: 評価メールで提案された修正を、ユーザーが GrowMate 上で「実行」を1回押すだけで WordPress 記事へ反映でき、反映内容が修正ログに残り、元に戻せる。
- 利用者・事業にとっての価値: 自分で書き換える手間をなくし、提案→実行の離脱を減らす。実行内容を後から追跡できる。

### 成功指標

| 指標 | 現状 | 目標 | 測定方法 | 測定時期 |
| --- | --- | --- | --- | --- |
| 実行提案メールのうち「実行」された割合 | 計測手段なし（実行機能なし） | 未確定（MVP では目標を置かず、まず計測できる状態にする） | 修正ログの件数 ÷ 実行提案メール送信件数（SQL で都度集計） | リリース後1か月 |

## 2. 利用者・関係者・利用シナリオ

| 区分 | 対象 | 期待すること・責任 |

| 利用者 | `admin` / `paid` ロールで、GA4 コンテンツ評価サイクルを設定し WordPress 連携済みのユーザー | メールの提案を読み、GrowMate で「実行」を押す。修正ログで結果を確認し、必要なら元に戻す |
| 運用担当 | 開発 | 実行失敗のログ確認 |
| 管理者・承認者 | クライアント（カオルさん・繁田さん） | 書き換えプロンプトの内容確認（Q-003）、承認点の合意（Q-005） |
| 外部サービス・連携先 | WordPress（WordPress.com / セルフホスト）、Anthropic（LLM）、Resend（メール） | — |

### 主な利用シナリオ

1. **利用者が**、**評価サイクルで「冒頭離脱型」と判定された記事の実行提案メールを受け取り**、**リンクから GrowMate を開いて「実行」を押し、冒頭が書き換わった記事を WordPress に反映したい**。
2. **利用者が**、**記事詳細のコンテンツ評価タブの修正ログで、いつ・何が・どう書き換わったか（変更前／変更後）を確認し、意図に合わなければ「元に戻す」を押す**。

## 3. 業務要件と業務フロー

### 現状（As-Is）

```text
評価サイクル（毎時 cron）→ GA4 コンテンツ評価 → 「コンテンツ評価が完了しました」メール
  → ユーザーが GrowMate で詳細を確認 → WordPress 管理画面を開いて自分で書き換え
  → 何をいつ直したかはどこにも残らない
```

### 導入後（To-Be）

```text
評価サイクル（毎時 cron）→ GA4 コンテンツ評価
  ├ 実行可能条件（BR-01）を満たす → 「コンテンツ評価実行提案」メール
  │    → リンク → ログイン → 記事詳細「コンテンツ評価」タブ → 「実行」
  │    → WordPress から本文（raw）取得 → LLM が冒頭を書き換え → WordPress へ更新
  │    → 修正ログに変更前・変更後を記録 → 画面に完了表示
  │    → （任意）修正ログから「元に戻す」→ 変更前の本文を WordPress へ書き戻し
  └ 満たさない → 従来どおり「コンテンツ評価が完了しました」メール（変更なし）
```

### 業務ルール

| ID | ルール | 例外 |
| --- | --- | --- |
| BR-01 | 実行提案メールにするのは、次をすべて満たす評価のみ: 結末が `evaluated`（narrative あり）、診断コードが実行対象（MVP は `R_TOP_EXIT` のみ。Q-001）、記事に `wp_post_id` がある、ユーザーに `wordpress_settings` 行がある | 満たさない評価は従来メールを送る（文面変更なし） |
| BR-02 | 実行できるのは、その記事の**最新の**成功評価履歴に紐づく提案だけ。新しい評価が出たら古い提案は実行できない | — |
| BR-03 | 1つの評価履歴につき実行は1回まで（成功済み・実行中なら再実行不可）。失敗した場合のみ再実行できる | — |
| BR-04 | 書き換えるのは本文の「冒頭」＝最初の `<h2>` より前の部分だけ。それ以降の本文・タイトル・抜粋・アイキャッチ・カテゴリは変更しない | 本文に `<h2>` が無い、または冒頭が空の記事は実行不可（エラー表示） |
| BR-05 | 実行したら必ず修正ログに変更前・変更後の本文全文を記録する。記録に失敗した場合でも WordPress 更新が成功していれば、その事実をエラーログに残す（§6 エラー時） | — |
| BR-06 | 「元に戻す」は、WordPress 上の現在の本文が修正ログの変更後本文と一致する場合だけ行う。一致しない（ユーザーが WordPress 側で編集済み）場合は書き戻さず、変更前本文を画面に表示して手作業での復元に委ねる | — |
| BR-07 | 実行・元に戻すは `admin` / `paid` のみ。サーバー側でも検証する | — |

## 4. 対象範囲と Non-goals

### 対象範囲

- 画面・操作: 記事詳細 `/analytics/[annotationId]` の「コンテンツ評価」タブに「実行」ボタンと「修正ログ」（元に戻す付き）を追加。メールのリンクからこのタブを開けるようにする。
- API・外部連携: WordPress REST API の投稿取得（`context=edit` で `content.raw`）と更新（`POST /wp/v2/{type}/{id}`）を `WordPressService` に追加。LLM による冒頭書き換え。
- データ・DB: 修正ログテーブルを1つ新設。
- メール: GA4 コンテンツ評価メールに「実行提案」版の文面を追加（BR-01 を満たすときのみ）。
- 権限・ロール: `admin` / `paid`。
- 運用・監視: 新設なし（`console.error` のみ）。

### Non-goals（今回の対象外）

| 対象外にするもの | 理由 | 将来検討する条件 |
| --- | --- | --- |
| 検索順位評価（GSC）の結果を合わせて「一番のボトルネック」を選び、1通で提案すること（GSC 提案の自動実行を含む） | GSC と GA4 は設定を共有し同じ毎時実行で評価されるが（`ga4-content-evaluation-spec.md` §6.6）、(1) GSC の改善提案は評価とは別ジョブ（`gsc-suggestions`）が後から LLM で生成し、評価直後は `suggestion_status='pending'` のため、GA4 メール送信時点で GSC の提案が揃っている保証がない。統合するには両方の完了を待ち合わせる送信フローへの組み替えが必要で、工数が 1.5〜2 倍になる見込み。(2) GSC の提案（`suggestion_summary`）は見出し単位のリライト指示表などの Markdown で、そのまま記事へ反映できる形ではない。MVP では GA4 の「次の一手」（GA4 評価がすでにボトルネックを1つに絞った結果）だけを実行提案にする（Q-004 回答済み・ALT-005） | GA4 側の実行が使われると確認できたら別仕様で |
| `R_TOP_EXIT` 以外の診断コード（`R_MISMATCH` タイトル・説明文 / `R_MID_EXIT`・`R_SKIM` 目次構成）の自動実行 | 説明文（メタディスクリプション）は WordPress コアの REST に無く SEO プラグイン依存。目次構成の変更は本文の大部分を書き換え、誤反映時の被害が大きい（Q-001） | 冒頭書き換えの実行率・元に戻す率を見てから |
| 実行前のプレビュー・差分確認画面、修正案の手直し | 依頼のフローは「リンク→実行→自動修正」であり、ユーザー操作を増やさない方針（§1.12.6）。誤反映は「元に戻す」で担保する（R-001） | 元に戻す率が高い場合 |
| メール内のワンクリック実行（署名付きトークンでログインなし実行） | 依頼文は「リンクにアクセスし『実行』をクリック」。メール転送で第三者が記事を書き換えられる経路を作らないため、ログイン必須の画面で実行する | — |
| 完全自動実行（ボタンなしで反映） | 依頼は「半自動」。承認点を残す | クライアント合意後 |
| 実行後の効果測定 UI（狙いの点数に届いたか） | 次回の評価サイクルの結果と前回差分（既存表示）で確認できる | — |
| 修正ログの一覧画面（記事横断）・検索・エクスポート | 記事詳細で追えれば足りる（§1.12.6「履歴を追えればよい」） | 記事数が多く横断確認の要望が出たら |
| 実行の停止機構（feature flag・Kill Switch） | `AGENTS.md` Core Rules。誤反映は記事単位で「元に戻す」、機能全体はデプロイ巻き戻しで止められる | — |
| WordPress 認証情報の暗号化 | 書き込み利用で影響が増すが、既存の別計画 `docs/plans/oauth-credential-encryption-design.md` の範囲 | 同計画の実施時 |
| WordPress のリビジョン機能を使った復元 | REST API に復元エンドポイントが無く、結局 PUT で書き戻すことになる。修正ログの変更前本文で足りる | — |

### 入力・出力・状態遷移

- 入力値: 実行 = `annotationId` と `ga4ContentEvaluationHistoryId`。元に戻す = 修正ログ `id`。いずれも Zod で UUID 検証。
- 正常時の出力: 修正ログ1件（変更前・変更後の冒頭テキストを画面表示用に含む）。
- エラー時の出力: `ServerActionResult` の `error`（`ERROR_MESSAGES` に追加）。

| エラー | ユーザー向け表示（案） | ログ状態 |
| --- | --- | --- |
| 提案が最新でない（BR-02） | 新しい評価が出ているため、この提案は実行できません | 記録しない |
| 実行済み・実行中（BR-03） | この提案はすでに実行されています | 記録しない |
| WordPress 未連携・認証切れ（401） | WordPress との連携を確認してください（`/setup/wordpress` へのリンク） | `failed` |
| 権限不足（403。アプリケーションパスワードのユーザーに編集権限がない） | WordPress のユーザーにこの記事の編集権限がありません | `failed` |
| 記事が見つからない（404） | WordPress に記事が見つかりません | `failed` |
| 冒頭を特定できない（BR-04） | この記事は見出し（h2）が無いため、冒頭を自動で書き換えられません | `failed` |
| LLM 失敗・出力検証失敗・タイムアウト | 修正文を作成できませんでした。時間をおいて再度お試しください | `failed`（WordPress は未更新） |
| WordPress 更新失敗 | WordPress への反映に失敗しました | `failed` |

- 状態と遷移（修正ログ `status`）:

```text
（なし）→ running → applied → reverted
              └→ failed → running（再実行）
running が 10 分以上続いた行は failed とみなし再実行を許す（プロセス異常終了の救済）
```

- 冪等性・重複実行時の挙動: 評価履歴 ID に一意制約。実行開始時に `running` 行を作る（既存行が `failed` または 10 分超の `running` の場合のみ条件付き更新で `running` に戻す）。作成・更新できなければ BR-03 のエラー。元に戻すは `applied → reverted` の条件付き更新で二重実行を防ぐ。
- 実行順序: ①ログ `running` 作成 → ②WordPress raw 取得 → ③冒頭抽出 → ④LLM → ⑤置換後本文で WordPress 更新 → ⑥ログを `applied`（変更前・変更後全文）に更新 → ⑦本文キャッシュ更新。⑤成功・⑥失敗の場合は `console.error` に変更前本文を含めず、ログ ID・記事 ID・時刻を出す（変更前本文は②の時点でログ行に先に保存しておき、⑥で失われないようにする）。

  | 実行可能（BR-01・BR-02 を満たし、ログなし or `failed`） | 「実行」ボタン | 実行 | — |
  | 実行中 | スピナー＋「記事の冒頭を書き換えています...」 | なし | ボタン無効 |
  | `applied` | ボタンの代わりに「実行済み（日時）」 | 修正ログで元に戻す | 再実行不可 |
  | `reverted` | 「元に戻しました（日時）」 | なし | 再実行不可（新しい評価を待つ） |
  | `failed` | 失敗理由（§6 エラー表）＋「実行」 | 再実行 | — |

- 画面遷移: メールのリンク → ログイン（未ログイン時）→ 本画面（コンテンツ評価タブ）。
- UI 用語: 「実行」「修正ログ」「元に戻す」。`ui-text.md` に辞書が無ければ追記する。

#### 誤読しやすい罠

- 「コンテンツ評価履歴」（評価の履歴）と「修正ログ」（記事を書き換えた履歴）は別物。見出しで区別し、混在させない。
- 「今すぐ評価を実行」と「実行」は別操作。後者は「次の一手」の箱の中にだけ置く。

## 11. トレードオフ判断

### ALT-001: 書き換え範囲

- 比較した案: 案A 冒頭（最初の h2 より前）だけを置換 / 案B 本文全体を LLM に書き換えさせる
- 採用案: 案A
- 採用理由: `R_TOP_EXIT` の「次の一手」は書き出しの修正であり、範囲を限るほど誤反映の被害と LLM コストが小さい。h2 以降をバイト一致で保てるため、装飾（色・画像・ショートコード）を壊さない（クライアントは WordPress 側の装飾を活かしたい意向。`client-vision-from-lark.md` §1.3）。
- 却下した案と理由: 案B は装飾・ショートコードの欠落リスクが高く、変更差分の確認も難しい。
- 将来変更する条件: 目次構成（`R_MID_EXIT`）を対象にするとき再検討。

### ALT-002: LLM の出力形式

- 比較した案: 案A 段落テキストの配列（JSON）をコードが HTML／ブロックに組み立てる / 案B LLM が HTML を直接返す
- 採用案: 案A
- 採用理由: 不正な HTML・スクリプト混入・ブロックコメント破損を構造的に防げる。
- 却下した案と理由: 案B は検証・無害化の実装が大きい。
- 影響: 冒頭内のリンク・太字などの装飾は書き換え後に失われる（R-002）。

### ALT-003: 修正文の生成タイミング

- 比較した案: 案A 「実行」を押した時に生成 / 案B メール送信時（バッチ）に生成して保存
- 採用案: 案A
- 採用理由: 実行されない提案に LLM コストを使わない。実行時点の最新本文に対して書き換えられる（バッチ後にユーザーが WordPress を編集していても上書き事故にならない）。
- 却下した案と理由: 案B はプレビューを出す場合に必要だが、プレビューは Non-goal。
- 将来変更する条件: プレビューを入れるとき。

### ALT-004: 実行の入口

- 比較した案: 案A ログイン必須の記事詳細で実行 / 案B メール内の署名付きリンクでワンクリック実行
- 採用案: 案A（依頼文どおり）
- 採用理由: メール転送で第三者が記事を書き換えられる経路を作らない。署名付きリンクの仕組みは未実装で新規になる。

### ALT-005: 実行提案の元にする評価

- 前提: GSC（検索順位）と GA4（コンテンツ評価）は `gsc_article_evaluations` の1行の設定を共有し、`gsc-evaluate` と `ga4-content-evaluate` が同じ毎時0分に別ジョブとして起動する（起動順は非決定。進捗列は系統別）。手動の「今すぐ評価を実行」は GSC → GA4 の順に直列実行する。
- 比較した案: 案A GA4 の「次の一手」だけを使う / 案B GSC と GA4 の結果を統合してボトルネックを1つ選び、1通で提案する
- 採用案: 案A
- 採用理由: GA4 評価は診断コードで書き出し・タイトル・目次構成のどこがボトルネックかをすでに1つに絞っており、既存のメール送信（`ga4ContentEvaluationBatchService.ts:758-831`）に分岐を足すだけで済む。
- 却下した案と理由: 案B は GSC の改善提案が別ジョブ（`gsc-suggestions`）で後から生成されるため、両方の完了を待ってから送る送信フローへの組み替えが必要（工数 1.5〜2 倍見込み）。GSC の提案は Markdown の指示表で、そのまま反映できる形でもない。
- 将来変更する条件: GA4 側の実行が使われ、GSC 側の提案も実行したいという要望が出たとき。
- 判断者・判断日: ユーザー・2026-10-16

## 13. テスト・リリース・ロールバック

### テスト方針

- 単体:
  - 冒頭抽出・置換の純関数: ブロックエディタ／クラシック、`<h2` なし、冒頭空、h2 前に画像ブロックのみ、h2 以降がバイト一致すること、テキストの HTML エスケープ（`<script>` を含む段落）。
  - LLM 出力スキーマ: 段落数・文字数上限、JSON フェンスあり／なし。
  - メール文面: BR-01 の各条件で実行提案版／従来版が選ばれること、案内文の文言。
  - Server Action: ロール拒否、BR-02（最新でない）、BR-03（`applied`／`running`／10分超の `running`／`failed` からの再実行）、BR-06（本文不一致で書き戻さない）、WordPress の 401/403/404・LLM 失敗で WordPress 更新を呼ばないこと。
- 実画面確認: テスト用 WordPress（WordPress.com・セルフホスト各1）で S-03・S-07・S-08 を手動確認。
- 品質ゲート: `npm run verify`。

### リリース方針

- migration（テーブル・RLS・prompt_templates）→ アプリの順で適用。Feature Flag なし。
- 本番確認: 自社記事で実行→元に戻すを1回ずつ。

### ロールバック方針

- アプリ: デプロイ巻き戻し（メールは従来版に戻る）。
- DB: テーブル drop と prompt_templates 行削除の逆 migration を用意する。修正ログは失われるため、drop 前に必要なら export する。
- データ不整合時: 記事単位で修正ログの `before_content` から復元。
- 判断者: ユーザー。
