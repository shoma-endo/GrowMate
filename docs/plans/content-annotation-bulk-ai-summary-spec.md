## 1. 背景・目的・成功指標

### 背景・解決したい課題

- 現在、誰が、どの業務で困っているか:
  - `admin` / `paid` 利用者が `/wordpress-import` で大量記事を取り込んだあと、チャット右パネルまたはコンテンツ一覧の編集モーダルで **1件ずつ「AIで要約」** する必要がある
  - 出典の引用（`docs/context/client-vision-from-lark.md` §1.9.3、verbatim）: 「**インポート直後に「AI 要約」と「初回評価」を自動開始**したい。現状は 100〜200 件を手動で「評価を開始」しており負荷が高い。」
  - 本仕様側の解釈（引用と分離）: 引用にある「100〜200 件を手動で」という運用規模は、出典上は**「評価を開始」**の操作について述べられたものである。要約も同じ母集団に対して1件ずつ実行する導線しかないため、同規模のクリック負荷がかかると本仕様では見込む。要約の自動開始要望自体は同じ引用文の前半に含まれる
- 放置した場合の影響:
  - 要約8項目が空のまま残り、以降の評価・記事改善の前提データが揃わない
  - インポート時自動は合意上後回しのままなので、一覧側の代替が無いと手動1件運用が続く

### 目的

- この開発で実現する状態:
  - `/analytics` で「未要約」記事をフィルタし、選択した複数件を **1操作で AI 要約**できる
  - 時間予算内に終わらなかった分は、同じフィルタで再実行して回収できる
- 利用者・事業にとっての価値:
  - 単記事ボタンを廃さずに、インポート後の初期セットアップコストを下げる

### 成功指標

| 指標 | 現状 | 目標 | 測定方法 | 測定時期 |
| --- | --- | --- | --- | --- |
| 要約開始の操作回数 | 対象 N 件なら編集 UI を N 回開いて要約 | 「未要約」フィルタ下で全選択し 1 回の操作で、時間予算内の件数を要約 | 手動確認（成功件数通知） | 受入時 |
| 未要約の発見〜実行 | フィルタ無し・1件操作のみ | チェック常時 →（推奨）「未要約」ON → 選択／全選択 → 「AIで要約」 | 画面確認 | 受入時 |

## 3. 業務要件と業務フロー

### 現状（As-Is）

```text
WordPress 一括インポート
  -> コンテンツ一覧に記事が増える（要約8項目は空が多い）
  -> 記事ごとに編集 UI を開き「AIで要約」を押す
  -> を N 回繰り返す
```

### 導入後（To-Be）

```text
WordPress 一括インポート（本仕様では変更しない）
  -> /analytics で行チェック／全選択で対象を選ぶ（チェック列は常時表示）
  -> 「未要約」フィルタを ON にする（ボタン活性の条件。OFF のまま選択しても「AIで要約」は出ない／理由表示）
  -> 「AIで要約」を押す
  -> システムが時間予算まで既存の単記事要約処理を逐次実行
  -> 成功 M / 失敗 F / 未実行（時間切れ）U を通知し、一覧を再取得
  -> 成功分は未要約フィルタ結果から消える（同フィルタ ON 時）。残りは再実行または単記事ボタンで回収
```

### 業務ルール

- ルール ID: BR-01
- ルール: 一括要約の対象は、利用者がチェックした記事のうち **未要約**（BR-02）かつ実行時点でも本人所有のものに限る。UI 上は「未要約」フィルタ ON 時に実行ボタンを出すため、推奨導線では表示行＝未要約である。フィルタ OFF でもチェックは可能だが、実行ボタンは出さない（BR-04）
- 例外: 実行までの間に手入力等で8項目が埋まった ID が混在した場合は、その件を `skippedCount`（§6 正常時の出力）に計上し、**失敗には含めない**。他件の処理は継続する（全体失敗にはしない）。成功扱いの上書きはしない
- 実装箇所: この事前再検証は既存の単記事コアには**無い**（`src/server/services/contentAnnotationSummaryService.ts` の `generateSummary` に充填チェックは無く、`saveSummary` は無条件 UPDATE。単記事設計 §2.3 も「確認ダイアログなしで全て上書き」が正本）。したがって**一括 Server Action 側で `generateSummary` 呼び出し前に対象 ID の8項目を再取得して判定する**。コアをそのまま呼ぶと手入力値を黙って上書きし、履歴が無い（§4 Non-goals）ため復旧できない

- ルール ID: BR-02
- ルール: **未要約**とは、AI要約対象8項目（`main_kw`, `kw`, `needs`, `persona`, `goal`, `prep`, `opening_proposal`, `basic_structure`。単記事設計 §2.1）がすべて未設定（NULL または trim 後空文字）**かつ** WordPress 連携済み（`wp_post_id` が正の数、または `canonical_url` が trim 後非空。単記事要約の活性化条件と同型）であること
- 例外: なし

- ルール ID: BR-03
- ルール: 1回の操作は **時間予算内**に逐次要約し、予算超過時点で打ち切る。打ち切り分は未実行件数（`unprocessedCount`）とする。自動リトライ基盤は作らない。時間予算は **`/analytics` の Server Action 実行枠に合わせる**。
  - **全体予算**: ページの `maxDuration`（現状 `app/analytics/page.tsx` で **800秒**）からレスポンス返却余裕 **40秒** を引いた **760秒**（`src/lib/constants.ts` の `INSTAGRAM_SYNC_TIME_BUDGET_MS` と同型の算出）。実装時は定数化し、`maxDuration` リテラルとズレないことをテストで担保する（Instagram／cron 系と同方針）
  - **チェック方式**: 着手前の予算判定「だけ」では成立しない。Instagram 同期の1単位は HTTP 1往復（数秒）だが、本仕様の1単位は WordPress 本文取得＋LLM 呼び出しで、既存単記事コアの LLM タイムアウトは **180秒**（`src/server/services/contentAnnotationSummaryService.ts` の `timeoutMs`）。着手前判定のみだと経過759秒で判定を通過した1件が180秒走って経過939秒に達し、`maxDuration` 800秒で Vercel にハードキルされる。成功分は1件ずつ DB にコミット済みなのに応答が返らず、**AC-04 の件数通知と AC-05 の未実行件数報告がどちらも成立しない**。40秒の余裕は「1単位＝数秒」前提の値なので、そのままでは流用できない
  - **したがって**、各件の LLM 呼び出しには「全体予算の残り − 後段処理予算」から算出した `timeoutMs` を**動的に渡す**。同一リポジトリの既存パターン `src/server/services/googleAdsAiAnalysisService.ts` の `computeLlmTimeoutMs`（`maxDuration*1000 − 経過 − GOOGLE_ADS_AI_EVALUATION_POST_LLM_BUFFER_MS`（30,000ms、`src/lib/constants.ts`）を LLM の `timeoutMs` に渡す）と同型とする
  - 残り時間が後段処理予算以下になった時点で、以降の件は**着手せず** `unprocessedCount` に計上してレスポンスを返す
  - **逐次処理の順序は §6「実行順序」に従う（`updated_at` 昇順）**。打ち切りが発生する規模では、順序が再実行時の前進可否を決めるため
- 例外: なし。`maxDuration` を将来変更する場合は時間予算も同じ算出で追従する

- ルール ID: BR-04
- ルール: **行チェック・全選択は常時表示**する（フィルタ OFF でも可）。**一括「AIで要約」ボタンは「未要約」フィルタ ON かつ選択≥1 のときだけ**活性表示する。フィルタ OFF で選択≥1 のときは実行ボタンを出さず、ツールバーに理由を1行出す（例: 「未要約フィルタを ON にすると要約できます」）。フィルタ OFF・未選択ではチェック列のみ
- 例外: なし

- ルール ID: BR-05
- ルール（2026-08-29 改訂。母集団の正本は本仕様ではない）: 「全選択」の対象は **利用者が所有する全記事**（表示中のページにも適用中のフィルタにも依存しない）とする。対象 ID の解決はサーバー側で行う（§6 入力）。**件数は絞り込み後の一覧の総件数表示（`total_count`）とは一致しない**（母集団が絞り込みに依存しないため、通常はそれより大きい）。
- ルール（正本の所在）: `/analytics` の行チェック・全選択は評価サイクル一括開始と **1本を共有**する（`docs/plans/analytics-bulk-actions-impl-note.md` §3.1）。共有コントロールは母集団を1つしか持てないため、**母集団の定義の正本は `docs/plans/gsc-bulk-evaluation-start-spec.md` BR-07** とし、本ルールはそれを参照する。2026-08-29 の PO 回答（同仕様 §12 Q-008）で、旧定義（全フィルタ条件の AND 結果の全件・件数は `total_count` と一致）から本定義へ改訂した。
- ルール（**全選択後の個別解除**。2026-08-31 追加。正本は評価親 BR-07「全選択後の個別解除」）: 全選択のまま表示中の行のチェックを外したときは、**全選択を解除せず、その記事だけを母集団から除外**する。行チェック・全選択は評価一括と1本を共有するため、要約一括も同じ挙動になる。サーバーへは全選択の入力に除外 ID の配列を添える。
- ルール（要約対象の絞り込みは別軸）: 母集団が全記事になっても、**実際に要約されるのは未要約（BR-02）の記事だけ**である。サーバーは要約済みをスキップする（BR-07）。「AIで要約」ボタンの活性条件（「未要約」ON かつ選択≥1。BR-04）は**維持する**
- 例外: 総件数が BR-06 の上限 1000 を超える場合は、一覧と同じ並び順（現行 RPC の `updated_at` 降順）の**先頭1000件**に丸める。丸めたことは選択件数表示で「1000 / 全 M 件」と明示し、無言の打ち切りにしない（`docs/context/db-row-limits-and-data-truncation.md` 最重要メッセージ）

- ルール ID: BR-06
- ルール: 1回の選択／実行上限は **1000件**。根拠は「1操作で扱う件数の運用上限」であり、時間予算760秒で実行できる件数（1件あたり最長180秒の LLM 呼び出しを含む）を十分に上回る値として1000を置く。一括 Server Action は 1001 件以上の入力を実行せずエラーにする。全選択は BR-05 の例外で先頭1000件に丸めるため、通常の UI 操作でこのエラーは発生しない（サーバー側の上限検証は直叩き対策として残す）。実行件数は時間予算でさらに小さくなることがある
- 例外: なし
- 根拠に**しない**もの（過去の誤記の訂正）: (a) PostgREST `db-max-rows`（GrowMate では 1000）は**返却行数**の上限で、Server Action の入力配列件数とは無関係（`docs/context/db-row-limits-and-data-truncation.md` §1）。現行の一覧 RPC は jsonb 集約の1行返しでそもそも当該上限に当たらない。(b) WordPress 一括インポートの 1000 は**1回のインポートあたり**の上限（`src/server/actions/wordpressImport.actions.ts`）であり、複数回インポートすれば未要約は 1000 件を超えうる

- ルール ID: BR-07
- ルール: 実行可能なロールは `admin` / `paid` のみ。**サーバー側（一括 Server Action）で必ず拒否する**。画面側は `/analytics` の既存ルートゲート（`proxy.ts` の `PAID_FEATURE_REQUIRED_PATHS`）で到達自体が限定されるため、一覧コンポーネントに新規のロール分岐は追加しない
- 例外: `trial` / `unavailable` は対象外。既存の **単記事**要約経路の role 強制追加は本仕様の Non-goals（評価一括と同方針）

- ルール ID: BR-08
- ルール: 個別記事の要約失敗時は、当該記事の既存 `content_annotations` 値を変更しない（単記事設計の Memory Write Policy と同じ）。成功した他記事の結果は維持する（部分成功）
- 例外: なし

- ルール ID: BR-09
- ルール: 評価サイクル一括開始（`gsc-bulk-evaluation-start`。**仕様書 `docs/plans/gsc-bulk-evaluation-start-spec.md` は `approved` で実在し、実装のみ develop に未着手。2026-08-27 実測**）と **ボタン・Server Action・処理を統合しない**。チェック列は両仕様とも常時表示し共有しうる（共有チェック列の契約は `docs/plans/analytics-bulk-actions-impl-note.md` §3。本仕様 BR-04 / FR-002 / AC-02 が共有列の正本で、評価側の GSC 条件を共有列へ持ち込まない）。実行ボタンは各仕様の条件でそれぞれ出す（**評価側はフィルタ非依存で、GSC 連携済みかつ選択≥1 なら「評価サイクルを開始」を出す**。評価親 BR-06 / FR-010。2026-08-29 Q-007 でゲート撤廃。非対称の理由は同 BR-06。要約側は「未要約」ON かつ選択≥1 で **「AIで要約」**）。選択状態の共有は必須としない。実行時は各ボタンが自仕様の対象条件をサーバーで再検証する
- 例外: なし

- ルール ID: BR-10
- ルール: 一括実行前の確認ダイアログは出さない。単記事要約（確認なし上書き）に合わせる。未要約フィルタにより、通常は空欄記事のみが対象
- 例外: なし

## 4. 対象範囲と Non-goals

> **判断軸: GrowMate は MVP 開発を最優先とする**（`CLAUDE.md` Core Rules）。

### 対象範囲

- 画面・操作: `/analytics` に「未要約」フィルタ、常時の行選択・全選択、および「未要約」ON 時の一括「AIで要約」。詳細は §6 画面設計
- API・外部連携: 既存の単記事要約処理（WordPress 本文取得＋Claude／機械抽出）を複数件向けに逐次呼び出す。プロンプト・抽出ロジックの作り直しはしない
- データ・DB: `get_filtered_content_annotations` 等への **未要約フィルタ条件の追加**（migration）。`content_annotations` の要約8項目更新は既存要約書き込み経路を再利用
- 権限・ロール: `admin` / `paid`。一括経路のサーバー側で強制
- ドキュメント: `.agents/skills/growmate-ui-ux/ui-text.md` への新規用語追記（§6 UI用語）。`README.md` の `## 🚀 主な機能` が更新対象になりうる（最終判断は `spec-to-pr` の `readme_sync` に委ねる）
- 運用・監視: 新規の監視ダッシュボード・Kill Switch・feature flag は作らない

### Non-goals（今回の対象外）

| 対象外 | 理由 | 将来検討する条件・時期 |
| --- | --- | --- |
| WordPress インポート時の AI 要約自動実行 | §1.9.5 の後回し合意を維持。本仕様は一覧一括で代替 | クライアントが後回しを明示撤回し、件数・コスト・時間予算に合意したとき |
| 評価一括とのボタン／処理の統合 | 依存・コスト・対象集合・失敗モードが異なる（Grill 合意） | 運用上どうしても1操作化が必要なフィードバック時 |
| 時間切れ・失敗分の自動リトライ基盤／キュー／常駐ジョブ | 要件に無い基盤。再フィルタ＋再実行と単記事ボタンで回収 | 未実行が常態化し手動回収が破綻したとき |
| Kill Switch・feature flag・監視ダッシュボード新設 | 要件に無い。壊れたときはデプロイ巻き戻しと UI 非表示 | 該当なし |
| 要約結果の履歴・バージョン管理 | 単記事設計と同じく最新値のみ | 単記事側で履歴が先に入ったとき |
| 単記事「AIで要約」の廃止・確認ダイアログ追加・コアロジック作り直し | 一括はトリガー追加。コアは再利用 | 単記事 UX の別要件 |

## 5. 開発工数（概算）

対象範囲（§4）が固まった時点の概算（grill-to-gherkin 承認時点）。**金額・単価は書かない。**

### 前提

- 換算: 8時間 = 1人日

### 入力・出力・状態遷移

- 入力値・形式・必須条件:
  - **個別選択時**: `contentAnnotationId[]`（1件以上、最大1000。サーバーでも上限検証）
  - **全選択時**: クライアントは ID 配列を送らない。**画面の絞り込み状態も送らない**（母集団はフィルタ非依存。BR-05）。サーバーは利用者の全記事を `updated_at` 降順で解決し、先頭1000件へ丸める。画面は10件／ページ固定（`app/analytics/page.tsx` の `perPage`）でクライアントは表示中ページ分の ID しか持たないため、クライアント送信では BR-05 のページ跨ぎ全件を満たせない（＝サーバー側解決が唯一の実装）
    - 解決クエリは既存 `get_filtered_content_annotations` と同じ **jsonb 集約の1行返し**（`RETURNS TABLE(items jsonb, total_count bigint)` と同型）を踏襲し、PostgREST `db-max-rows`（1000）に当たらないようにする（主経路）
    - 行返しにする場合のみ、**`SupabaseService` 内に解決メソッドを追加して `this.fetchAllPaged` を使う**。`src/server/services/supabaseService.ts` の `fetchAllPaged` は `protected` 宣言でクラス外から呼べない（`src/server/services/analyticsContentService.ts` は `SupabaseService` を継承せず `getClient()` 経由で使う構成）。既存の `getContentInventoryForMatching` と同型にし、`db-max-rows` 未満のページサイズと決定的な並び順（タイブレーク付き）を指定する
    - **1000件超の判定は解決結果の配列長ではなく `total_count` で行う**（`docs/context/db-row-limits-and-data-truncation.md` §3(d): `length >= limit` での打ち切り検知は不可）
- **実行順序（対象 ID の解決順序とは別に定める）**:
  - 選択ウィンドウ（BR-05 の先頭1000件）は一覧と同じ **`updated_at` 降順**で決めるが、一括 Server Action 内の**処理順序は `updated_at` 昇順（同値は `id` でタイブレーク）＝古い順**とする
  - 理由: 既存コアが呼ぶ `fetchWpPostContentLive`（`src/server/services/wordpressContentSync.ts`）は WordPress 本文取得に成功した時点で `updateContentCache` を呼び、`updated_at` を現在時刻で更新する。この更新は本文サイズ判定と LLM 呼び出しより**前**にあるため、**WP 取得は成功したが要約が後段で失敗した記事（LLM 失敗・パース失敗・本文サイズ超過・8項目すべて空）も、未要約のまま `updated_at` だけが最新化される**
  - 一覧 RPC は `ROW_NUMBER() OVER (ORDER BY f.updated_at DESC NULLS LAST)`（`supabase/migrations/20260809100000_add_gsc_unstarted_evaluation_filter.sql`）なので、降順のまま処理すると失敗記事が次回実行でキュー先頭に戻る。とくに本文サイズ超過（`CONTENT_ANNOTATION_SUMMARY_MAX_CONTENT_CHARS = 80_000`、`src/lib/constants.ts`）は本文が縮まない限り**毎回必ず失敗する決定的失敗**で、先頭に単調に蓄積する。本仕様は自動リトライ基盤を作らず**再実行が唯一の回収経路**（§4 Non-goals・R-001）であるため、その先頭が塞がれると前進件数が0になりうる
  - 昇順にすれば失敗記事は次回の末尾へ回り、未着手記事が必ず先に処理される。**新規の除外リスト・連続失敗カウンタ・デッドレター等は作らない**（順序の指定のみで足りる）
- 正常時の出力:
  - `{ success: true, data: { succeededCount, failedCount, skippedCount, unprocessedCount, stoppedReason } }` 相当（命名は実装時）
    - `succeededCount`: 要約が成功し、8項目のいずれかが非空で保存された件数
    - `failedCount`: 本文取得失敗・LLM 失敗・パース失敗・8項目すべて空（下記「状態と遷移条件」）
    - `skippedCount`: 実行時点で既に8項目が埋まっていた件数（BR-01）。**再実行しても対象外**
    - `unprocessedCount`: 時間予算切れで着手しなかった件数（BR-03）。**再実行すれば進む**
    - `stoppedReason`: `'completed' | 'time_budget'`
    - 分離する理由: 統合カウンタでは「再実行すれば進む分」と「何度実行しても対象外の分」を利用者が区別できず、再実行を無駄に繰り返す。既存の同型実装も分離済み（`src/types/instagram.ts` の `InstagramSyncResult` は `synced/failed/skipped/truncated/stoppedReason`、`src/server/services/gscEvaluationService.ts` は `stoppedReason` と `usersSkippedDueToLimit`）
  - UI: 件数通知（4カテゴリ）。一覧再取得
- エラー時の出力:
  - 未認証／権限なし／選択0件／1000件超／サーバーエラーを区別可能なメッセージ
- 状態と遷移条件:
  - 未要約 →（要約成功**かつ8項目のいずれかが非空**）→ 未要約フィルタ対象外
  - **8項目すべてが空（NULL または trim 後空文字）で返った場合は成功にせず `failedCount` に計上し、既存値は変更しない（BR-08）**。理由: `src/server/schemas/contentAnnotationSummary.schema.ts` の `contentAnnotationAiSummarySchema` は全フィールドが `z.string()` で `.min(1)` を持たず空文字が通る。サービス側は `.trim() || null` で null 化し、`opening_proposal` / `basic_structure` も機械抽出が空なら null になるため、8項目すべて null でも保存自体は成功しうる。これを成功と数えると記事は未要約のまま残り、再実行のたびに WordPress 取得と Claude 呼び出しを繰り返す（R-004 の費用リスクに直結）
  - 失敗／未実行 → 未要約のまま
  - スキップ（実行時点で既に埋まっていた） → 元から未要約ではないため、一覧再取得後は未要約フィルタ結果に現れない
- 冪等性・重複実行時の挙動:
  - 既に8項目が埋まっている ID は上書きせず `skippedCount` へ（BR-01）。空のまま再実行は通常の要約成功になりうる

#### 誤読しやすい罠

- 「AIで要約」＝評価サイクル開始ではない。評価は別仕様・別ボタン。チェック列は共有しうるが、ボタンは別
- チェック列は常時だが、要約できるのは「未要約」ON のときだけ。フィルタ OFF で選んでも実行ボタンは出ず、理由表示が出る
- 時間予算で打ち切られてもインポートや一覧自体の失敗ではない。未実行件数を見て再実行する
- 「スキップ」と「未実行」は別物。スキップ＝既に埋まっていて対象外（再実行しても変わらない）、未実行＝時間予算切れ（再実行すれば進む）
- 全選択が「1000 / 全 M 件」と出るのは異常ではない。1回で扱える上限まで丸めた表示で、残りは再実行で回収する
- 行チェックによる選択は**表示中ページ内に限る**。ページ送りは URL ナビゲーション（`app/analytics/page.tsx` の `prevHref` / `nextHref` が `/analytics?page=...` を返す）で Server Component が再描画されるため選択状態はリセットされる。ページを跨いだ一括は全選択（BR-05）を使う。ページ跨ぎで行チェックを保持する状態管理は作らない（MVP 最優先）
- 要約に失敗した記事も、WordPress 本文取得の副作用で更新日時が新しくなる。一覧の並び順は変わるが、一括実行は**古い順**に処理する（§6 実行順序）ため、未着手分が後回しになることはない
- 未要約フィルタは WordPress 未連携を含まない。連携前の空欄記事は対象外
- **「全選択」は画面の絞り込みに従わない**（2026-08-29 改訂）。「未要約」ON で絞っていても選ばれるのは全記事で、選択件数が一覧の総件数より大きくなるのは正常。要約済みはサーバーが実行直前の再検証でスキップする（BR-01 / BR-07）。**実行ボタンは「未要約」ON が条件のまま**なので、絞ってから押す導線は変わらない（評価一括はこのゲートを撤廃したが、要約は LLM 呼び出しのコストが取り消せないため維持する。評価親 BR-06）

#### 一次情報の引用（verbatim）と解釈

- **WordPress REST API**（https://developer.wordpress.org/rest-api/reference/posts/ 、2026-08-24 確認）
  - 引用（verbatim）: `GET /wp/v2/posts/<id>` / `id` — "Unique identifier for the post"
  - 解釈（引用と分離）: 単記事要約と同じ経路を件数分だけ繰り返す。**同ページにレート制限・スロットリングの記載は無い**ため、WordPress 側のレート制限は断定せず「実機観測が必要」として扱う（本仕様では上限値を仮定しない）
- **Anthropic Rate limits**（https://platform.claude.com/docs/en/api/rate-limits 、2026-08-24 確認）
  - 引用（verbatim）: "The rate limits for the Messages API are measured in requests per minute (RPM), input tokens per minute (ITPM), and output tokens per minute (OTPM) for each model class. If you exceed any of the rate limits you will get a 429 error describing which rate limit was exceeded, along with a `retry-after` header indicating how long to wait."
  - 引用（verbatim）: "Limits are set at the organization level."
  - 解釈（引用と分離）: 本仕様は1件ずつ逐次呼び出すため RPM 超過の可能性は低い。ただし ITPM / OTPM は**組織単位の共有資源**であり、cron の GSC 評価や Google Ads 分析と同時に走れば 429 は起こりうる。その場合も当該件の失敗として計上するのみで、自動リトライ基盤は作らない（§4 Non-goals）

#### 連携ライフサイクル（WordPress 認証情報の失効）

- 既存単記事コアは `ReadonlyRequestCookies` を受け取り、wp.com の場合は cookie にトークンがあれば `refreshWpComAccessToken` を呼ばない（`src/server/services/wordpressContentSync.ts`）。cookie 値はリクエスト開始時点で固定されるため、760秒のループ中に失効すると以降の全件が本文取得失敗になりうる
- 挙動: 本文取得失敗は当該件のみ失敗として計上し、既存値は変更しない。長時間実行中に WordPress 認証情報が失効した場合も同じ経路で失敗に計上される（残り全件が失敗になりうる）。**データ破損は起きず**、利用者が画面を開き直して再実行すれば新しい認証情報で再取得される
- **専用の失効検知・再認証導線は本仕様では作らない**（要件に無い安全機構。MVP 最優先）

### テスト方針

### リリース方針

- 通常デプロイ。Feature flag なし
- DB: 未要約フィルタ用 migration をアプリより先または同時適用（**適用順序は「DB → アプリ」**）

### ロールバック方針

- **逆適用順序は「アプリ → DB」**。アプリ巻き戻しで一括 UI／Action を無効化する
- migration の逆適用方針（**確定。2026-08-27 に実測へ訂正。「フィルタ列追加のみ」および「7 → 8 引数」という旧記述はいずれも事実誤認だった**）:
  - 未要約フィルタの追加は列追加ではなく `get_filtered_content_annotations` の**引数追加＝関数シグネチャ変更**である。`CREATE OR REPLACE` は引数リストが変わると置き換えにならない（`supabase/migrations/20260809100000_add_gsc_unstarted_evaluation_filter.sql:10` に同趣旨のコメントと `DROP FUNCTION` が記録されている）
  - **起点は現行最新の8引数版**である。`supabase/migrations/20260818000300_update_get_filtered_content_annotations_for_ga4.sql:6-15` が `p_user_id, p_page, p_per_page, p_selected_category_names, p_include_uncategorized, p_has_unread_suggestion, p_has_unstarted_gsc_evaluation, p_has_unstarted_ga4_evaluation` の8引数を定義している。したがって本仕様の変更は **8 → 9 引数**である（旧記述の「7 → 8」は、GA4 統合 migration `20260818000300` を見落として1つ前の `20260809100000`（7引数）を最新と誤認したもの）
  - 順適用: 8引数版を `DROP FUNCTION` → 9引数版を `CREATE` → `REVOKE EXECUTE ... FROM PUBLIC, anon, authenticated` と `GRANT EXECUTE ... TO service_role` を**再実行**する（`20260818000300` の `:93-94` と同型。引数リストは9引数版のものに書き換える）
  - 逆適用: 9引数版を `DROP FUNCTION` し、**`20260818000300_update_get_filtered_content_annotations_for_ga4.sql` の8引数定義を再適用**する。同ファイルは `:93-94` に8引数版の `revoke` / `grant` を持つため、ファイル全体を再適用すれば権限も復元される
  - **逆適用先を `20260809100000`（7引数版）にしてはならない。** `p_has_unstarted_ga4_evaluation` を持たない7引数版が復元され、GA4 評価フィルタと GA4 射影フィールドが失われて `/analytics` の GA4 表示が壊れる
