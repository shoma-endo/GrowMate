- **現状（2026-09-10確認）**: 上記2点はいずれも未実装。
  - ロジック説明: `EvaluationHistoryTab.tsx` の「AIの改善提案内容」ダイアログに、ステージ進行ロジックの説明文は存在しない（評価日・判定・前回順位・現在順位・改善提案の4項目のみ）。
  - メモ機能: `gsc_article_evaluation_history` テーブル、`gsc_article_evaluations` テーブルのいずれにもメモ用カラムは存在しない（`supabase/migrations/` 全件確認）。
- 放置した場合の影響: クライアントが「既読=次のステップに進む条件」と誤認したまま運用し、記事の改善判断（次にどの段階の提案が届くか）を見誤る。改善施策の記録が残らず、傾向分析ができない。

### 目的

- ステージ進行ロジック（評価サイクルごとの順位比較による自動進行/リセット、既読ボタンとは無関係であること）を、クライアントが評価画面上で自己解決できる状態にする。
- 評価1回につきメモを1件記録・閲覧できるようにし、改善施策の履歴をアプリ内に残す。

### 主な利用シナリオ

1. **クライアントが**、評価履歴の「AIの改善提案内容」ダイアログを開いたとき、**ステージ進行の条件（いつ・何を基準に次の段階へ進むか）を読んで理解したい**。
2. **クライアントが**、ある評価回に対して実施した改善施策や気づきを**メモとして残し、後から見返したい**。

## 3. 業務要件と業務フロー

### 現状（As-Is）

```text
1. GSC評価が自動実行される（評価サイクルごと。初期値30日、ユーザーが1〜365日で変更可）。
   「今すぐ評価を実行」でも同じ評価が行われる。
2. 順位が悪化/変化なし → current_suggestion_stage が+1（上限4）。改善 → 1にリセット。
3. gsc_article_evaluation_history に評価結果・提案文（suggestion_summary）が保存される。
4. クライアントが EvaluationHistoryTab で履歴一覧→詳細ダイアログを開く。
5. ダイアログには評価日・判定・順位・改善提案のみ表示。ステージ進行の根拠や、
   過去に何を改善したかの記録は画面上のどこにも存在しない。
6. 「既読にする」ボタンは通知バッジを消すだけで、ステージ進行には無関係
   （クライアントが混同しやすい）。
```

### 導入後（To-Be）

```text
1〜3は変更なし。
4. クライアントが詳細ダイアログを開くと、評価結果の状態（成功・no_metrics・エラー）に
   かかわらず、ステージ進行ロジックの説明（§6「ロジック説明の固定文言」）が画面内に表示される。
5. 同ダイアログ内にメモ入力欄が1箇所あり、当該評価回に対する任意のメモを
   入力・保存できる。保存済みメモは同じ評価回を開いたときに再表示される。
   空欄で保存するとメモは削除される。
```

### 業務ルール

- ルール ID: BR-001
- ルール: メモは評価履歴（`gsc_article_evaluation_history` の1レコード）に対して1件のみ。上書き保存とする。
- 例外: 空欄（前後の空白を除いて空）で保存した場合は `null` を保存し、メモの削除として扱う。

### メモ保存の Server Action

- 配置: `src/server/actions/gscDashboard.actions.ts` に新規関数 `saveEvaluationHistoryMemo(historyId: string, memo: string)` を追加する
- 認証・認可: 同ファイルの `getAuthUserId`（L115-123）で認証し、未認証なら `gscAuthErrorPayload` を返す。`canWriteGa4`（`src/server/lib/ga4-permissions.ts:14-16`）が false なら `ERROR_MESSAGES.GA4.FEATURE_ACCESS_DENIED` を返し、更新しない（既存の `runEvaluationNow` L1085-1091 と同じ形）
- 保存値: `memo` が前後の空白を除いて空なら `null`、それ以外は入力値をそのまま保存する
- ユーザー境界: Service Role クライアントで書き込むため RLS は効かない（§9）。`.update({ memo })` に `.eq('id', historyId).eq('user_id', userId)` を付けて自分の行に絞る（migration の適用と型の再生成までは `asPendingClient` 経由。§10 影響するファイル）
- 0件更新の扱い: `.select('id').maybeSingle()` で結果を受け取り、`data` が無い（他ユーザーの ID・存在しない ID）なら失敗として `ERROR_MESSAGES.GSC.EVALUATION_MEMO_SAVE_FAILED` を返す（既存例: `src/server/services/gscSuggestionService.ts:210-224`）
- DB エラー時: 詳細は `console.error` に記録し、返すのは `ERROR_MESSAGES.GSC.EVALUATION_MEMO_SAVE_FAILED` のみ（DB のエラーメッセージは返さない）
- 追加する文言定数: `src/domain/errors/error-messages.ts` の `ERROR_MESSAGES.GSC` に `EVALUATION_MEMO_SAVE_FAILED: 'メモの保存に失敗しました'` を1件追加する

### 入力・出力・状態遷移

- 入力値・形式・必須条件: メモは自由記述テキスト、改行可（複数行テキストエリア）。任意入力（空欄のまま保存・既読も可。shoma.endo 回答済み（2026-09-10、§12 Q-002/Q-003））
- 文字数上限: UI と DB では上限を設けない。Server Action のリクエスト本文上限（Next.js の初期値 1MB。`next.config.ts` に `serverActions.bodySizeLimit` の設定はなく、変更もしない）を超えた場合は、保存失敗のエラートーストになる。根拠: `node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/serverActions.md:29`（2026-09-10 確認）「By default, the maximum size of the request body sent to a Server Action is 1MB」
- 正常時の出力: `toast.success('メモを保存しました')`（Sonner）
- エラー時の出力: `ERROR_MESSAGES.GSC.EVALUATION_MEMO_SAVE_FAILED` のエラートースト（Sonner）。未認可時は `ERROR_MESSAGES.GA4.FEATURE_ACCESS_DENIED` のエラートースト。クライアントは Server Action 呼び出しの例外（本文 1MB 超過で拒否された場合を含む）も捕捉し、保存失敗のエラートーストを出す。画面側で日本語文言を直書きしない
- 失敗時の入力: 入力中のメモは消さずに残す（再保存できる）
- 保存せずに閉じた場合: 入力中の内容は破棄する（確認ダイアログは出さない）。再度開くと保存済みのメモが表示される
- 状態と遷移条件: メモの有無以外に新しい状態遷移は発生しない（既読/未読の状態遷移は変更しない）
- 冪等性・重複実行時の挙動: 同一評価履歴への再保存は上書き（BR-001）

## 11. トレードオフ判断

### ALT-001: メモの保存先

- 判断: メモを既存の `gsc_article_evaluation_history` テーブルにカラム追加するか、別テーブルに切り出すか
- 比較した案:
  - 案A: `gsc_article_evaluation_history` にカラム追加
  - 案B: 別テーブル（`gsc_evaluation_memos`）を新設し、`evaluation_history_id` で1:1紐付け
- 採用案: 案A（カラム追加）
- 採用理由: カード内合意が「1回の評価毎にメモの入力欄が1箇所」という1:1の単純な関係であり、将来複数件化の要望が出ていない現時点では、新規テーブル（新たな結合・RLSポリシー管理）を追加するコストがMVP原則に見合わない
- 却下した案と理由: 案Bは1:1関係にテーブルを分ける必要性が無い割に、RLSポリシー・migrationの管理対象が増える
- 影響: 将来メモを複数件化する場合はテーブル分割への移行が必要になる可能性がある
- 将来変更する条件: クライアントから複数メモ・メモの版管理の要望が出た場合
- 判断者・判断日: Claude Code 提案（2026-09-10）。spec-review audit（2026-09-10）で妥当性を確認。既存テーブルの拡張で、最小実装ラダーの2段目

- DB変更の戻し方・逆マイグレーション: 追加した `memo` カラムは null 許容で既存処理に害がないため、アプリを戻してもカラムは残す。drop 用の migration ファイルは作らない（`supabase db push` で一緒に適用され、カラムが即座に消えるため）。drop の SQL は追加 migration 内のコメント（`-- Rollback instructions:`、既存例 `supabase/migrations/20251130050000_add_is_read_to_evaluation_history.sql`）にだけ書き、drop するとメモは消えて戻せないことを併記する
- データ不整合時の復旧: 該当なし（追加カラムのみ、既存データへの影響なし）
- ロールバック判断者: shoma.endo（依頼者）
