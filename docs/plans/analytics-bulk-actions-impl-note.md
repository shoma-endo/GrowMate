## 3. 共有UI契約（実装必須）

### 3.1 チェック列

- `/analytics` コンテンツ一覧に **行チェック・全選択を1本** 出す
- 位置は **表の最左**（既存の「操作」列よりさらに左）。「操作」列は折りたたみ可（`AnalyticsTable.tsx` の `analytics-ops-cell` / `opsWidth`）だが、チェック列は折りたたみ対象に含めない
- チェック列・全選択は **常時表示**する（要約親仕様 BR-04 / FR-002 / AC-02）。**GSC 連携状態に依存しない。** 要約一括は WordPress 連携が前提（要約親 BR-02）で GSC とは無関係のため、共有列に GSC 条件を掛けると GSC 未連携かつ WordPress 連携済みの `paid`/`admin` が要約一括を1件も実行できなくなる
- GSC 未連携／`property_uri` 取得失敗時に隠すのは **評価固有の操作系だけ**（「評価サイクルを開始」ボタンと評価側の理由表示）。チェック列は隠さない（評価親 BR-04 の例外・BR-06 の例外・FR-005 / AC-05 は 2026-08-27 にこの範囲へ改訂済み）
- **評価一括のみ先行し要約一括が未実装の期間**は、共有列に載る操作が評価だけになるため、評価親 AC-05 どおりチェック列も非表示とする。要約一括を投入した時点で常時表示へ切り替える
- 要約一括だけ先に出す場合でも、チェック列のモデルは同じ（後から評価を足しても列を増やさない。評価の GSC 条件を共有列へ持ち込まない）
- 行チェックの選択スコープ: **表示中ページ内**（要約親仕様）。ページ跨ぎは全選択。**ページ送りに加え、一覧の中身が入れ替わるフィルタ変更（カテゴリ・未分類・改善提案あり・評価未設定）でも選択を解除する**（1ページ目のままフィルタだけ変えると、表示されていない記事の選択が残るため）。GA4 集計期間の変更は一覧の行を入れ替えないので解除しない
- **全選択の母集団は「フィルタ非依存の全記事」で1本**（2026-08-29 PO 回答。正本は評価親 `gsc-bulk-evaluation-start-spec.md` BR-07、要約親 BR-05 は同定義へ追従改訂済み）。画面の絞り込み状態をサーバーへ送らない。1000件超は `updated_at` 降順の先頭1000件へ丸め、「1000 / 全 M 件」と明示する（両親の BR-05 / BR-07 例外で同型）
- 選択件数の **M は母集団の件数**であり、絞り込み後の `total`（`app/analytics/page.tsx`）とは別物なので流用できない。**フィルタ条件なしで一覧 RPC を呼び `total_count` だけ使う**のが最小
- **M の取得に失敗したときは 0 件と同じ扱いにしない。** 全選択（ヘッダのチェック）だけを無効化し、行チェックは使えるままにする。0 に丸めると「行のチェックは ON なのに実行できない」矛盾した状態になる（評価親 BR-07「母集団の件数 M の取得失敗」）

### 3.2 実行ボタン（別ボタン・条件付き）

| ボタン | 活性条件 | 親仕様 |
| --- | --- | --- |
| **評価サイクルを開始** | 選択≥1 **かつ** GSC 連携済み（**フィルタ非依存**。2026-08-29 Q-007 でゲート撤廃） | 評価 BR-06 / FR-010 |
| **AIで要約** | 「未要約」ON **かつ** 選択≥1 | 要約 BR-04 / FR-008 |

**ゲートは非対称でよい。** 誤実行のコストが違う。評価側は `gsc_article_evaluations` への insert で、既登録はサーバーがスキップする（評価親 BR-01）ため実質無害。要約側は記事ごとの LLM 呼び出し（要約親 BR-03。1件あたり最長180秒）でコストと時間を消費し取り消せない。根拠は評価親 BR-06。

- ボタン・Server Action・処理は統合しない
- 各ボタンは自仕様の対象条件を **サーバーで再検証** する

### 3.3 理由表示（選択あり・フィルタ OFF）

**2026-08-29 改訂: 理由表示は要約側だけになった。** 評価側はゲート撤廃（§3.2）により、選択≥1 なら常に開始できるので理由表示のスロットを持たない。

選択≥1 だが「未要約」フィルタが OFF のとき、「AIで要約」の代わりに **理由を1行** 出す。

~~「評価未設定フィルタを ON にすると開始できます」~~ は 2026-08-29 に**廃止**（評価親 AC-10 が「フィルタ非依存で開始できる」へ改訂されたため）。未実装の機能の理由は出さない（§3.4）。

なお、両理由文はいずれも `.agents/skills/growmate-ui-ux/ui-text.md` に未収録である（2026-08-27 実測。「未要約」「AIで要約」「評価未設定フィルタを ON にすると開始できます」「未要約フィルタを ON にすると要約できます」はいずれも0ヒット）。実装前に §5 の文言行のとおり追記する。

### 3.4 ツールバー配置（2026-08-29 PO 指定で確定。要約親 OPEN-001 の決着）

**GA4 集計期間の行に横並び**で置く。`app/analytics/AnalyticsClient.tsx` の `<div className="flex flex-wrap items-end gap-3 mb-4">`（GA4集計開始日／終了日／「期間を適用」を並べている行）の、「期間を適用」の右。

```text
[GA4集計開始日] [GA4集計終了日] [期間を適用]  [選択中 N 件 / 全 M 件]  [評価サイクルを開始]  [AIで要約 | 理由]
```

- **「フィルタ群の下」には置けない。** `CategoryFilter` は画面に常設されておらず、「フィールド構成」ダイアログの中にある（`AnalyticsTable.tsx` の `FieldConfigurator` の `dialogExtraContent`）。2026-08-27 版の本節はここを誤認していた
- ボタン文言は変えない。**「評価サイクルを開始」**（記事詳細 `EvaluationSettings.tsx` と統一。`ui-text.md`「評価」の行）と **「AIで要約」**。PO 提示のラフでは「評価サイクル設定」「AI要約」だったが、状態を表す語（設定）と動作を表す語（開始）を分ける `ui-text.md` の規約を優先する（2026-08-29 合意）

- 未実装の機能のボタンは出さない（評価だけ先なら要約ボタンなし）
- 活性ボタンと理由表示は同じスロットを使う（同時には出さない）
- 選択件数表示は `[選択中 N 件 / 全 M 件]`。**M は母集団（フィルタ非依存の全記事）の件数**で、絞り込み後の `total` とは別物（§3.1）。全選択が1000件に丸められた場合は `1000 / 全 M 件` と明示する（無言の打ち切りにしない）
  - 必須性の出典: **両方で必須**（要約親 BR-05 例外 / AC-09 Must、評価親 BR-07 例外 / §6 項目定義）。2026-08-29 に評価一括も丸めを採用したため、単独先行でも丸め表示が要る

## 4. 実装順（推奨）

1. **共有選択UI** — チェック列・全選択・選択件数・理由表示スロット（評価ボタンの GSC ゲート配線を含む。**同波リリース前提のためチェック列はゲートしない**。§3.1）
2. **評価サイクル一括** — Server Action・開始ボタン・トースト・未要約フィルタ以外の受け入れ
3. **未要約フィルタ + AI要約一括** — migration／フィルタ UI・要約ボタン・時間予算・4カテゴリ件数
4. **同時表示の回帰** — 両フィルタ ON でチェック1本・ボタン2つ・各 AC の主要シナリオ

**手順1〜4 は同波リリース（メタデータの前提）の内部工程**であり、手順1〜2 の時点でチェック列をゲートしないのは、同じリリースに手順3の要約一括が含まれるため。**手順ごとに分割してリリースする運用へ振れた場合**（＝評価一括だけを単独でリリースし要約一括を後続リリースへ回す場合）は、§3.1 第4バレットに従いチェック列も非表示とする。片方だけ先に出す場合も、チェック列の契約（§3）は崩さない。
