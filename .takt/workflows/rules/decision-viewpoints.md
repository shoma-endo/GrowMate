要件確認と設計判断では、次の3観点を必ず言語化する。この3観点は「開発前に不確実性を可視化し、可能な範囲で排除する」ためのものであり、記載量を増やすこと自体が目的ではない。対象の不確実性に見合う粒度で書き、書くことがなければ「なし」と判断根拠を書く（黙って省略しない）。

対象が既存仕様の小改修で、主要な設計・スコープ判断が発生しない場合は、3観点をまとめて1行「主要な設計判断なし（既存 `<path>` の踏襲のみ）」と書けば足りる。観点ごとの個別根拠は求めない。チェックリストを埋めること自体を目的化しない。

## 1. 代替案（今回採用しなかった選択肢）

- 主要な設計・スコープ判断については、比較した案、採用案、採用理由、却下した案とその理由を残す。エンジニアリングの意思決定はトレードオフの選択であり、選択肢と判断基準が読み取れない記述は不十分とみなす。
- 判断基準（工数、既存パターンとの整合、MVP としての出荷速度、運用負荷、将来の変更容易性）を明示する。
- 既存実装の再利用・拡張案は、**複数案を実際に比較して却下した場合のみ**代替案として起こす。単一候補で自明な再利用判断は推奨実装方針に留め、二重に書かない。
- 合意済み要件を満たさない案を代替案として並べない。
- 代替案を検討していない場合は「検討不要と判断した理由」を書く。空欄のままにしない。

## 2. 懸念点（意思決定はしたが不安が残るもの／分からないもの）

- 採用案を前提にしたうえで残る不安を書く。代替案（不安なく却下した選択肢）と混同しない。
- 「調べたが判断できない。レビュアーの助けが必要」も、そのまま懸念点として書く。隠さない。
- 種別=判断できず助けが必要 とするのは、**答える人を特定でき、その回答が無いと仕様の該当箇所を書けない**ものに限る。答える人を特定できない、または書けはするが不安が残るだけのものは 種別=不安が残る とする。この1語が仕様書での行き先（確認質問 Q-xxx かリスク R-xxx か）と仕様レビューの完了可否を分ける。
- ToB SaaS として、データ量・リクエスト量の増加で前提が崩れる条件（この機能はどのくらいの期間もつ想定か、どうなった場合にもたないか）を検討し、無視できない場合に書く。
- 要件に無い安全機構（Kill Switch / feature flag / 専用の設定テーブル / 監視ダッシュボード / 冗長化 / リトライ基盤）の不在は、懸念点として書かない。書いてよいのは `.takt/workflows/rules/mvp-scope.md` の例外条件（放置するとデータが壊れる / 誤った外部送信が続く / 課金が膨らむ / 既存手段で止められないことを具体的に示せる）に該当する場合に限る。
- 懸念点は要件を追加する根拠にしない。対応が要件外になる場合は Non-goals か未決定事項へ振り分ける（`.takt/workflows/rules/mvp-scope.md` に従う）。

## 3. 未決定事項（今は決めないもの）

- 「なぜ今決めないのか」と「いつ・誰が決めるのか」をセットで書く。**どちらか一方でも**書けないものは未決定事項にしない。答えが出るまで先へ進めないなら step の判定に従って要件確認へ戻し、判断を助けてほしいだけなら懸念点（CON-xxx）へ振り分ける。
- 実装時に決めればよいもの、そもそも今は決められないもの、決める必要がないものを区別する。
- あえて決めないことで着手までのリードタイムを短縮し、実装時に決める事項を明示してタスク漏れを防ぐことが目的。判断の先送りを正当化する欄ではない。
- 未決定であることを理由に、要件に無い安全機構・汎用化・拡張点を先回りで作らない（`.takt/workflows/rules/mvp-scope.md` に従う）。
