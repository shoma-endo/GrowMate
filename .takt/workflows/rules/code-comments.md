**コードコメント規約**（参考: [note / shibats](https://note.com/shibats/n/n54ba80742bae)、[Qiita / ohakutsu](https://qiita.com/ohakutsu/items/b087e6959699769b93a6)）

コメントは「次にこのコードを触る人（AI を含む）が、コードからは読み取れないこと」だけを書く。迷ったら書かない。書く前に、名前・型・関数の切り出し・テストで表せないかを先に試す。

**書く**（コードで表せない場合のみ）:

1. なぜそうしたか — 自明な実装を選ばなかった理由、外部 API・クライアント要件の制約（例: GSC は通常 2〜3 日遅れる）
2. 意図か不具合か — 一見バグに見えるが仕様である振る舞い
3. 直感に反すること — 予想と違う出力・副作用・順序依存。原因が自分たちのコードなら、先に名前・切り出し・型・構造で直感どおりの形に直す。コメントで残すのは、外部 API・ベンダー・プロトコルなど変えられないものが原因のときと、直す範囲が今回の変更を超えるときだけ
4. 意図的な近道の上限 — 天井と見直しのきっかけを 1 行で（例: 全件走査。件数が数千を超えたら索引化）
5. 役割 — 名前と型から役割が読み取れない関数・型・定数の JSDoc

**書かない**:

- コードを読めば分かる「何をしているか」の言い換え
- 変更履歴・経緯（「〜に変更した」、PR 番号、日付、旧実装の説明）。git に任せる
- 未検証の前提だけのコメント（「〜の想定」）。型・アサーション・テストで表す
- コメントアウトしたコード、区切り線などの飾り

**抑制コメント**（`eslint-disable*`・`@ts-ignore`・`@ts-expect-error`・`@ts-nocheck`）:

- 正しさ・安全を守るルール（`react-hooks/exhaustive-deps`、`@typescript-eslint/no-explicit-any`、型エラー全般など）の違反は、抑制せずにコードを直す。
- 新たに足してよいのは、ルールが誤検知している・書式だけのルールであるときに限る。理由を同じ行に書く（例: `// eslint-disable-next-line <rule> -- <理由>`）。
- 抑制を含むコードに触れたら、そのルールが何を防ぐかを確かめ、直せるなら同じ差分で抑制を外す。

**書き方**:

- 実行される時点の状態を書く。分岐の前に後続の処理を先回りして説明しない。`if` / `else` の中には、その条件が成り立った時点の状態を書く。
- コードを変えたら、同じ差分で周りのコメントを直すか消す。実態とずれたコメントは無いより悪い。
- 既存コメントの一括削除・書き換えはしない。触ったコードの範囲だけ適用する。
