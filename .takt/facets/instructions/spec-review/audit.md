`.agents/skills/spec-review/SKILL.md` を正本として、対象仕様書をレビューしてください。

必須条件:
- 共通観点 A（完全性）/ B（既存コード整合）/ C（非機能）/ D（セキュリティ）を全項目確認する。
- `docs/templates/requirement-definition.md` の項目を使い、目的・成功指標、業務要件、対象範囲・Non-goals、機能要件、Gherkin受け入れ条件、非機能要件、データ・外部連携、制約・前提・依存関係、トレードオフ、リスク・未確定事項、テスト・リリース・ロールバック、承認状態の不足を確認する。
- テンプレート項目が対象外の場合は、仕様書に対象外の理由があることを確認する。理由のない空欄は `needs_fix` とする。
- 対象範囲と Non-goals を照合し、要件達成に直接必要でない画面・UI・機能・改善を仕様書へ混入させない。混入している場合は `needs_fix` とする。
- **MVP 最優先（`CLAUDE.md` Core Rules / knowledge facet `growmate.md`「Delivery Principle: MVP First」）を判定軸に含める。** 指摘を出す前に「これは要件が求めているか」を自問する。**チェックリスト項目の存在自体を、要件を発明する根拠にしない。**
  - 要件に無い安全機構（Kill Switch / feature flag / 専用の設定テーブル / 監視ダッシュボード / 冗長化 / リトライ基盤）の**不在を指摘しない**。指摘してよいのは、要件かクライアント合意に明示がある場合、放置すると**データが壊れる・誤った外部送信が続く・課金が膨らむ**場合、または既存手段（デプロイ巻き戻し・該当UIの非表示・既存 env フラグ）で止められないことを具体的に示せる場合に限る。
  - 逆に、**仕様書が要件外の安全機構を作ろうとしている場合は 🟡 として削減を提案する。**過剰実装も `needs_fix` の対象である。
- 新規機能の既定対象ロールが `admin` / `paid` であることを確認する。`trial` / `unavailable` を含める例外は、理由と承認が仕様書に明記されていなければ `needs_fix` とする。
- 認可条件、未認可時の利用者向け挙動、Server Action・Route Handler・APIなどサーバー側での認可強制が仕様書に明記されていることを確認する。
- 下記添付の `spec-review-scope.md` で判定された条件付き観点の正本ファイルを読み、該当チェックリストを適用する。
- B の確認では仕様書の記述を鵜呑みにせず、実コード（services / actions / components）を読んで再利用対象・乖離を検証する。
- 外部サービス連携が対象の場合、下記添付の `spec-review-scope.md` で列挙した公式ドキュメント URL を **WebFetch で実際に取得し**、`.agents/skills/spec-review/external-services.md`「一次情報検証 > 検証必須項目」（エンドポイント / 必須パラメータ・フィールド名 / 権限スコープ / レート制限 / 非推奨告知 / 前提条件 / データ反映遅延）を照合する。記憶・過去の実装・ブログ記事・要約を根拠にしない。あわせて同ファイル「連携ライフサイクル（失効・剥奪・切断）」のチェックリストを適用する。
- 公式ドキュメントを根拠にした指摘には、参照 URL・確認日（YYYY-MM-DD）・**公式ページ本文の verbatim 引用**を必ず添える。要約を経由した引用は禁止。公式に記述が見つからない挙動は断定せず確認質問に隔離する。
- 外部サービス連携が対象の場合、`spec-audit.md` の冒頭に **「公式ドキュメント照合: 実施 / 未実施」** を必ず書く。実行中の provider に web 取得手段（WebFetch 等）が無く照合できない場合は「未実施（provider に web 取得手段なし）」と明記し、記憶や既存実装で代替して照合したことにしない。
- WebFetch が失敗した URL は「未確認」として `spec-audit.md` に残し、レビュー自体は止めずに他の観点を続行する。
- 指摘は「問題箇所 / なぜ危険か / 修正案」の形式で、重大度（🔴/🟡/🟢）を付ける。
- クライアント確認が必要な論点は修正案を断定せず、確認質問（Pre-implementation Questions 形式）として隔離する。
- ステータス、ゲート表、未確定事項、確認質問、レビュー記録を突合し、対象スコープに関係する「未回答 / 未確定 / 合意待ち / 受領待ち / 見積待ち」の項目を抽出する。過去に解消済みの項目、対象外フェーズの項目、単なるリスク記録は未解決として数えない。
- **実装前ゲート**（例: UIたたき台／UIモックの PO 承認 CP）は、仕様書が「仕様レビューのブロッカーにしない／実装前ゲートとして残置」と明記している場合、本 audit の未解決承認ゲートに**数えない**（`approved` を妨げない）。その残置は最終レポートと仕様書に残し、実装着手は `.takt/workflows/spec-to-pr.yaml` 側が止める。明記が無く実装に必須なら通常どおり未解決として数える。
- 判定基準（structured output の verdict）: 🔴 がゼロ、対象スコープの未解決質問・意思決定・外部入力・承認ゲートがゼロ、かつ 🟡 が修正済みまたは理由付きで残置合意済み（仕様書の「レビュー記録」セクションに理由が記録されている）なら `approved`。エージェントが解消できる 🔴/🟡 があれば `needs_fix`。対象スコープの未解決事項が1件でも残る場合は `approved_with_questions`（レビュー完了にはならず ABORT する）。判定理由を先に reason_1_to_3_lines へ1〜3行で書き、その根拠に基づいて verdict を出す。
