下記に全文添付された `spec-audit.md` を一次情報として、対象仕様書の未解決指摘だけを修正してください。

必須条件:
- 編集対象は `docs/` 配下の対象仕様書（および付随する docs）に限定する。プロダクションコード・設定ファイルは一切編集しない。
- クライアント確認が必要な論点は本文を勝手に確定させず、仕様書内の「リスク・確認質問・未決定事項 > 確認質問」へ質問ごと明記する（`Q-xxx`、状態=クライアント確認中。テンプレートでは §12 だが、既存仕様書は番号がずれることがあるため見出し名で探す）。未解決の実装判断・外部入力・承認ゲートも同様に確定前の状態を明記する。対象スコープに未解決事項が残る場合、audit は `approved_with_questions` を出してもレビュー完了にはせず ABORT する。
- 理由付きで残置合意とする 🟡 論点は、仕様書内の「レビュー記録」セクションに理由付きで記録する。`spec-audit.md` 冒頭に「公式ドキュメント照合: 未実施」とある場合はその旨も同セクションに記録する（audit の再実行と後続の spec-to-pr workflow はこのセクションを正本として参照する）。
- 外部サービスの公式ドキュメントを根拠に本文を直す場合、仕様書に参照 URL・確認日（YYYY-MM-DD）・公式ページ本文の verbatim 引用を残す。引用と、そこから導いた解釈は分けて書く。裏取りが必要なのに `spec-audit.md` に URL・引用がない指摘は、自分で WebFetch して確認してから直す。
- 指摘への対応方針が複数あり判断できない場合は、勝手に選ばず ABORT する。
- 修正した指摘と、対応しなかった指摘（理由付き）を報告する。
- **取りこぼし防止（必須）:** 事実主張・用語・ルール ID の文言を直したら、対象ファイル（と audit が名指しした付随 docs）を **全文 grep** し、同じ誤主張・旧用語が残っていないことを確認してから完了とする。指摘行だけ直して同ファイル内の別節に旧記述が残る状態は不合格（再 audit の `persists` を自分で作ることになる）。
- **実装メモ + 親仕様:** scope が「親は矛盾チェックのみ」のとき、親の深い改訂（AC 分割・画面設計の全面書き換え）は必須にしない。メモ側の契約を正し、親追従が必要ならレビュー記録に「親は別ランで追従」と残す。audit が親の最小限の矛盾解消を明示している場合のみ、その範囲で親を直してよい。
