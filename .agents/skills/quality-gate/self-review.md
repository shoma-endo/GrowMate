# セルフレビュー・プロトコル

全てのコーディング作業完了後、返信前に必ず以下の 2 パスのセルフレビューを実行してください。

## Pass 1: 静的解析と整合性 (Verification)

このパスでは、コードが正しく動作し、プロジェクトの基本ルールに沿っているかを確認します。

- [ ] **自動検証**: [`SKILL.md`](SKILL.md) の `npm run verify` が成功していることを確認。
- [ ] **型安全**: TS ファイルの場合、`any` の乱用や型不一致がないか確認。`unknown` + narrowing または `zod` スキーマの使用を優先。
- [ ] **命名規則**: `project-naming` スキルを読み直し、新規ファイルや変数が規約通りか確認。
- [ ] **UI 文言の表記統一**（表示文言を追加・変更した場合）: `npm run verify:ui-text` が成功していることを確認。機械判定外の用語一貫性・略語の初出・句点・英日間スペースは [`manual-testing.md`](manual-testing.md) で確認。正本は [`growmate-ui-ux/ui-text.md`](../growmate-ui-ux/ui-text.md)。
- [ ] **既存破壊の防止**: 既存の `interface` や共有定数を変更した場合、その影響範囲（`rg` で検索）を調査したか。共有ロジック・設定値・モデルを変えた場合は、同じ用途の兄弟設定・他の生成フロー・他の外部連携にも揃える必要があるかを `rg` で確かめ、今回のスコープ外なら報告に残したか。

## Pass 2: 品質とコンテキスト (Quality & Context)

このパスでは、実装がプロジェクトの設計思想やセキュリティ基準に合致しているかを確認します。

- [ ] **スコープ遵守**: 変更差分が対象仕様書と実装計画（`plan.md` の `対象スコープ:`）の範囲内か。要件にない画面・UI・機能・改善、ついで修正、将来対応が混入していないか（混入があれば修正または差分から除去）。
- [ ] **実装指針**: `implementation-guidelines` スキルに基づき、SupabaseService 経由の統一、Server Actions / Route Handlers の使い分け、機密情報のサーバー側限定を遵守しているか。
- [ ] **セキュリティ**: `supabase` スキル（`rls.md`）に基づき、RLS やセキュリティ定義者関数に関わる変更が安全か確認。入力検証・ハードコードされた秘密の有無を確認。
- [ ] **エラー処理**: `nextjs-server` スキル（`error-handling.md`）に基づき、`ERROR_MESSAGES` 経由・`ServerActionResult` 形式を遵守しているか。
- [ ] **未認証ユーザーの保護**: ログイン不要なパブリックページ（`/home`, `/privacy`）に、ユーザー名や通知トーストなどの認証済み情報を漏洩させていないか。
- [ ] **エラー表示**: エラーが適切に捕捉・処理され、意味のあるメッセージでユーザーに伝わるか。サイレント失敗がないか。
- [ ] **コード品質**: 重複コード（DRY）がないか、デッドコード・コメントアウト、マジックナンバー（定数化）を確認。フォーマットは一貫しているか。
- [ ] **関数設計**: 単一責任、長さ（50行以下）、入出力明確、副作用最小化。
- [ ] **撤去と一時物**: 機能・仕様をやめた場合、コード・型・未使用メソッド・文言・docs・ルールファイルの残りまで消したか。ローカル検証用のスクリプト・モックデータ・開発用ログを差分に入れていないか。
- [ ] **主張の根拠**: 原因・影響・「直った」の説明に、確かめた手段（SQL・ログ・実行結果・実画面）を添えたか。守りの処理を足す前に、該当するデータが実在するか件数を確かめたか。
- [ ] **テストの過不足**（テストを追加・削除した場合）: `docs/specs/testing-strategy.md`「過剰なテストを書かない」の「書かない」「消さない」基準に沿っているか。追加したテストは仕様書の目的・受け入れ条件か fix の回帰に対応しているか。下位層で固定済みの内容を上位層で重ねていないか。fix の回帰テストや、ある分岐を通る唯一のテストを消していないか。
- [ ] **パフォーマンス**: Supabase クエリで N+1 を起こしていないか。ループ内でのクエリ発行は避ける。
- [ ] **対象時のみの非機能チェック**: 変更が該当する場合だけ、次を確認する。
  - DB / SQL: `supabase` に基づき、INDEX、データ量、トランザクション範囲、ロック／デッドロック、RLS の影響を確認する。
  - HTTP / 認証: `nextjs-server` に基づき、入力検証、認証・認可境界、XSS / CSRF の影響を確認する。
  - 外部 API / 非同期処理: `spec-review` に基づき、タイムアウト、リトライ、冪等性を確認する。Google 系は `google-integrations` も適用する。
  - 依存関係: 依存を追加・更新した場合、`npm audit` と既存ライブラリとの互換性を確認する。
  - 「対応なし」「対応不可」とした項目は、根拠と残存リスク、受容者、期限を記録する。

## 運用ルール

1. 修正が必要な箇所が見つかった場合は、即座に修正し、再度 Pass 1 から開始してください。
2. 複雑な機能追加の場合、実際の動作確認（手動検証）の結果もセルフレビューに含めてください。
3. [`manual-testing.md`](manual-testing.md) に従い、変更した画面・機能の確認観点を押さえてください。
4. 修正の優先度: 🔴 Critical（セキュリティ・データ損失・重大バグ）→ 🟡 Important（パフォーマンス・保守性）→ 🟢 Nice-to-have（スタイル・軽微な改善）の順で対応する。
5. TAKT の外で commit するときは、その前に変更をサブエージェントにレビューさせ、通ったかどうかを報告に書く。一度通したレビューを理由なく回し直さない。TAKT ではワークフローのレビュー工程で代える。
6. 完了報告には、何が変わったか、最初の目的を達成したか、既存ユーザー・既存機能・UI への影響の有無を書く。
